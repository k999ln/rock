# 104 本人の鍵で暗号化する（案 K）— Memory と成果のファイルを、運営も読めない形にする

本人の決め: K3（2026-11-21 22:54。[07](../../docs/structure/07-decisions-from-minutes.md)）。設計は [compute-placement.md 0.4](../../docs/compute-placement.md)。

## 決めてある事（変えない）

- 暗号化するのは **Memory と成果のファイルだけ**。仕事の状態（Work・Job・Receipt）・請求・権限は、運営が読める形のまま。
- 鍵の作り:
  - 本人ごとに、データの鍵（DEK、AES-256-GCM）を 1 つ、本人の端末で作る。
  - DEK は 2 通りで包んでサーバーに置く。① パスキーの PRF の値から HKDF-SHA256 で作った鍵。② 復旧コード（128 ビットの乱数。最初に 1 回だけ見せる）から HKDF-SHA256 で作った鍵。
  - サーバーに置くのは、包んだ DEK と暗号文だけ。DEK・PRF の値・復旧コードは、サーバーへ送らない。
- PRF は「あれば使う」。PRF の値が返らない環境（他社のパスワード管理など）では、復旧コードの鍵だけで使える。
- 引き換えとして画面に出す事: 運営は中身を読めないので、推薦と検索に中身を使わない。パスキーと復旧コードを両方無くすと戻せない。

## やること

1. `lib/owner-key.ts`（ブラウザで動く純関数）: DEK の生成、PRF・復旧コードからの鍵の導出、包む・開く、ファイルと Memory の暗号化・復号（ファイルごとに別の 96 ビットの nonce）。
2. 保存: 包んだ DEK の表（owner・包み方・版・作った時刻）。成果のファイルと Memory は、暗号文と nonce と版だけを保存する。暗号化の前の物と混ざらないよう、版の欄で分ける。
3. 画面: 最初の保存の時に、復旧コードを 1 回だけ見せて、書き写したことを確かめる。別の端末では、パスキー（同期されていれば）か復旧コードで開く。
4. 既存の平文の Memory・ファイルを、本人が開いた時に暗号文へ移す（本人の操作で 1 回。黙って消さない）。

## 合格条件

- 試験の DB とログを探して、暗号化の対象の平文が 0 件。
- 2 台目の端末（試験の別の環境）で、復旧コードだけで開ける。PRF の値だけでも開ける。
- PRF の値が返らない環境で、保存と復号が通る。
- 1 ビット書き換えた暗号文は、復号で拒まれる。
- 運営の権限で中身を読む口が無い（API の一覧で確かめる）。
- `npm run typecheck`・`npm run lint:product`・関係する試験。

## やらないこと

- 仕事の状態・請求・権限の暗号化。運営の側での鍵の預かり（作らない）。本番 D1 への migration（本人の許可の後）。
