## 商品購入の現行実装

対象は有効なmanifest reviewを持つ `verified` Packageかつ `external_contract` の円建て買い切り。LLMもこのPackage条件で販売でき、カタログ掲載だけでは販売商品にならない。登録者の所有権とStripe受取先をWeb D1へ結び付け、価格・条件のrevisionを購入時に固定する。金額・受取先・手数料はサーバーが決定し、Stripeの署名と最新入金状態を検証する。10%はapplication fee、残り90%は提供者への分配額であり、決済処理費用や返金・紛争は別に扱う。

注文の購入アクセスはSky内の記録であり、第三者MCP側の認証・利用権強制を代行しない。有料提供者は実サービスのアクセスと返金後の失効を実装する。今回の経路は注文購入であって、下記のTool貢献に応じた成功報酬・作者間還元や旧Billing Workerの月額上限を有効化するものではない。

Web D1 migration `0018_sky_commerce.sql`、server-only `SKY_PAYMENTS_MODE` / `SKY_STRIPE_SECRET_KEY` / `SKY_STRIPE_WEBHOOK_SECRET` / `SKY_PAYMENT_ORIGIN` を使用する。liveでは本人ヘッダーを保護するSites gatewayが必要で、直接Originの迂回公開は不可。Stripe署名Webhookの匿名到達も配備先で確認する。カード・銀行情報はStripeへ入力し、Skyに保存しない。[API・導入手順・返金・受入条件](sky-billing.md#sky-market決済2026-09-27実装)を正本とする。

## 確定した方針

- tobがSkyへ登録、接続、公開し、基本検査と利用分析を受けるSky利用料は0円。
- tob商品の売上に対するSky手数料は10%。残り90%を提供者の売上として扱い、外部実費・返金・税は別項目で表示する。
- 決済、外部API、AIモデル、cloud等の第三者実費はSky手数料から分離して表示する。
- RQ20の8.88 USDはToCへの先払い基本料金ではなく、自動化の検証済み月間収益からだけ回収する上限とする。
- 売上0なら回収0、未達分の債務化・翌月繰越・カード請求はしない。登録・接続・公開の基本利用料は0円で、売上が発生した場合だけ10%をSky手数料として扱う。
- ToC/ToBの貢献分配率、最低払出額、本人確認、税、返金負担はProvider接続前に確定する。
- 最新の還元案は、**Sky経由の検証可能な利益に対して実際に回収した成功報酬の一部**を原資とする。成功報酬と別に開発者還元の追加請求を重ねず、未合意の控除をしない。従来の「回収済み利用料」案はこの訂正で置き換えるが、契約・実装移行は未完了である。
- 還元率、複数Toolの配分方式、留保期間、払出し閾値は未確定。未設定中は金額を確定せず、実送金は無効にする。無料公開の方向性からlicense変更や課金条件変更を導かない。

## Skyとしての一つの利用経路

利用者はSkyで目的に合うToolチームを選ぶか編成し、Tool、役割、接続状態、必要な許可、実費、構成版を確認する。参加後はZemaへ引き継ぎ、同じ仕事の状態・成果を見る。既存の`automation-fund`の構成・参加・分析を再利用し、別のFundホームを新設して二重管理しない。既存のFund URLや保存済みIDは互換入口として扱う。

開発者はSkyでToolを登録し、どの版がどの実行に使われたか、検証された貢献、配分準備の明細、停止理由を確認する。登録数、選択数、実行成功、確認済み収益、検証可能な利益、成功報酬の請求、実回収、開発者配分、実払出しはそれぞれ別状態である。Fundへの加入やTool候補への掲載だけで収益への貢献を認定しない。

Walletは成功報酬の根拠と請求内容を示し、支払い・領収・照合を円滑にする窓口とする。外部サービスから本人の銀行口座へ入金される場合、銀行入金の確認とSkyへの支払いは別の出来事である。銀行口座登録や売上確認だけで自動引落し権限を取得したとは扱わず、回収方法と本人の支払同意を別途確定する。

## 還元の最小契約

次は追加機能の設計契約であり、この記述だけでは実装・本番合格にならない。

| 記録 | 信頼する根拠 | 不足時の扱い |
| --- | --- | --- |
| 作者とTool版 | 認証済み登録者、検証済みpackage key/manifest hash、実行時に固定した版と作者 | manifestの`developer.id`や`developerRecipientId`だけでは本人・受取先確認済みにしない |
| 実行貢献 | 本人所有の非sample完了job、実行時Tool版、必要ならその時点のFund ID/revision | 過去jobに版/作者証拠がなければ帰属未確認。現在のmanifestや後日の参加状態から補完しない |
| 収益との関係 | Provider署名Earning Receipt、Execution Receipt、利用者・Tool・時刻、Billing適用結果の一致 | 実行完了だけでは売上にしない。証拠不足は配分対象として確定しない |
| 還元原資 | 新契約で定義する当該成功報酬の実回収証拠 | 利益発生・請求だけでは回収済みとしない。旧`sky_fee_minor`や回収指図を新成功報酬へ自動変換しない |
| policy | 版/hash、利益の定義、成功報酬率、月上限の扱い、回収方法、開発者への率/weight、丸め、留保、返金規則 | 最新要望を確認中。draftのまま金額は未確定、実払出し無効 |
| 受取先 | 作者本人との検証済み対応付けと有効な受取先 | 作者アカウントIDを送金先へ読み替えず、受取先未確認で停止 |

貢献記録はexecution ID、Tool ID、package版/hash、登録者の内部参照、受取先確認状態、Fund実行時参照、証拠hashを保持する。公開表示や開発者画面へ利用者の原稿・成果本文・個人情報を流さず、本人の貢献に必要な最小情報へ絞る。複数Toolへの分配は将来の版付きpolicyと実際のstep証拠を必要とし、一つの売上全額を各Toolへ重複配賦しない。

## pending明細と精算の分離

初期の明細は既存Billingを参照する貢献・配分準備記録である。新たな残高、利用者債務、送金指図を作る別会計にはしない。policy未決や回収未確認の金額は`null`相当の「未確定」であり、0円確定や獲得報酬と表示しない。policy、作者帰属、収益照合、実回収、返金照合、受取先の不足を別理由で示す。

将来policyが確定した場合も、配分原資は実回収済み成功報酬から返金・取消・既配分・必要留保を照合した範囲内に限る。これは今回の率決定や送金実装ではない。既存の利用者払出し台帳と`payout_instructions`を開発者還元のために変更・流用しない。

同じ実行・Tool版・貢献ID、Earning Receipt、回収証拠、policy版による再処理は同じ記録を返し、異なる内容は競合拒否する。policy版が変わっても同じ原資を再び全額配分できない一意な原資参照を必要とする。返金・chargeback・作者の権利紛争は元記録を削除せず、参照付きの保留・取消・相殺記録で追う。返金のProvider経路が未受入の間は解決済みを装わず、実払出しを開始しない。

## 今回の受入と本番への残件

最小縦断の受入対象は、Skyで編成/参加→Zemaで実行管理→検証可能な貢献記録→policy未決の配分準備明細まで。作者なりすまし、未検証package、非所有/未完了/sample実行、版不明の過去job、重複/内容競合、未署名収益、請求と実回収を区別することを確認する。旧経済契約から新成功報酬契約への移行を未完了として示し、テスト用証拠を実売上・実回収・実還元へ換算しない。

実際の作者binding、実行時snapshot、Billing実回収readback、返金adapter、配分policyの有効化、受取先確認、開発者実払出しは、対応sourceと受入証拠が揃うまで未完了とする。配分率と払出し条件を後から設定できる設計は、設定済み・送金可能を意味しない。

## フロントの役割

MCP接続・管理はSky本体の中核機能として、接続の簡単さと、その裏側の参入障壁を同じ操作面で扱う。Sky画面に常設sidebarや独立したSky Networkナビゲーションは置かず、最初の画面に状態と接続・管理導線を表示する。ToB向け掲載もSky内のダイアログで開く。

1. MCP URL、Registry名、packageの入力
2. Connection Passportによる作者、版、transport、OAuth audience、価格、受取人の確認
3. Execution Covenantによる呼出し単位の権限・データ・予算・期限
4. Contribution Receiptによる成果へ使われた貢献の検証
5. Reconciled Settlementによる取消、不明状態、重複の照合

## 従来のMCP・収益分配実装の境界

旧Sky Networkの外部MCP「安全確認」は合成フロントデモであり、入力URLへの通信、資格情報取得、公開、現金保管、送金を行わない。ローカルMCPの実接続と今回のMarket決済を区別する。収益精算Workerは署名付きEarning Receipt、月888 cents上限、追記台帳、払出し指図まで実装したが、旧収益系の販売・決済・払出しProviderは未接続である。Connection Passportの外部Provider表示値も合成である。

実払出は、販売主体、本人確認、提供地域、決済provider、税、返金、chargeback、最低払出額、資金保管方式を確定し、sandboxと本番受入を通過するまで有効化しない。
