## 01 設計の中心と今回決めること

**RockstarOSを、将来のコロニーで設備・人・資源・貨物・保守・通信をつなぐ現地運用の中核にする。** rocketstarが輸送、A-LINKが外部通信、avokadoが人との接点を担当し、同じ資産ID・仕事ID・実行履歴で結ぶ。画面の名称だけをOSとするのではなく、切断時にも現地に残る権限・状態・仕事・記録をOSの仕事にする。

最終的な建設場所、人数、滞在期間、補給と退避条件は未決定。設計を止めないため、初期開発は**有人居住を伴わない地上試験環境**を仮置きする。これは宇宙コロニーの目的地を地上へ変更する決定ではない。地上・地球軌道・月面の設備を、ミッション別プロファイルとして同じ運用核へ接続する。

| 決定ID | 本版で選ぶ設計 | 固定の範囲 |
| --- | --- | --- |
| ADR-01 | RockstarOSを現地運用核にする | 本計画の基本方針。単一機械・単一カーネルに全機能を集中させない |
| ADR-02 | 設備の局所制御と独立保護を分離 | Core、AI、avokado、地球回線を重要設備の制御ループに入れない |
| ADR-03 | 指令の状態と物理的な完了を分ける | 通信到着、受理、設定反映、動作完了、実測確認を区別 |
| ADR-04 | 現地を設備状態の正本にする | 地球側は遅延した複製。復帰時は現物との照合を先に行う |
| ADR-05 | SIM_ONLYと実機経路を分ける | 本版は公開試験鍵・合成データのみ。実機モードを備えない |
| ADR-06 | 現行無人ロケットと有人輸送を分ける | rocketstar C3を有人宇宙船や完成済み貨物船として扱わない |

今回の完成範囲は、全体アーキテクチャ、接続・権限・復旧の設計、輸送引渡し契約、検証台帳、限定した動作模型。居住設備の容量・配管・構造・実装機種や、ロケットの製造図面が全て確定したという意味ではない。

## 02 全体構成と故障の境界

{{SYSTEM_DIAGRAM}}

RockstarOS Coreは、設備制御器から状態を取り込み、資源を割り当て、承認された作業を送る。設備制御器は、最新の現地状態を使って実行可否を再判定する。重要設備の保護・警報・必要な現地操作は別の故障領域に置く。共通電源や共通ネットワークによって、独立性が見かけだけにならない構成を実機で検証する。

| 領域 | 主担当 | 止まった場合の設計動作 |
| --- | --- | --- |
| 独立保護 | 機器保護・局所警報・現地操作 | 他領域の停止に依存しない。具体方式は設備選定時に確定 |
| 局所制御 | 空気・水・電力・熱などの専用制御器 | 認定された運転プロファイルと故障時処置を現地で継続 |
| 現地運用核 | RockstarOS Core | 新しい監督操作は停止。設備側の制御を一律に停止しない |
| 操作・AI | avokado、通常画面、会話支援 | 他の操作経路と局所警報を残す。音声・身振りだけに依存しない |
| 外部連絡 | A-LINK・地上網・将来の宇宙中継 | 保存と再送待ち。期限のある指令は再接続時に再検査 |

NASAの安全資料は、冗長計算機の共通原因故障と保護機能の独立性を扱う。本設計も、同じソフトを二台で動かすだけでは重要設備の独立保護が成立したとしない。[S4: NASA-STD-8739.8B](https://standards.nasa.gov/sites/default/files/standards/NASA/B/0/NASA-STD-87398RevB.pdf)

## 03 RockstarOSの実装基盤と追加モジュール

既存RockstarOSのソースを読み、再利用候補と不足を監査した。対象HEADは 5d5f3dc4f73ac3389c8dbc00f9ca6e8beba526e0。元リポジトリは変更していない。保存・権限・承認・仕事・結果不明の照合には実装がある。生命維持・飛行制御・設備の物理保護の実装は確認できない。

| モジュール | 責任と接続先 | 本版の到達点 |
| --- | --- | --- |
| Identity / Authority | 操作者、役割、設備範囲、有効期限、承認 | 既存Platformの境界を参照。現場資格・認証・鍵基盤は追加設計 |
| Asset / Configuration | 設備ID、部品、版、校正、配線・区画関係 | データ契約案。実設備台帳の構築は未実装 |
| Telemetry / Alarm | 品質と時刻付き観測、欠測、警報、確認履歴 | 合成電力データの限定実装。汎用時系列系と警報系は設計 |
| Work / Broker | 提案、承認、送信記録、照合、保守手順 | 独立SIM実装を付属。既存OSへの組込みは未実施 |
| Resource Scheduler | 電力・通信枠・作業・貨物の予約 | 非重要模擬負荷の優先順位計算のみ実装 |
| Local Adapter | 型付き操作と設備プロトコルの変換 | Python内の模擬経路のみ。物理バスは未選定 |
| Logistics / Evidence | 物品、所在、封印、品質、点検・受領証拠 | 共通引渡し契約と状態遷移を設計 |
| Communication Gateway | 外部回線、接触計画、蓄積転送、重複除去 | 将来接続仕様。BPv7 / BPSecは候補で未実装 |
| avokado Shell / AI | 状態の説明、提案、作業支援 | E3の4本のTowerとHubを前提に接続を設計 |

既存Webの仕事状態は active / review / completed / cancelled。今回の指令状態をそのまま上書きしない。指令がUNCERTAINの間は仕事をactiveの照合待ちに置き、取消や完了へ丸めない。SIM専用の仕事テンプレートを追加し、sample=trueの結果を実作業の合格に数えない。article等の既存テンプレートへ設備指令を埋め込まない。

既存Control Coreの純粋テスト4件は監査時に再実行した。QEMUとPixel APKの起動・復旧は過去の保存証拠であり、今回のコロニー実機受入ではない。詳細は os_inventory.md / json に、元ファイルのハッシュ付きで収録する。

## 04 データの正本と接続契約

機器ごとの接続契約は、データ型、単位、版、所有者、権限、期限、拒否理由を持つ。自由記述のAI回答を設備の命令として渡さない。運用データと個人の会話・映像データは保存境界を分け、設備に必要な最小限の情報だけを渡す。

| データ | 必須の意味 | 正本・更新規則 |
| --- | --- | --- |
| Asset | assetId、親区画、型式、製造番号、設定版、校正証拠 | 現地資産台帳。状態変更には仕事IDと担当者を記録 |
| Observation | チャネル、単位、値、品質、採取/受信時刻、起動世代、連番 | 設備の観測が正本。受信時刻で採取時刻を置換しない |
| Command | 対象、操作型、要求/仕事/指令ID、内容ハッシュ、期限、制御権、期待版 | Coreが意図を保存、設備が受理と結果を保存 |
| Result | 元指令、受理/実行/完了/不明、理由、版、証拠 | 設備記録を照合。地球側の送信成功で完了にしない |
| Resource Reservation | 資源ID、量と単位、時間帯、優先度、版、失効条件 | 現地Core。ただし局所保護と機器側上限が常に優先 |
| Manifest / Handover | cargoId、容積・質量の測定根拠、輸送条件、所在、検収 | 受渡し両側の照合と受領証拠。予告到着は在庫に算入しない |
| Evidence | 手順版、担当、入力/出力、観測、ファイルハッシュ | 改変・欠損を検出し追跡。ハッシュだけで物理的真実を保証しない |

本版の具体スキーマは command / receipt / telemetry の3種類。識別子は rockstaros-colony-command/1、rockstaros-colony-receipt/1、rockstaros-colony-telemetry/1。component IDは dev.rock.colony.supervisor。contracts/ に標準JSON Schemaを収録し、未定義フィールドを許さない構造を定義する。標準バリデーターは未導入のためスキーマ標準検証は未実行。コード側の受信判定は別途試験した。

SIMで必須にしたのは ownerRef、siteId、nodeId、workId、requestId、commandId、idempotencyKey、payloadDigest、holderId、authorityEpoch、componentGeneration、expiresAt、expectedRevision。単位は模擬電力のkW。将来の汎用Observation、校正台帳、資源予約、貨物管理はこの模型の実装対象外で、別の版付き契約を追加する。

## 05 制御権・承認・復旧の仕様

{{COMMAND_DIAGRAM}}

設計上、AIは提案者であり、承認者や設備署名鍵の所有者にはしない。操作者の役割、設備範囲、手順版、有効期限、承認した内容のハッシュを確認する。重要な操作に必要な複数人確認や現地操作優先は、設備別の危険分析で決める。音声認識の成功を本人確認や操作承認の代わりにしない。

| 場面 | 必須動作 | 模型での実装 |
| --- | --- | --- |
| 操作内容の変更 | 旧承認を無効にし再確認 | 内容全体のdigestと承認を照合 |
| 二つのCoreが同時に操作 | 設備側で一つの監督制御権に限定 | holder、期限、単調に増えるepochを保存 |
| 設備再起動 | 旧世代の要求を拒否 | generation更新、旧lease失効、再観測が必要 |
| 送信したが返事なし | 結果不明を保持し設備記録へ照合 | UNCERTAIN。自動的なexecute再送なし |
| 同じ指令が再到着 | 同じ内容なら過去の結果、異なる内容なら拒否 | receiptと要求digestを同一DBに保存 |
| 送信前のCore再起動 | 保存した承認を自動で使い回さない | PREPARED/QUEUEDをCANCELLED_RESTARTへ |
| 時計の逆行・不正 | 時刻を要する新規操作を停止 | clockTrusted=falseを設備側で持続。局所計算は継続 |

設備の設定変更と結果記録は一つのトランザクションで保存する。ただし、これは模擬設定の保存に限る。実機の弁やモーターが動く瞬間とDB保存は一般に一つのトランザクションにできない。実機アダプターは操作別に状態読出し、装置側のID保持、再起動後の照合、再実行可能性を定義し、作用が不明なら人の確認へ送る。

自動切替用の台数・合意方式・独立した監視点は未選定。最初の実機試験は現地確認を伴う制御権移管を基本とし、通信分断下で旧Coreが操作できないことを実証してから自動化する。

過去のAPPLIEDは、その時点で設定が保存された履歴である。Controller再起動後も同じ過去receiptを返すが、現在の希望負荷は初期値へ戻る。現在の設定と動作は、新世代のtelemetryで別途確認する。

## 06 居住設備との境界設計

空気、水、電力、熱、廃棄物は相互に依存する設備群として扱う。NASA ECLSSの整理を参考にした区分であり、ISSの機器容量や運転条件をこのコロニーへ転用するものではない。[S1: NASA ECLSS](https://www.nasa.gov/reference/environmental-control-and-life-support-systems-eclss/)

| 設備系統 | OSが扱うもの | 局所側に残すもの・必要な設計 |
| --- | --- | --- |
| 電源・蓄電・配電 | 供給、蓄電、消費、遮断原因、予約 | 電気保護、充放電、給電切替。過渡負荷・劣化・停電継続を実測 |
| 空気・区画環境 | 圧力/成分/温湿度/換気の品質付き観測、警報 | 専用環境制御、異常時処置、区画保護。設定値と応答期限は未確定 |
| 水・廃棄物 | 使用可能量、品質、処理履歴、消耗品 | 処理、隔離、機器保護。品質未確認の水を使用可能と数えない |
| 熱 | 機器温度、熱負荷、冷却余力、故障 | ポンプ・弁・ヒーター・熱保護。Core断で全冷却を止めない |
| 構造・区画 | 状態、漏れ・衝突等の検知、点検履歴 | 構造、気密、遮蔽、独立警報。居住場所ごとに設計 |
| ロボット・保守 | 作業区域、工具・荷物・設備許可、証拠 | 衝突保護、現地停止、隔離状態。AI計画単独では始動不可 |

発電、蓄電、電力分配を分ける考え方はNASAの電源資料にも沿う。実容量には平均電力だけでなく同時ピーク、始動、変換損失、温度・劣化、故障継続、予備を入れる。[S2: NASA Power](https://www.nasa.gov/smallsat-institute/sst-soa/power-subsystems/)

資源計算は、必要量 = 人数・設備ごとの消費の時間積分 + 故障・補給遅延の予備、使用可能量 = 計測で確認された残量 - 使えない残量、とする。回収率、蓄電容量、断電継続時間、放熱面積は未入力。OS上の計算欄を埋めるために仮の生命維持設定を実運転値として配布しない。

各系統のICDには、機器ID、物理バス、コネクター、給電、単位、計測周期、品質定義、操作型、禁止条件、応答期限、起動/通信断状態、保守隔離、復旧手順、合格証拠を揃える。期限は設備の危険分析から配分し、今回のPython実行速度を採用しない。

## 07 衛星通信とavokadoの接続

外部通信は「地上網」「A-LINK」「将来の遠方拠点リンク」を差し替えられる。コロニー内部の制御LANと外部通信ゲートウェイを分け、外部接続が設備操作の権限を直接与えないようにする。監督操作の制御権は現地設備側で判定する。

| 経路 | 本計画での役割 | 未成立の事項 |
| --- | --- | --- |
| 地上LAN / 許可されたWAN | 先行開発・地上試験の通信 | 実配置、冗長給電、帯域と障害試験 |
| A-LINK低軌道衛星 | 地球周辺での自前通信網の開発 | RF設計、衛星・地上局の可視、周波数/波形、実通信、全域連続性 |
| 9704 / Iridium経路 | 別系統の端末受信実証候補 | A-LINKの代用品や互換モデムではない |
| 遠方コロニー回線 | 月面等の接触計画・遅延を伴う中継 | 別の軌道・中継配置・アンテナ・リンク予算が必要 |
| 拠点内avokado | Hubから現地Coreへ接続 | 実装アダプター、認証、切替時の表示と復旧試験 |

**「電源がつけばどこでも衛星を直接受信」は保証できない。** 屋内・地下・金属外壁・遮蔽物がある場所では、空が見えるアンテナや外部中継と拠点内回線を使う設計にする。回線がない間は保存済み情報と現地機能を提供し、未受信の新情報を受信済みと表示しない。初期衛星2機の案から、全地球の常時接続や月面通信を導かない。

遅延・断続リンクにはBPv7とBPSecを採用候補とする。到着状況は通信の証拠であり設備動作の完了ではない。期限・重複・権限・状態をアプリケーション側でも確認する。模型はBPv7/BPSecを実装していない。[S6: RFC 9171](https://www.rfc-editor.org/rfc/rfc9171.html) / [S7: RFC 9172](https://www.rfc-editor.org/rfc/rfc9172.html)

転送待ちは容量上限と優先度を持つ。候補順は警報と結果照合、要約状態、保守証拠、通常ファイル。ただし警報を外部通信へ依存させない。キュー満杯では低優先データを制限し、重要記録が保存できない状態を明示する。実際の上限・保持期間・帯域予約はミッション予算で確定する。

## 08 ロケット・貨物・建設の接続

rocketstar C3は、両段を回収・再使用する無人の小型衛星輸送案として継続する。従来の500kg級衛星2機という参照搭載量は、まだ飛行で確認されておらず、コロニーの居住区や建設資材を運べる能力の証明ではない。C3の40項目台帳と、未確定の推進・構造・熱防護・帰還・再使用試験を維持する。

{{TRANSPORT_DIAGRAM}}

ロケットの軌道投入、貨物船の移送・接近・係留、拠点での受領と設置は別の引渡し段階とする。NASAの深宇宙物流も貨物・設備・消耗品の輸送を独立した物流機能として扱う。本計画に貨物船や係留設備が既に存在するという意味ではない。[S9: NASA Deep Space Logistics](https://www.nasa.gov/gateway-deep-space-logistics/)

| 境界ID | 必須入力・出力 | 引渡し条件 |
| --- | --- | --- |
| ICD-L01 地上→打上げ | cargoId、計測質量・重心、包絡、固定点、電源、熱・振動許容、危険物/取扱い情報、版 | 実測・構造荷重・分離・環境適合を審査。OSの登録だけで搭載許可にしない |
| ICD-L02 ロケット→貨物船/衛星 | 分離状態、位置・速度の誤差、時刻、電源・通信・健全性、保持具状態 | 分離と自機機能の確認。輸送先に適した軌道条件を確認 |
| ICD-L03 貨物船→拠点 | 接近許可、独立航法、接触/係留状態、電源・データ境界、退避条件 | 専用飛行制御と拠点設備が確認。CoreやAIが姿勢制御を直接行わない |
| ICD-L04 貨物→在庫 | 封印、ID、数量、保管条件の履歴、検査結果、両者の受領証拠 | QUARANTINEDで検収し、ACCEPTED後だけ使用可能在庫へ |
| ICD-L05 機材→設備 | 台帳、設置・接続、設定版、校正、単体/統合試験、保守手順 | 設備のcommissioning完了後に運用権限を付与 |

貨物の状態は PLANNED → PACKED → LOADED → IN_TRANSIT → RECEIVED → QUARANTINED → ACCEPTED → INSTALLED。破損・欠測・照合失敗はHOLD。どの段階も現在地、担当、時刻品質、証拠を保存し、一つ先の推定状態を完了として使わない。この物流機械は本版で設計し、まだ実装していない。

有人輸送、避難船、与圧貨物、軌道組立、月面着陸はそれぞれ追加の機体・運用設計が必要。打上げ回数は、総質量を参照搭載量で割るだけでは決まらない。容積、重心、打上げ荷重、軌道移送、帰還余裕、保管寿命、建設順序、予備を含む実際の貨物一覧から求める。

## 09 avokadoらしい操作体験と外観

外観はC3で合わせたサテン調シルバー、黒い縦長の角丸面、シアンの3点と細い光の線を継承する。avokado E3は全高200mmのMotion Tower 4本と独立Edge Hubを前提にする。各Towerに大型計算機を追加する設計へ戻さない。コロニーCoreはHubと同一筐体である必要がなく、設備室の運用計算機をHubから利用できる構成にする。

操作画面の共通単位は「場所」「設備」「状態」「仕事」「結果」。設備IDと普段使う名前を対応させ、異常時には最後に確認した時刻と不確かさを見せる。文字・図形・音を併用し、色や3点の光だけで重要状態を区別しない。会話・ジェスチャーは要求の入力方法であり、承認の代用ではない。

| 状況 | 表示・操作の設計 | 誤認防止 |
| --- | --- | --- |
| 正常に観測 | 状態、採取時刻、主要資源の残量 | SIM表示は常時残す。合成値を実測値風に見せない |
| 外部通信断 | 「地球回線なし・現地運用中」、次の連絡予定 | 拠点内設備まで故障した表示にしない |
| 古い観測 | 「最終確認時点」、経過時間、更新待ち | 最後の正常値を現在の正常としない |
| 操作確認 | 対象、変更前後、影響、期限、担当 | 承認後に内容が変われば再確認 |
| 結果不明 | 「結果確認中」、設備記録の照合、担当へ引継ぎ | 成功の表示や同じ操作のワンタップ再実行を出さない |
| 重要資源不足 | 不足量、影響区画、局所設備の状態、承認済み手順 | AIの楽観的な説明で警報を打ち消さない |

画面デザイン案は今後のShell実装で具体化する。本版は画面アプリを完成・配備したものではない。設置・放熱・清掃・保守・視認性と両立する筐体にするため、外観より先に機器・アンテナ・保護の必要面積を確認する。

## 10 配備・更新・保存の運用設計

地上開発では一般計算機上のCoreと模擬設備を分離する。実機段階では、Core、設備制御器、保護系、外部ゲートウェイ、avokadoを別の権限・通信・更新範囲にする。宇宙機向けの計算機、OS/RTOS、耐環境部品、冗長台数はまだ選定しない。ブランドとしてRockstarOSを統一しても、全装置で同じカーネルを動かす必要はない。

| 設計項目 | 運用規則 | 実機移行前に必要な証拠 |
| --- | --- | --- |
| 起動 | 保護と局所制御が先、Coreは現物読出し後に監督権を取得 | 電源投入・再起動・不完全起動の実測 |
| 設定・更新 | 署名・互換性・手順版を確認、領域単位で実施 | 中断・旧版復帰・設定移行・復旧試験 |
| バックアップ | 運用記録と設定を保存、古い制御権は復活させない | ストレージ全損からの復旧、現物との照合 |
| 記録容量 | 警報/結果記録を優先し、容量不足を報告 | 満杯・破損・書込み失敗・転送滞留の試験 |
| 人員・権限 | 現地役割と担当を明確化、利用者端末から鍵を分離 | 認証・失効・交代・現地優先・侵入試験 |
| 資源予算 | CPU、メモリー、保存量、通信量、電源、熱を配分 | 実負荷で測定し、ピーク・故障時も上限内 |

設計上の保護境界は、模型の別プロセス・別SQLiteだけでは成立しない。同じOS、電源、ストレージ、ネットワークの共通故障を含めて確認する。検知時間・反応時間・継続可能時間は各設備の危険分析から値を決め、測定結果と対にする。[S5: NASA SWE-134](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695493/SWE-134%2B-%2BSafety-Critical%2BSoftware%2BDesign%2BRequirements)

## 11 動作模型と今回の試験結果

付属runtimeはPython標準ライブラリで動く独立したSIM_ONLY模型。Core/BrokerとControllerに別のSQLiteを持たせ、非重要な模擬電力負荷の設定だけを許す。機器ドライバー、無線送信、酸素・水・弁・推進装置への出力、実機モードはない。既存RockstarOSへのインストールは行っていない。

**公開fixture鍵とactor文字列は、実際の本人確認・認可ではない。** 同じPythonプロセスで鍵やControllerへアクセスできれば、Brokerを迂回できる。承認拒否の試験はBroker API上の契約試験に限る。実配備ではAI、端末、Core、署名機能、設備の権限隔離と認証を別途実装する。

模擬の初期値は供給10kW、重要負荷需要4kW、非重要負荷要求5kW。これらは計算分岐を通す試験用数値であり、コロニーやavokadoの機器定格ではない。蓄電、発電、電気回路、環境制御の物理モデルは含めない。

APPLIEDおよびBrokerのSUCCEEDEDは**模擬の希望負荷設定が保存された**という意味。実負荷の計算は次のController.stepで行い、別の観測値として確認する。重要負荷へ電力が足りない場合はCRITICAL_DEFICITを返し、正常・安全維持成功として扱わない。
