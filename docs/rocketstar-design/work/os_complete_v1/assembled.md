# RockstarOS 設計書完全版 v1.0

2026-09-24 / rocketstar・A-LINK・avokado・コロニー

## 01 この完全版の範囲と設計の読み方

**RockstarOSを、rocketstar・A-LINK・avokado・将来のコロニーに共通する運用基盤として設計する。** 人、機器、権限、状態、仕事、資源、貨物、通信、保守履歴を共通化し、機器固有の制御は機器側へ配置する。今回の完全版は、基盤OSから接続契約、保存、復旧、運用、検証、実装移行までを一つの基準書にしたもの。機械の製造図、飛行制御則、有人居住の成立証明は別の成果物として管理する。

本書の基準日は2026-09-24。ロケットの正式名称は小文字のrocketstar、OSはRockstarOS、衛星網はA-LINK、操作製品はavokadoとする。旧称RETURN-1の資料は、出典・過去の計算・試験履歴として残す。

| 表示 | 意味 | 証拠の扱い |
| --- | --- | --- |
| 本版の設計選定 | 実装担当が従う方式・責任・禁止境界 | 設計変更の対象。稼働済みという意味ではない |
| 既存実装確認 | 元repoにソースがあることを読取確認 | 対象SHAと能力範囲を記録。現機体への搭載証拠にしない |
| SIM確認 | 合成データ、模型、ホスト試験 | 物理設備・実認証・実時間保証・実飛行と分離 |
| 文書・契約検証 | Schema例、設計DDL、参照・状態・予算の整合 | OSの起動・制御性能の試験ではない |
| 搭載前に必要 | ミッション／機器に依存し未完了 | 決定者、入力、成果物、受入条件を記録する |

「完全版」は記載範囲を表す。実装完了・全ての部品選定完了・飛行許可を表さない。本書で値を決められるソフトウェア契約は具体化し、人数・軌道・機体応答・機器定格に依存する値は、その算定方法と未設定時の動作まで定義する。未設定の実機プロファイルでは運転を解放しない。

## 03 13の論理サービスと正本

次のサービス名は本版の論理設計。既存のPlatform／Engine／Brokerと結び付ける際に責任を割り当てる。論理サービス数とプロセス数は同一でなくてよい。ただし、AI・UI・署名と認可・設備通信の権限境界は維持する。

| 論理サービス | 責任・正本 | 許可経路／停止時 |
| --- | --- | --- |
| Identity & Authority | 人・機器・役割・有限権限。認証・鍵参照・失効台帳 | Platform、Brokerの検証API。不明な資格で新規操作を許さない |
| Asset Registry | 拠点・設備・構成・校正・所在。asset/profileの正本 | 版付き登録・参照API。不明な構成は操作不可 |
| Telemetry & Alarms | 観測の品質・時刻・警報。観測／警報DB | adapter入力、購読API。欠測と保存失敗を明示 |
| Work & Procedures | 提案・工程・承認・担当。仕事・手順・cargo対応 | PlatformとBrokerのAPI。activeの照合待ちを維持 |
| Command Broker | 有限指令・claim・結果照合。指令／承認／結果DB | 認可検査、adapter、receipt。新規送信停止、UNKNOWN保存 |
| Resource Scheduler | 資源の予約と競合調整。予約・優先順位・計画 | 観測・仕事・提案API。局所制御を待たせない |
| Device Adapter | 機種別有限操作の翻訳。接続世代・転送履歴 | 機器allowlistとBroker。再送せず結果を照会 |
| Link Gateway | 拠点外配送・蓄積転送。期限・宛先・spool | 外部通信と限定受信API。現地制御継続、期限検査 |
| Evidence Store | 証拠file・hash・引渡し。内容fileと受領索引 | 所有サービスの参照API。未完fileを公開しない |
| Update & Recovery | 版・配布署名・A/B・復元。release manifest・復旧記録 | 保守資格とPlatform。旧版保持または読取復旧 |
| avokado / Shell | 表示・音声・利用者操作。期限付きUI状態 | Platformだけへ提案。途中入力を承認にしない |
| Local AI Planner | 限定情報で作業案を生成。隔離された一時context | 読取と提案APIのみ。停止しても定型操作可 |
| Health & Audit | 監督サービスの状態と監査。health・監査参照 | readinessと観測API。局所保護の代用にしない |

各サービスは起動時にserviceId、version、schemaMajor、profileDigest、bootId、読み取り可能な健全性状態を公開する。依存先の存在だけでreadyにしない。必要な資格、保存領域の整合、schema互換、参照機器の状態取得を確認する。

本版のルールは、①一つの正本に一つのwriter、②書込みは所有サービスのAPIを経由、③他サービスのDBを直接開かない、④外部転送成功で設備の完了にしない、⑤同じ障害で重要制御と監視を同時に失わない構成を別途検証、の5点とする。

## 05 基盤OSと配備プロファイル

本章の「選定」は、今回の統合設計で採用する方式を意味する。既存コードの到達点、追加する実装、実機で確認する条件を分ける。2026-09-24に元リポジトリを読取確認した。HEADは `5d5f3dc4f73ac3389c8dbc00f9ca6e8beba526e0`、branchは `codex/readme-navigation`、作業木はclean。前回監査と同一SHAで、追跡ファイルの差分は0。元OSの変更・試験・GitHub最新状態の照合は行っていない。[OS-L01]

**地上の参照OSは、既存RockstarOSのLinux／Buildroot系統を継承する。** カーネルはプロセス、メモリー、デバイス、ファイルシステムを管理する。RockstarOSはその上で、利用者の仕事、Tool、権限、接続、結果、更新・復旧を管理する。独自カーネルの新規開発を前提にしない。Buildrootはツールチェーン、選択したパッケージ、カーネル、rootfsを組み合わせる仕組みであり、Buildrootという名前だけで機種互換や安全性は成立しない。[OS-W01: Buildroot公式マニュアル](https://buildroot.org/downloads/manual/manual.html)

| 配備先 | 基盤と今回の選定 | 実装・受入の境界 |
| --- | --- | --- |
| 地上の仮想参照機 | 既存ARM64 QEMU virt、Linux／Buildroot、initと専用UIDのサービス、読取専用rootfs | 既存開発資産を継承。今回のcolonyサービスを含む新imageは未作成 |

## 06 サービスと権限の配置

本版は、**操作画面、実行権限、設備への通信、AIを別プロセスにする**方式を選定する。全体サービス台帳の13項目は論理的責任の数であり、PID数と一致させる要求ではない。下表はその責任を地上参照機へ配置する候補で、具体的なprocess割当はresource budgetと隔離試験で確定する。地上Linuxでは専用UIDと私有ディレクトリーを与え、APIで情報を交換する。UIやAIから設備ファイル、署名鍵、指令DBへ直接アクセスさせない。次表のcolony用サービス名と保存先は新規実装の設計値であり、現在稼働するサービスの一覧ではない。

| プロセス／役割 | 自分が持つ状態 | 許可する経路・停止時の挙動 |
| --- | --- | --- |
| 既存Platform | component、導入版、Tool資格、本人との対応 | Shellの要求を検査してcolonyへ渡す。認証不能時は新規操作を拒否 |
| `colony-supervisord` | 作業、提案、承認、指令、送信claim、受領結果 | `dev.rock.colony.supervisor`の実装先。唯一の指令台帳writer。停止後は未送信の再承認と送信済みの照合を先行 |
| `device-adapterd` | 対象機器profile、接続世代、受信連番、転送履歴 | allowlistに載る機器・操作だけへ変換。機器認証と機器側の拒否を返し、独自の新規指令を作らない |
| `telemetryd` | 型・単位・時刻品質付き観測、警報履歴 | 観測を購読・保存。古い値にはstaleを付ける。監督画面への通知が失敗しても機器の局所警報を止めない |
| `link-gatewayd` | 外部送信待ち、宛先、期限、結果照合待ち | 拠点外通信だけを扱う。回線復帰は承認の復活条件にしない |
| Shell／Local AI | 表示状態、利用者入力、限定された計画用情報 | Platform APIへ提案する。承認発行、DB操作、任意shell、設備通信は許可しない |

ローカル制御器はこの表の監督サービスと別の故障領域に置く。監督側が止まったときに、認定済みの局所制御まで停止する構成にはしない。別プロセス化は同じホストのOS停止・電源喪失から保護しないため、重要設備の独立性は配線・電源・計算機を含む別試験で確認する。

地上実装では、AIと一般Toolに名前空間分離、最小権限、`no_new_privs`、seccompを組み合わせる。seccompはシステムコールを制限する機構であり、それ単体を完全なsandboxと呼ばない。[OS-W02: Linux seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html) 今回はcgroup v2によるCPU・メモリー・プロセス数の資源枠も設計に追加する。既存の全サービスに適用済みとはしない。特に`memory.max`到達はプロセス停止を招き得るため、AI／一般Toolの枠と運用記録サービスの枠を分け、実測した常駐量・ピーク・障害時余裕から値を決める。[OS-W03: Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

## 07 IPC・本人資格・指令の入口

既存Linux PlatformはUnix socketの相手UIDを`SO_PEERCRED`で取得し、許可UID、プロトコル版、操作名、入力容量を検査する実装を持つ。JSON内の自己申告UIDを本人資格にしない。Androidは実インストールAPKのpackage、UID、署名digest、版をBrokerが照合する。これらはプラットフォームごとの資格取得方法であり、同じ文字列だけで相互認証が成立するわけではない。[OS-L03／OS-L04]

新しい地上IPC入口を `/run/rock-colony/supervisor.sock` とし、Platformの専用UIDだけから監督操作を受ける設計にする。socketの親ディレクトリーと所有者・modeを起動時に照合する。要求はプロトコル版、操作型、requestId、workId、対象、内容digest、期待revisionを含む閉じたschemaとする。入力の大きさ、同時要求数、応答期限はprofileに定義し、未設定ならread-onlyで起動する。数値は性能測定後に確定し、既存Platformの接続上限を設備能力へ転用しない。

`ownerRef`は認証済みPlatformセッションから導く。表示名や要求本文の`actor`を信頼しない。操作者資格は、site、設備範囲、操作型、有効期限、資格世代へ結び付ける。承認は指令全体のdigest、手順版、期限、対象構成に拘束し、対象や内容が変われば再発行する。設備側はさらにgeneration、authority epoch、lease、期待revision、現在状態を確認する。信頼済み画面で承認したことと、設備が受理したことを別の記録にする。

署名は三系統に分ける。OS／Tool作者は配布物の版を署名し、操作者は承認した意図を表明し、機器はその機器が返した結果を認証する。OSの配布鍵を第三者Tool作者や設備指令に共用しない。本番鍵の保管装置、登録・失効・回復は未選定。現SIMの公開HMAC鍵や`actor='operator'`は本人認証ではなく、同一プロセスからの迂回を防がない。[OS-L04／OS-L05]

## 08 仕事・保存・結果不明の契約

既存WebのWorkは `active / review / completed / cancelled` を持ち、工程順、revision、同一command IDの内容不変を確認する。`sample=true`や失敗結果は工程を進めない。colony指令は別状態機械として保持し、既存article／coconalaのTool名を書き換えて接続しない。SIM専用templateと実設備用templateを別版で追加する。送信後に結果不明になった指令は、Workをactiveの照合待ちとし、失敗や取消へ丸めて消さない。[OS-L06]

保存の正本を次のように分ける。これらは今回の追加設計であり、既存Wallet／Web D1／Android EngineのDBを統合・移管する指示ではない。

| 保存領域 | 正本と更新者 | 永続化の境界 |
| --- | --- | --- |
| `/data/colony/supervisor` | supervisordの指令DB、作業対応、承認、監査 | 承認とqueue、送信claim、結果とeventをそれぞれ同一DBのtransactionで保存 |
| `/data/colony/telemetry` | telemetrydの観測・警報DB | 採取時刻と受信時刻、単位、品質、機器世代・連番を保持。観測を承認に変換しない |
| `/data/colony/adapters/<profile>` | adapterの接続・転送記録 | 設備が受理したかは設備receiptが根拠。送信処理終了だけで成功にしない |
| `/data/colony/evidence` | 内容hash付き成果物と受領索引 | 書込完了後に索引へ登録し、不完全fileを成果として公開しない |
| 機器内の記録 | その機器の設定・実行・結果 | Coreのbackupを戻しても、機器の現在状態を上書きする根拠にしない |

新規の局所DBはSQLite、単一writer、WALとFULL同期を基準にする。既存native内の異なるjournal設定は改変しない。WALをネットワーク共有DBとして使わず、別ホストへは版付きメッセージとreceiptを送る。SQLite公式文書でもWALは同一ホストを前提とし、複数DB全体の一括atomicityは与えない。FULL同期を選んでも、実機媒体の耐電源断や故障耐性は試験が必要である。[OS-W04: SQLite WAL](https://www.sqlite.org/wal.html)

外部作用の送信前にclaimを永続化する。claim後に落ちた場合、機器まで届いたか不明なので`unknown`を保持し、照会だけで回復する。受理済みの同一ID・同一内容には過去receiptを返し、同じIDの内容変更は拒否する。過去APPLIEDは当時の処理結果であり、現在の設定は新世代の観測で確認する。この方式は既存MCP Brokerの単一writer、接続epoch、immutable consent、送信後再送禁止に対応するが、新colony adapterとの実コード共用・統合は未実施。[OS-L05]

保存容量の予算はDB、WAL、索引、成果物、更新候補、復旧作業領域を含める。新規仕事を受ける前に必要容量を予約し、空き不足では新規実行を止める。未照合receiptや重要警報を任意削除して継続しない。保持期間、圧縮、checkpoint間隔、予約量は機器profileと記録量試験から決める。

## 09 起動・停止・更新・回復

起動は、①boot構成・image検査、②dataの所有者・schema・容量確認、③Platformと本人資格、④telemetry／adapterのread-only接続、⑤機器世代と未照合指令の回復、⑥監督権の取得、⑦新規操作の許可、の順にする。AI・外部回線は④までの成立条件にしない。保持すべきDBが消えた状態を「初回起動」と見なして自動初期化しない。世代・権限が確かめられない場合は状態閲覧と診断に限定する。

正常停止は新規仕事の受付を閉じ、未送信の指令を止め、送信済みを照合または不明として保存してからDBを閉じる。応答期限を過ぎた指令を停止直前に駆け込み送信しない。強制停止後は未送信承認を再利用せず、古いleaseが無効であることを機器側で確認する。監督機の停止要求を、生命維持の電源遮断要求へ伝播しない。

既存QEMUはstage0によるrootfs候補選択、署名検査、読取専用起動、起動healthとmark-good、失敗rollbackを持つ。ただし公開試験鍵であり、kernel／initramfsのハードウェア信頼鎖、実行中dm-verity、ハードウェアrollback counter、kernel更新を完成した実装ではない。[OS-L02] 本版はinactive rootfsの更新とdata互換検査を継承し、kernel・firmware変更を別のDevice Profile改訂として扱う。更新前には必要な旧版reader、更新中断時の扱い、戻せないschema移行の復旧を確認する。boot成功だけで機器操作を再開しない。

backupは秘密鍵を平文に含めず、設定、仕事、receipt、成果物索引、schema版、取得対象の識別を一組にする。稼働中DBの本体fileだけをコピーしない。writer停止・整合確認後に取得する方式を初期地上基準とし、無停止backupは後続設計に分ける。復元先は設備操作を無効にして起動し、旧承認を停止、古いtokenとleaseを失効させ、現物の世代・設定・未照合結果を読んでから再認定する。旧機と復元機を同時に操作可能なwriterにしない。

## 10 既存実装へ組み込む単位と受入

統合の第一単位は、SIM専用のWork→Platform→colony-supervisord→模擬adapter→receipt→Work reviewまでの一周とする。既存owner、revision、sample、取消の意味を保つadapter fixtureを先に通す。次に専用UID／socket／ファイル境界、AIからの直接呼出し拒否、機器相手の詐称、版不一致、切断・再起動・容量不足を同じimageで確認する。根拠のない自動failoverは追加しない。

主担当はNative／QEMU／ReleaseのROCK。既存OS01、V01、N01/N02、RLS01等の受入とcolony追加受入を区別する。元repoへ実装を統合する際はPlatform契約、専用Work template、`data/design-document-index.json`、全体OS設計、該当workstream、進捗を同一変更で同期する。今回作った文書を、これらのファイルへの実装反映や新OS image完成とは数えない。[OS-L07]

合格の単位は「同じsource＋同じimage＋同じprofile＋同じ実行環境」。host試験、QEMU起動、Pixel APK、Edge Hub実機、機器接続、飛行の各結果を独立に記録する。本章では新しいOS試験を実施していない。本番鍵、実機の独立電源、冗長切替、実時間応答、耐環境性、有人運用の受入は未完了のままである。

## 11 共通メッセージと互換性

付属する7種類のSchemaは、実装担当へ渡すDraft 2020-12の構造契約である。全トップレベル項目を必須とし、未知項目を不許可にする。メッセージ本文とは別に、通信相手の認証、承認、暗号学的な証明、現在の権限・装置状態を検証する。[SC-W01: JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)

| 型 | 内容・必須意味 | 主な拒否条件 |
| --- | --- | --- |
| observation | 資産／チャネル、単位、値、品質、採取と受信時刻、世代・連番・版 | 欠測なのに値を持つ、不正型、未知schema。古い観測は現在状態に使わない |
| command | 仕事／要求／指令ID、対象、内容digest、承認参照、制御権、期限、期待状態版 | 無資格、内容変更、失効、旧世代、旧版、機器禁止条件 |
| result | 元指令、装置・版、段階、理由、作用範囲、観測結果、証拠 | 別の指令の結果、身元不一致、成功の根拠欠落 |
| authority-lease | 保持者・装置、epoch、bootId、許可profile、期間、証明参照 | 古いepoch、別装置、期限・時刻不確かさ、競合保持者 |
| alarm | 設備、異常、重要度、継続／確認／解消、担当、手順と証拠 | 原因が残るのに解消、確認担当がないのに確認済み |
| cargo-manifest | 貨物・版・所在・状態、質量・包絡、取扱い、検収証拠 | 未測定で搭載済み、証拠なしで受入済み |
| release-manifest | component、成果物hash、source版、対象profile、互換条件、試験・承認参照 | 対象外機種、署名不正、互換性不足、復旧手順なし |

全型にexecutionMode、dataClass、siteId、nodeId、messageIdと時刻品質を持たせる。SIMULATION／HARDWARE_IN_LOOP／OPERATIONALは記述分類であり、値を書くだけで実機権限を得られない。添付例は全てSIMULATIONかつSYNTHETIC。digestやproofRefも構造の例で、本物の鍵・資格・実測値を含まない。

operationは本版の参照例として、模擬の非重要負荷設定と、事前に検証されたprofileIdへの切替要求を定義する。機体や生命維持設備へ任意の弁・推力・圧力を直接指定する汎用APIは定義しない。実機の有限操作はDevice Profileごとに追加・審査する。

旧C0.1のrockstaros-colony-command/1等は別契約として保持する。例えばcomponentGenerationとtargetBootId、APPLIEDとSUCCEEDEDは、名前を置換するだけでは互換にならない。C0.1のAPPLIEDを移す場合はappliedScope=SIM_SETTING、observedEffect=NOT_OBSERVEDとし、物理完了と区別する。新Schemaのproof・capability・承認参照の実装は追加が必要。

## 12 指令の状態機械と実行条件

{{COMMAND_FLOW}}

| 遷移 | 条件と保存 | 障害時の扱い |
| --- | --- | --- |
| PREPARED→APPROVED | 認証した担当、対象・内容・構成・期限に拘束された承認 | 内容や資格が変われば再承認 |
| APPROVED→DISPATCH_CLAIMED | 再検査して送信claimを永続化 | 保存できなければ送らない |
| DISPATCH_CLAIMED→ACCEPTED | 装置が世代・epoch・期限・状態・禁止条件を判定し記録 | 返事なしはUNKNOWN。送信完了を受理にしない |
| ACCEPTED→EXECUTING | 装置固有の許可条件が成立 | 実行開始前の取消可否を操作型ごとに定義 |
| EXECUTING→SUCCEEDED | 操作に必要な結果と証拠が一致 | 物理作用は相関する観測・装置記録で確認 |
| 任意の送信後状態→UNKNOWN | 応答・装置記録・作用の確認が不足 | 結果照会だけを行い、勝手にexecuteを再送しない |
| 送信前→EXPIRED/CANCELLED | 未送信であることをclaimの不存在で確認 | 送信後の取消要求で過去の作用を消したことにしない |
| 装置→REJECTED/FAILED | 拒否、または確認済みの失敗を理由付きで記録 | 未確認を失敗と断定しない |

主キーはcommandId、重複判定はidempotencyKeyと内容全体のdigestを使う。同じID・同じ内容なら過去結果を返し、同じID・違う内容を拒否する。受理済みの過去結果は、現在の設定・位置・状態の証明ではない。新bootIdの現物状態を読む。

物理作用とDB保存を一つのtransactionとして保証できない装置では、①作用前の装置側ID保持、②作用後の結果記録、③現物読出し、④再実行可否、⑤不明時の担当者確認、を操作ごとに決める。結果不明の間に同じ作用を新しいIDで再投入することも、同じ仕事・資産のロックで制限する。

新規指令の有効期限は運用profileに従う。ローカル制御の毎周期はこの人の承認フローを通さない。承認済みのmission／equipment profileが、設備側の制御周期と禁止条件を管理する。

## 13 永続化、資産、証拠の関連

データを「現在状態」「仕事の意図」「装置の受理・結果」「観測された作用」「証拠のファイル」に分ける。Coreが持つ希望状態と装置の現在状態が食い違うことを表現できるようにし、片方で上書きして一致したように見せない。

付属operations_store.sqlは指令台帳の設計用DDL。command_intent、approval_binding、dispatch_claim、command_result、audit_eventの5表を定義する。外部キーと主キー、重複キー、列の制約を持つが、本人確認、承認内容の一致、状態遷移、期限、署名、装置作用はアプリケーションが検査する。DDLだけでこれらが実装済みとはしない。command_jsonにはpayloadだけでなく指令包絡全体を保存し、承認後の不変性と索引列との一致をアプリケーションで強制する。resultは認証済み発行主体・発行bootId・messageIdで重複を排除し、同じキーの内容変更を拒否する。

| 記録の組 | 原子的に保存する範囲 | 別に確認するもの |
| --- | --- | --- |
| 指令と承認 | 同じDB内のintentと承認binding | 認証済み主体、署名、現在資格、内容digest |
| 送信claimと監査 | claimの一意登録と監査event | 装置への到着、受理、物理作用 |
| 結果と監査 | 受領した結果とその検証記録 | 結果の機器身元、対象、内容、必要な観測との一致 |
| 大きな証拠fileと索引 | 一時file→同期→名前確定→索引登録 | ハッシュが同じでも物理的に正しい証拠とは限らない |

録音・映像や個人情報を設備DBへ混在させない。設備作業の証拠に必要な部分だけを、目的・担当・保持期間付きで参照する。バックアップから復元された承認やleaseは、そのまま再利用しない。

## 14 容量・負荷・待ち行列の予算

CPU、メモリー、永続記録、転送待ち、更新候補、復旧領域を個別に予算化する。平均値だけでなくピーク、機器切断、転送滞留、ログ増加、再起動直後を対象にする。制御周期や人命設備の反応期限は、以下の地上試算から決めない。

| 予算 | 本版の地上参照値 | 確定に必要な確認 |
| --- | --- | --- |
| 観測保存 | 8機器×16ch×1Hz、7日、256byte仮定 | 実測byte、索引、WAL、証拠増加 |
| データ領域 | 100GiB、通常80%上限 | 100GiBは仮定。OS/更新/AI領域は別 |
| 転送待ち | 2GiB／20,000件、P0–P3 | 実回線と暗号込み。隔離入口64MiB別枠 |
| 結果台帳 | 4GiB、90日以上、未照合は自動削除しない | 満杯で新規監督操作を止める |
| CPU／RAM | 数値未設定、profileなしはread-only | 常駐、ピーク、故障時、応答時間 |
| 更新・復旧 | 別領域と旧版を必要量予約 | image、data移行、全損復元の実測 |

この試算は8模擬機器×16チャネル×1Hz、1件256byte、raw7日を仮定する。DB・索引・WAL等をrawの2倍、その他の記録に8GiBを配分し、100GiBのデータ領域の80%を使用可能とすると、推定使用量は約44.91GiB、予備は約35.09GiB。その他8GiBの内訳は結果台帳4GiB、転送待ち2GiB、ログ・隔離入口等2GiB。rootfs A/B、更新と復旧の作業領域、AIモデル、原映像はこの100GiBに含めず、別予算を要求する。圧縮による節約は計上しない。実際のJSONの長さ、索引、ログ、証拠fileを測定して仮定を置き換える。

データ量は1秒件数×保存時1件byte×保持秒数、メモリー待ち行列は最大件数×最大message byteで計算する。通信は送信窓、再送・暗号・ヘッダーを含む総量を、実測した有効スループットへ照合する。データ件数だけでCPUやメモリーの性能を保証しない。

予算を使い切ったときは、低優先の新規受付を止め、制御側を待たせず、欠落・間引き・保存失敗を記録する。未照合の指令や重要警報を勝手に削除しない。監査と結果の保存に必要な空きを確保できない場合、新規の外部作用を伴う仕事を受け付けない。

## 16 身元・役割・有限の実行権

機器間の地上IP経路にはTLS 1.3の相互証明書認証を選定候補とする。証明書の機器IDから登録台帳上の`siteId/deviceId/serviceId`を引き、本文の自己申告IDで上書きしない。mTLSは接続相手の身元を確かめる手段で、許される操作を決める仕組みは別に置く。状態変更APIでTLS 0-RTTを許さない。[NS-S1]

人は現地の認証サービスと信頼済み画面を使い、登録済みWebAuthn認証器の利用者検証を候補とする。認証器を使えない場合は事前登録した現地復旧手順へ移り、音声・身振り・AIの判断へ置換しない。地球のIDサービスを必須にせず、地上参照では現地の人台帳を正本にする。ログイン中でも指令承認は対象・内容・期限を表示して別に取得する。[NS-S2]

`local actor`は実UID、サービスID、実行版、起動世代に結び付けたプロセス主体である。これは人の`subjectId`と別ID。IPCはOSが渡す相手資格を検査し、JSONのactor欄で権限を得られないようにする。監査には「人・代理サービス・機器・仕事」を別々に記録する。

| 役割 | 付与する範囲 | 付与しない権限 |
|---|---|---|
| Observer | 担当区画の状態・警報・仕事の閲覧 | 個人録音閲覧、設定変更 |
| Planner / AI | 許可された要約を読み、仕事案を作る | 承認、capability発行、鍵の読出し・署名API |
| Local Operator | 指定設備・指定手順の承認、結果照会 | 権限拡張、信頼ルート変更 |
| Maintainer | 隔離・保守状態での診断と承認済み設定 | 通常運転の無条件上書き |
| Authority Service | 検証済み承認から短命な操作権を発行 | AI生成文だけによる発行 |
| Trust Custodian | 登録・失効・復旧を二者確認で管理 | その役割だけで設備操作・個人復号 |
| External Gateway | 宛先・型が許可された配送と記録 | Operatorへのなりすまし、設備制御権 |

有限capabilityは、発行者、主体鍵、宛先サービス、対象設備集合、操作型、量/回数上限、`workId`、内容digest、`notBefore/expiresAt`、`policyRevision`、一意IDを持つ。ワイルドカード操作と再委任は地上参照で禁止する。盗んだトークンだけを使えないよう主体鍵へ結び付け、所持証明と対象・操作を受信側で検査する。ACE-OAuthのPoPとaudience/scopeを参照するが、相互運用プロファイルの実装完了は主張しない。[NS-S3]

現地の人ログインは最大15分、読み取りcapabilityは最大5分。承認は内容固定・1回・最大60秒、Controllerが与える監督制御権は最大30秒、指令期限は最大10秒かつ承認・制御権の残期間以下を地上参照値とする。更新は再検査を伴い、AIやGWへ更新権を渡さない。Controllerが単調増加epochと現在holderを永続保持して旧Coreを排除する。Controller再起動・時刻不信・権限失効で新規監督操作を止めるが、局所制御と独立保護は別途継続する。長距離リンクにはこの短命指令を流さず、地球から届いた仕事提案を現地で再観測・承認して実行する。

## 17 鍵の用途分離・導入・更新

機器身元、操作権発行、結果署名、BP配送保護、保存暗号化、OTA署名の鍵と信頼ルートを分離する。TLS証明書の更新権を取得してもOTAや設備命令を署名できない構成にする。秘密値はVaultの参照として渡し、ログ・作品・診断ZIP・環境変数の一括取得・AI contextへ含めない。AIプロセスには秘密鍵ファイルと汎用署名サービスの両方へのアクセスを禁止する。

地上参照の導入は、現物確認と登録台帳の承認→端末内鍵生成→公開鍵の登録→限定証明書発行→隔離網試験→運用許可の順。TPM/HSM等による非抽出鍵は候補で、E3採用基板の実装・復旧との適合試験が完了するまで達成済みとしない。機器証明書の有効期間は24時間、残り8時間で現地CAに更新を試みる。外部回線断でも現地CAは動作できる。CA停止時は期限を延長せず、期限後は操作不可とする。長期孤立するミッションは別の有効期間・危殆化対策を承認して配布する。

現地失効リストは単調増加する版と発行時刻を持ち、操作可の端末は5分以内に同期済みであることを要する。オフライン中に未到達の失効を即時知れるとはしない。紛失・侵害が判明した鍵は現地で失効し、GWへ送るまで待たない。更新時の新旧鍵重複は最大1時間、受信側は鍵IDと用途を指定して検証する。復旧では隔離した機器の現物と台帳を二者確認し、新鍵・新世代を発行して旧承認を復活させない。

OTAは別の検証器と信頼ストアを持ち、署名された機種・対象部品・版・digest・前提条件・ロールバック方針を検査する。ネットワーク接続成功を更新承認にせず、運用中設備の保守窓と現地条件を再確認する。OTA署名鍵はオフラインまたは専用署名装置に置き、オンライン運用CAから発行できない。信頼ルート分離はSUITの更新アーキテクチャを参照した本計画の選択である。[NS-S4]

## 18 API・時刻・結果照合

地上参照APIは`/v1`の型付き要求とし、SIM `/1`スキーマを本番名へ置換するだけの移行はしない。新しい`rockstaros.icd.{observation,command,result,authority-lease,alarm,cargo-manifest,release-manifest}.v1`の7型は設計案で、C0.1 runtimeへ未接続。例は全て`SIMULATION/SYNTHETIC`とし、本物の資格情報を同梱しない。

包絡では版、executionMode、拠点、`actorRef`、`issuingDeviceRef`、起動世代、要求/仕事/メッセージID、内容digest、発行/失効時刻、時刻品質を対応する型に結び付ける。commandは`capabilityRef`と`authorizationReceiptRef`、対象、制御権epoch、機器世代、期待状態版を持ち、送信機器をleaseの`holderDeviceRef`と照合する。operationは模擬の`reference.noncritical_load.set`、または設備別に事前検証した`profileId/profileDigest`を要求する`equipment.profile.request`へ限定し、任意の弁・レジスター命令を持たせない。署名はpayloadだけでなくactor/device・宛先・権限参照・epoch・期限・期待版を含む完全な命令包絡を保護し、参照する承認/能力の内容digestも固定する。`envelopeProofRef`等は既知の保管庫内の不変記録を引き、任意URLを自動取得しない。各JSONプロパティの綴り・必須性は同梱ICDを正本とする。送信者IDは認証情報と一致させ、未知の主要版、重複JSONキー、NaN、過大/過深データ、未知の操作を入口で拒否する。

| API契約案 | 呼出主体 | 成功の意味・禁止事項 |
|---|---|---|
| `GET /v1/assets/{id}/state` | 許可された人・サービス | 観測値、品質、採取/受信時刻、世代と版。鮮度不明を最新としない |
| `POST /v1/work-proposals` | Planner、外部GW | 提案の永続受付。設備実行や承認ではない |
| `POST /v1/approvals` | 再検証した人セッション | 画面で確認したdigestに固定した1回承認 |
| `POST /v1/commands` | 許可された現地Brokerのみ | 永続受付receipt。物理完了ではない |
| `GET /v1/commands/{id}/receipt` | その仕事に権限がある主体 | 受理・拒否・実行中・結果不明・証拠参照を返す |
| `POST /v1/commands/{id}/reconcile` | 現地Broker | 状態読出し・装置側履歴との照合だけを要求。execute再送は禁止 |
| `POST /v1/transfers` | 許可されたAsset Service | 宛先・分類・期限・容量を検査して配送待ちへ。相手受領ではない |

接続再送を含め、一意IDとdigestの組を保存する。同じID/内容なら既存receipt、同じID/別内容なら`ID_CONFLICT`。新ICDのresultは`status`に加え`appliedScope`と`observedEffect`を使う。`SUCCEEDED/CONFIGURATION/NOT_OBSERVED`は設定保存だけ、`SUCCEEDED/PHYSICAL_ACTION/MATCHED`には実機作用と観測一致の証拠を要求する。C0.1の`APPLIED`を物理完了へ読み替えない。送信後の返事消失は新v1の指令状態`UNKNOWN`、既存WebのWorkは`active`の照合待ちとする。旧C0.1指令の`UNCERTAIN`とはこの対応関係で区別する。装置receipt未取得時の照合APIは、Broker自身の照会状態`UNKNOWN`と理由`RECEIPT_UNKNOWN`、deviceResult=nullを返す。これは機器発行のresult ICDとは別のAPI応答であり、deviceProofRefや機器状態を補作しない。失敗や未実行と断定しない。設定保存とreceiptは同一トランザクションにする。実物への作用は一般にDBと不可分にできないため、装置側ID・観測・現地確認で照合し、自動execute再送をしない。

時刻は採取時刻と受信時刻、現地単調時刻、起動世代、推定誤差、同期元、最終確認を分ける。新ICDの時刻オブジェクトでは`utcMs/monotonicMs/bootId/quality/uncertaintyMs`を用いる。観測の順序は世代＋連番＋状態版で決め、結果は認証済みnodeId・issuedAt.bootId・messageIdで重複排除し、状態版と遷移で照合する。地球受信時刻で現地順序を上書きしない。地上時刻同期はNTS候補だが、認証された時計が正確であることまで自動保証しない。[NS-S5]

地上参照では時刻誤差上限2秒以内、認証済み確認から24時間以内、逆行・世代矛盾なしを新規監督操作の条件とする。判定時は「現在推定＋誤差」が期限未満、「現在推定−誤差」がnotBefore以上であることを要求し、保守的に期限を短縮する。起動時に信頼時刻を得られなければ隔離/閲覧限定とし、証明書の日付検証を無効にしない。既知の時刻ルート・保護RTC・現地保守による復旧は専用経路で設計する。時刻品質回復後も旧leaseや承認は再利用しない。

## 19 断続配送・容量制限・個人データ

断続リンクはBPv7＋BPSecを候補に選ぶ。地上試験の収束層と接触計画は別の版付き設定とし、衛星が自動で保存中継するとは仮定しない。RFC 9171に加え管理レコードとipn表記の更新RFC 9713/9758を追跡する。配送到着・BP状態報告はアプリ受理・設備実行を証明しない。[NS-S6]

BPSecのBIB/BCBで必要なブロックを保護し、既定のHMAC-SHA2/AES-GCM文脈は相互運用試験候補とする。共有MACは保有者全員が作成できるため、人の承認や個別機器の否認防止の証拠にしない。BPSec自身は鍵配布方式を確定しない。アプリ包絡の承認・結果は別の非対称署名をCOSE_Sign1候補で保持し、GWが復号・検証する区間でも現地の操作権を作り直せないようにする。アルゴリズム集合は採用HSMとライブラリーの試験後に版固定する。[NS-S7][NS-S8]

**以下の容量・期間は非有人の地上試験用ポリシーであり、RF速度・衛星能力・生命維持要件ではない。** 送信待ちは最大2GiBかつ20,000件、メタデータと暗号化分も計量する。予約内訳は結果/警報要約256MiB、状態要約256MiB、保守証拠512MiB、通常ファイル1GiB。未検証の外部受信は別の64MiB/1,000件隔離枠へ置き、検証前に保護枠を消費させない。小データの本文は4KiB、地上ファイルは256KiB以下のチャンクを候補とし、実リンクの制限がさらに小さければ従う。

| 配送クラス | 保持・優先度 | 混雑時の決定 |
|---|---|---|
| P0 結果照合・警報要約 | 配送待ち30日、送信配分50% | 操作前に結果保存枠を予約。保存できなければ新規監督操作を受け付けない |
| P1 状態要約 | 24時間、20% | 同じチャネルの未送信要約を集約し、欠測範囲を残す |
| P2 保守証拠 | 7日、20% | 上限で新規配送受付を停止。元証拠は別の記録領域に残す |
| P3 通常ファイル | 7日、10% | 上限・料金・接触窓不足で保留。無承認の別回線へ送らない |

配分は帯域保証ではなく、使える回線内の地上スケジューラーの比率で、未使用枠は貸す。送信者がP0を自己指定できないようデータ型と役割から分類する。小データだけの回線ではP2/P3の大容量転送を開始しない。キュー80%で新規通常ファイル受付を抑え、90%でP2を抑える。各予約枠の満杯で`QUOTA_EXCEEDED`、一時混雑で`BUSY/retryAfter`を返し、上流も生成を減らす。壊れた宛先への無限再試行や受信反射を防ぐため、送信元別件数・バイト・同時処理枠を設ける。監督要求は期限切れで実行せず、記録と期限切れ理由だけ保持する。局所の保護・警報をこの外部キューに依存させない。

配送期限が切れても不明な作用を「未実行」に変えない。照合台帳とreceiptは別の4GiB枠で90日以上保持する地上方針とし、未解決項目は期限による自動削除を禁止する。枠が逼迫したら監督操作を停止し、承認された書出し/保管で容量を回復する。これにより輸送キューの30日と未解決仕事の保全を分ける。

接続状態と操作許可状態を別に表示する。操作許可は`QUARANTINED`（登録/検証のみ）、`READ_ONLY`（認証済み閲覧）、`OPERATE_LOCAL`（現地権限・時刻・保存正常）、`RECONCILE_ONLY`（結果不明の対象は照合のみ）、`MAINTENANCE`（隔離確認付き作業）の5モードとする。通信断だけなら現地権限が有効な範囲で現地運用を続ける。権限・時刻・保存条件を失えば該当対象を降格し、インターネット再接続だけでは昇格させない。「端末保存」「相手受領」「設備確認済み」、最終観測時刻と品質を別表示する。

個人の原音・画像は設備テレメトリーと別owner領域・別鍵に置く。E3に従い起動時の入力はOFF、音声はPTT、原音は既定で保存も外部送信もしない。MIC OFF/利用者交代で取得、残留バッファ、処理ticketを失効する。記録・外部処理を使う場合は目的、対象、送信先、期限、費用を承認に固定し、AIや診断が後から用途を広げられない。[NS-L2]

設備用APIに渡すのは承認済みの型付き意図や最小限の品質情報とし、音声/顔/身体映像を通常の観測添付にしない。保守録画も設備管理者であるだけでは閲覧可能にせず、映り込む人のデータを含む別分類として審査する。監査には原音や秘密の代わりに承認ID・対象ID・digest・結果を記録する。プライバシー削除と監督操作の監査保持を別台帳で管理する。

受入では、偽actor/別機器証明書、盗用capability、旧epoch、期限と時刻誤差、CA/回線断、GW侵害、満杯/再起動、receipt消失、OTA鍵の誤用途、AIからの署名要求、MIC OFF後の残留/送信を注入する。実装と対象機器でこれらを試験するまで、本章の認証・分離・可用性を達成済みとしない。

## 20 機上基盤の評価構成を選ぶ

第一評価候補を **cFS＋RTEMS** とする。cFSは共通サービスとアプリ群を組み合わせる飛行ソフトウェアの枠組み、RTEMSはその下でタスク・割込み・機器入出力を扱うリアルタイムOSである。RockstarOSは操作者、資産、仕事、権限、履歴、通信を統合し、機上ソフトと契約を共有する。名称の統一を、一つのOSイメージやCPUで全機能を動かすことに置き換えない。

| 評価構成 | 選ぶ理由・用途 | 代替へ移る条件／搭載選定までの残条件 |

| EVAL-F01: cFS＋RTEMS | cFEの実行・時刻・イベント・テーブル・メッセージ等の共通サービスを使い、ミッション固有appと機器依存部を分けて評価する | 実CPU、RTEMS BSP、cFSのOSAL/PSP、コンパイラー、各版の互換性、時間・メモリ・入出力・耐環境を確認する |

## 22 周期・CPU・メモリの予算を閉じる方法

地上評価の最初の解析モデルは、単一CPUの固定優先度タスクとする。これは比較を始める条件であり、実機のCPU数を決めるものではない。cFS側の周期トリガーとRTEMS側のCPU割当てを別々に記録する。周期を発行できることと、処理が締切までに終わることを別に検証する。

| 予算項目 | 入力と算定 | 合格証拠 |
| --- | --- | --- |
| タスク時間 | 各taskの周期T、締切D、最悪実行時間C、起動ジッターJ、共有資源の阻害B、割込み負荷を列挙 | 代表・異常入力での実測と経路解析。観測最大値だけを最悪値の証明にしない |
| 応答時間 | 全taskのC/T合計を一次点検し、優先taskの干渉、B、割込み、キャッシュ・DMAの影響を加えて各締切へ照合 | 選んだスケジューラー条件に適合する解析と、対象CPUでの締切検査。CPU使用率だけで合格にしない |
| 制御の周期 | 機体・センサー・操作系モデルから許される遅延とジッターを決め、取得→計算→出力の全経路へ配分 | RDR-022等のモデル評価とHIL。根拠のないHz値や制御ゲインを仮決定しない |
| メモリ | 静的領域＋taskごとのstack＋メッセージ長×queue上限＋ドライバーbuffer＋保存管理＋予備を集計 | 対象ビルドmap、stack最深値、queue飽和、長時間・異常時の増加検査 |
| 通信・保存 | 最大発生量、転送可能時間、保存期間、優先度、故障時の保持量を計算 | 制御と共有するCPU・バス・記憶装置の競合試験。溢れた情報と原因を記録 |

RTEMSのRate Monotonic Managerは周期の実行時間や取りこぼしを観測できるが、資料自体も統計を要求に照らして分析する必要性を示している。評価では取りこぼし、遅延、queue深さ、stack、実行モードを同時に記録する。高速経路に無制限の待ち、保存処理、外部通信、動的資源確保を置かない設計を原則とし、例外は上限と根拠を示す。[FE-S5](https://docs.rtems.org/docs/6.1/c-user/rate-monotonic/background.html) [FE-S7](https://docs.rtems.org/docs/6.1/c-user/scheduling-concepts/uniprocessor-schedulers.html)

## 23 起動・モード・故障・更新

| 場面 | 本版で固定する設計要求 | 次段階の確認 |
| --- | --- | --- |
| 起動 | イメージ・設定・機体ID・機器整合を確認し、観測と保護を開始。過去の外部要求を再生して出力を作らない | bootloader、鍵、ストレージ故障、出力初期値、起動時間 |
| モード | BOOT_VERIFY、STANDBY、LOCAL_MISSION、DEGRADED、MAINTENANCEを管理用の骨格にする。実飛行フェーズは別のミッション状態表へ展開 | 各遷移の入力、禁止条件、出力、時間制約、復帰可否。飛行中の再起動を地上待機と同一扱いにしない |
| 時刻喪失 | 制御の経過時間には検証した現地時計を用い、外部時刻との対応と不確かさを別管理。同期喪失時は時刻依存の新規要求を制限 | 時計の飛び、逆行、再起動、長時間不通、採取時刻と受信時刻の区別 |

| 外部通信断 | 機上の承認済み運用と故障処置を継続し、記録を保持。通信を待って閉ループ制御を停止しない | 通信断とCPU・電源・センサー故障を分けて試験 |
| 更新 | 署名、適用機体、依存版、設定互換性を検査。転送、検査、保存、切替、正常確認を分離し、状態不明で自動切替しない | 中断・破損・rollback、保存の原子性、機器状態との整合。飛行中の更新可能性は別途評価 |

NASA HSはapp・イベント監視やwatchdogへの通知等を提供するため、監視機能の評価部品とする。ただしHS自身を同じCPUに載せただけでは独立保護にならない。watchdogをどの故障から隔離するか、どのモードで何を復旧するかは、機体全体の危険・故障分析で決める。具体的な処置を「全電源断」「全task再起動」に共通化しない。[FE-S8](https://github.com/nasa/HS) [FE-S10](https://standards.nasa.gov/sites/default/files/standards/NASA/B/0/NASA-STD-87398RevB.pdf)

## 24 コロニー重要設備とRockstarOSの境界

重要設備は独立保護と専用制御器を持ち、RockstarOSは状態、作業、構成、履歴を統合する。Coreが二台あること、同一PC上で別プロセスに分けたことを、電源・配線・センサーまで分離された証拠にしない。C0.1の模擬非重要負荷試験を、空気・水・熱・給電設備の運転実証へ数えない。

| 境界 | Coreから許す内容 | 設備側に残す決定・必要入力 |
| --- | --- | --- |
| 電力 | 予算要求、計画、認可済み非重要負荷の設定要求 | 保護、重要負荷優先、現地状態からの拒否。定格、過渡、蓄電量、継続時間は機器設計入力 |
| 空気・水・熱 | 状態照会、点検、版固定された運転プロファイルの要求 | 物理機器の制御と保護。圧力・空気成分・温度・水質等の限界は有人／設備要求から決定し、AIに生成させない |
| 権限 | 役割・要求ID・期限・対象構成を束ねた操作意図 | 現地が制御権epoch、前提状態、禁止条件を再検査。通信断時の権限と復旧を明文化 |
| 保守 | 作業指示、部品・校正・手順版、証拠の記録 | 現地隔離、作業可否、復帰許可。履歴欠損時は自動で運転可能へ戻さない |
| 警報 | 状態集約、作業起票、遠隔通知 | Core、AI、WANから独立した必要警報と現地操作。実配線・給電・共通故障試験で確認 |

NASA SWE-134の既知状態への初期化、命令順序・前提条件検査、異常時応答を設計要求へ反映する。各設備の状態と応答期限は物理モデルから与える入力であり、本版に未設定の値があるまま実機運用へ解放しない。[FE-S11](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695493/SWE-134%2B-%2BSafety-Critical%2BSoftware%2BDesign%2BRequirements)

機上評価を次へ進める成果物は、固定構成表、値入りメッセージ／機器ICD、モード表、時間・資源予算、ビルド再現記録、異常系試験、対象CPUでのHIL、環境試験と独立レビューである。これらをrocketstar、A-LINK、コロニーの別々の機体・設備構成に対して追跡する。

## 25 全体の運転モードと権限移管

CoreのモードをBOOT_VERIFY、READ_ONLY、RECONCILING、READY、DEGRADED、MAINTENANCE、RECOVERYに分ける。設備の正常／異常、外部回線の接続、UIの状態とは別に表示する。CoreがREADYでも、個別設備が運転可能とは限らない。

| モード | 入る条件 | 許される仕事 |
| --- | --- | --- |
| BOOT_VERIFY | 起動直後、image・設定・保存領域を確認中 | 診断、局所制御器の保護を妨げない読出し |
| READ_ONLY | 資格・時刻・構成・権限が未確認 | 状態読出し、原因説明、現地の復旧手順 |
| RECONCILING | 保存済み仕事と装置状態の照合中 | 結果照会。古い送信要求の再実行なし |
| READY | 必要依存・保存予算・資格・状態が成立 | 許可された範囲の新規仕事 |
| DEGRADED | 一部設備・通信・容量等に問題 | 影響範囲を限定。無関係の局所制御は継続 |
| MAINTENANCE | 現地で隔離と保守条件を確認 | 版固定の保守・更新。制御権と工程を記録 |
| RECOVERY | 全損復旧や不整合から戻す途中 | 再認定前は外部作用を許さない |

監督権は設備ごとの一人のwriterに限定する。初期の移管は、現地確認→旧holderの隔離／lease失効→機器側epochの更新→新holderの現物読出し→未照合結果の処置→新規受付再開、の順にする。旧側の復活や通信分断で二重のwriterが生じないことを試す。自動切替や合意アルゴリズムを実装済みとはしない。

飛行中の機体は、地上のREAD_ONLYやCore再起動とは別の機上モードを持つ。外部権限を失ったために飛行中の制御を全停止する設計にはしない。継続・縮退・帰還等の具体処置は機体のmission profileと故障解析で決める。

## 26 avokadoとAIの操作設計

avokado E3は4本のMotion Towerと別Edge Hubを使う。Towerは入力・センシング、Hubは入力統合、利用者の資格、画面・音声、通信と保存の入口を担当する。コロニーの重要設備用センサーや独立保護器の代用にしない。

基本画面は「拠点→区画→設備→仕事→結果」。状態には採取時刻・品質・実測／推定／合成の分類を付ける。希望値と観測値、受理と完了、確認済み警報と原因解消を分ける。外部回線がなくても、現地で得られる状態と承認済みの手順を使える構成にする。

| 操作場面 | 表示と処理 | 失敗時 |
| --- | --- | --- |
| 状態を見る | 最新値、取得時刻、品質、影響する仕事 | 欠測は欠測。最後の正常値で現在の正常を装わない |
| AIへ相談 | 許可された状態から、理由と手順版付きの提案 | AI停止でも定型画面・現地操作を残す |
| 変更を確認 | 対象、変更前後、影響、期限、資格を表示 | 条件が変われば承認を取り直す |
| 結果を見る | 送信／受理／実行／観測を区別 | UNKNOWNは確認中として担当へ引継ぐ |
| 警報を確認 | 原因、影響区画、承認済み手順、担当 | 「確認した」で警報原因を消さない |

AIが参照する観測、文書、ツール結果は非信頼入力として扱う。文書内の指示で権限を増やさず、認証情報や機器鍵をモデルへ渡さない。AIは許された有限操作の提案を作り、独立した検査が仕事へ変換する。自由文をそのままshellや装置へ渡さない。

銀色、黒い縦長角丸面、シアンの3点はブランド上の共通意匠。警報や重要状態は色・光だけに頼らず、文字、形、必要な音で判別できるようにする。本版で操作画面アプリを実装したという意味ではない。

## 27 貨物・設備・再使用のライフサイクル

rocketstarの輸送とコロニーの設備管理を、cargoId、assetId、workId、configurationDigest、evidenceRefsでつなぐ。貨物が到着予定であることを、現地の使用可能在庫として数えない。rocketstar C3の参照搭載量から、コロニーの建設能力や有人輸送能力を導かない。

貨物はPLANNED→PACKED→LOADED→IN_TRANSIT→RECEIVED→QUARANTINED→ACCEPTED→INSTALLED。実測・封印・温度等の取扱い履歴・検査が不足するとHOLDへ置く。INSTALLEDへ進むには、接続・構成・校正・単体試験・統合試験と設備台帳への登録が必要。これらは設計した状態で、物流runtimeは未実装。

| 引渡し | OSが関連付ける証拠 | 物理側で必要な成果物 |
| --- | --- | --- |
| 地上→rocketstar | cargoId、実測質量・包絡、構成版、搭載仕事 | 荷重・固定・熱・電源・分離の値入りICD |
| 機体→衛星／貨物船 | 分離状態、時刻品質、ソフト版、健全性 | 軌道・誤差・分離・自己機能の確認 |
| 貨物船→拠点 | 接近許可と係留結果、受渡し双方の記録 | 独立航法・係留・退避・接続適合 |
| 貨物→設備 | 検収、所在、校正、設定、commissioningの仕事 | 設置と機器の受入、運転許可 |
| 帰還機体→再飛行 | 個体番号、負荷・熱履歴、交換・点検、判定 | 寿命・損傷・修理・試験の実証 |

機体の生涯記録は飛行回数だけでなく、構造・推進・熱防護・脚・電池等の交換と負荷履歴を追う。OSは証拠と判定を管理するが、検査の合否値や寿命をAIの推測で決めない。

## 28 異常時の運用と復旧表

| 故障・異常 | 最初の処置 | 再開に必要な確認 |
| --- | --- | --- |
| 地球／衛星回線断 | 現地制御を継続、期限付き転送を保管 | 宛先・期限・資格・現在状態を再確認 |
| Core停止 | 機器の局所制御・必要警報を継続 | 新boot、記録整合、結果照合、権限再取得 |
| AI／画面停止 | 定型操作と現地経路へ | 入力途中を承認済みにしない |
| 装置再起動 | 旧generationの新規命令を拒否 | 設定と観測・時刻品質を取り直す |
| 時計の逆行／不確かさ拡大 | 時刻依存の新規操作を制限 | 現地時計とUTC対応を再認定、旧承認再利用不可 |
| 送信後に返事なし | UNKNOWN、対象仕事を照合待ち | 装置記録・現物を確認。新IDでの再作用も制限 |
| 資源不足 | 現地優先順位を適用、不足を明示 | 実資源と影響を確認。重要負荷不足を正常にしない |
| DB／WAL／証拠破損 | 新規外部作用を停止、閲覧・診断 | 整合した復元、装置の現物との照合 |
| 旧Coreが復活 | 旧epochの操作を装置側で拒否 | 保持者の一意性、古い鍵・leaseの処理 |
| 更新中断 | 旧版保持または回復モード | image・data互換・機器世代・未照合結果 |
| 共通電源／バス故障 | 機器別の独立保護と局所手順 | 代替経路を含む実配線・電源の確認 |

全系統に共通の「安全＝全て停止」は定義しない。異常時の許される状態、検知期限、応答期限、復旧回数、不可逆操作、現地作業が必要な条件を機器ごとに定める。自己回復を無制限に繰り返さず、失敗回数と影響を記録して縮退へ移る。

## 29 検証計画と今回の証拠

本版で **43/43項目合格**。jsonschema 4.26.0による新7型と旧3型の構造例、選択した拒否条件、SQLite設計DDLの5表・一意キー・外部キーを検査した。7つのschema自体もDraft 2020-12のメタschemaで確認した。これは暗号・OS起動・実行性能の試験ではない。個別結果と対象hashはevidence/contract_checks.jsonに収録する。

旧C0.1の35件合格は、その時点のソースとホストでのソフト模型試験として保存する。本版の新契約・認証設計・機上候補・基盤サービスがその35件で確認済みになったわけではない。本版は新OS image、RTEMS/cFSビルド、実機通信、GNC、有人設備の試験を実施していない。

## 30 実装への移行とリリース条件

実装は既存OSを丸ごと作り替えず、専用componentと仕事テンプレートから始める。最初の縦の接続は、avokado／Shellの模擬要求→既存Platform資格→新Broker→模擬設備→結果照合→Work reviewとする。各工程のID、版、証拠を保持し、元のsampleを工程合格にしない規則を保つ。

| 作業単位 | 作るもの | 完了条件 |
| --- | --- | --- |
| W1 構成固定 | Device Profile、source/依存版、service権限・IPC表 | 再現buildとboot、旧基盤との互換性 |
| W2 共通契約 | 7型ICDのvalidator、canonical化、proof/capability参照解決 | 構造と意味・権限・期限を独立に拒否試験 |
| W3 Work接続 | SIM template、指令状態とWork状態のadapter | UNKNOWN中active、模擬結果で実工程を完了しない |
| W4 保存・復旧 | 私有DB、claim、receipt、証拠、backup/restore | 破損・容量・中断・二重writer・全損回復 |
| W5 機器・通信 | 1機種の値入りICD、署名/認証、有限操作 | 身元・型・現在状態・禁止条件を受信側で検証 |
| W6 配備受入 | image＋profile＋構成＋試験結果のrelease manifest | 同じ構成で受入、rollbackと操作再認定 |
| W7 機上評価 | cFS/RTEMS構成、message辞書、task予算、driver | 対象CPU/BSPでのbuild、時間・故障・HIL |

リリースの判定は「bootした」だけではない。対象機器とprofile一致、データ互換、試験構成との一致、未照合仕事、復旧手順、担当による承認を確認する。物理設備の試験不足を、過去のQEMUやPixelの結果で代替しない。

## 31 機体・機器ごとに値を確定する項目

| 入力 | 決める担当領域 | 必要な成果物・未設定時の扱い |
