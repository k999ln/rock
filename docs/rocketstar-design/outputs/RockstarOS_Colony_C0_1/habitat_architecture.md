# RockstarOS Colony — 設備・運用の接続設計入力 C0

作成日: 2026-09-23。適用範囲: rocketstar、A-LINK、avokado、将来コロニーを結ぶ統合設計への入力。状態: アーキテクチャ選定案／検証前。地上・軌道・月面の配置先は未決定。最初の適用先は、有人居住を行わない地上の設備試験環境とする。以下の「shall」に相当する表現はこの計画への提案要求であり、実装済み・NASA適合・有人使用可能を意味しない。

同時に作成する参照実装の識別子は `dev.rock.colony.supervisor`、実行範囲は `SIM_ONLY` とする。コマンドのスキーマ名は `rockstaros-colony-command/1`、テレメトリーは `rockstaros-colony-telemetry/1`。Coreとcontrollerは別々のSQLite記録を持ち、controllerが世代・制御権epoch・期限・期待状態版・重複・試験用MAC・局所状態を受信時に判定する。操作対象は模擬の非重要負荷のみで、重要設備を任意操作するAPIは設けない。電力供給が重要負荷に不足する場合は不足を明示し、安全維持の成功として扱わない。この実装は本番の物理隔離、鍵管理、認証、フェイルオーバーを完成させるものではない。本書の全接続契約を実装したとは扱わず、参照実装に含まれる項目はその実装仕様と試験記録で照合する。

## 1. 今回選ぶ構造

RockstarOSを、設備・人・貨物・通信・保守履歴をまとめる現地運用の核にする。空気、水、電力、熱の機器制御は設備ごとの専用制御器が受け持つ。独立した保護機能と現地操作経路は、RockstarOS Core、avokado、AI、外部通信が停止しても働く構成にする。

NASAのECLSS説明は、圧力、換気、火災検知、水、廃棄物、酸素供給、空気再生を一体の設備群として扱う。本計画も「酸素センサー一つ」をコロニー管理の代用にせず、設備群ごとの監視・制御・故障処置を設計する。[S1: NASA ECLSS](https://www.nasa.gov/reference/environmental-control-and-life-support-systems-eclss/)

| 領域 | 責任・配置 | RockstarOSとの境界 |
| --- | --- | --- |
| H0 独立保護 | 機器側の保護回路、独立警報、必要な現地操作経路 | Coreから保護解除や限界値の任意上書きをできなくする。共通電源、通信、センサーが独立性を壊さないことを検証する |
| H1 設備制御 | 電源分配、環境調整、水処理、熱制御それぞれの専用制御器 | 認可された運転意図を受け、実行可否を現地で判定。閉ループ制御と故障時処置は現地で継続する |
| H2 現地運用核 | RockstarOS Core。設備台帳、状態、権限、作業、資源配分、監査、保守を保持 | 許可された意図だけを設備アダプターへ渡す。設備の最終制御権を奪わない |
| H3 操作・支援 | avokado、作業画面、会話AI、遠隔運用画面 | 状態と根拠を表示し、操作要求をCoreへ渡す。AI出力を機器コマンドとして直接送らない |
| H4 外部連絡 | A-LINK、地上網、将来の深宇宙通信、転送ゲートウェイ | 通信断でもH0–H2が働く。遅れて届く要求は、その時点の状態・権限・期限を再検査する |

NASAのソフトウェア安全資料は、同じソフトウェアを載せた冗長計算機の共通原因故障と、保護・冗長性の独立性を壊す経路を検討対象にしている。このためCoreを二台に増やすだけでは設備保護の独立性を満たしたことにしない。[S4: NASA-STD-8739.8B Appendix A](https://standards.nasa.gov/sites/default/files/standards/NASA/B/0/NASA-STD-87398RevB.pdf)

## 2. 必要な設備領域

| 設備領域 | Coreが保持する状態・記録 | 専用制御器・保護側に残す仕事 |
| --- | --- | --- |
| 電力 | 発電・受電状態、蓄電状態、消費、給電区画、予測、遮断原因、保守状態 | 機器に適合した電気保護、充放電制御、許可済みの負荷優先順位、切替実行 |
| 居住環境 | 計測時刻と品質付きの圧力、温湿度、空気成分、換気、煙・漏れ検知状態 | 認定された設備プロファイルに基づく環境維持、異常検知、局所警報、区画ごとの処置 |
| 水・廃棄物 | タンク・配管系統の状態、水の検査結果と来歴、処理系統、使用可能量 | 水質条件を満たさない流れの隔離、機器保護、処理系統の運転・停止 |
| 熱 | 機器温度、系統状態、熱負荷推定、冷却能力と故障 | ポンプ・弁・ヒーター等の局所制御、機器保護。Core停止を一律の全停止へ結び付けない |
| 保守・物流 | 部品ID、交換履歴、校正、在庫、消耗量、作業手順版、実行者、点検証拠 | 現地で定義された隔離と作業許可条件の保持 |
| ロボット | 作業領域、作業予約、荷物・工具台帳、完了証拠 | 接触・衝突等の機体側保護と動作停止。設備へ作用する作業は設備側の許可も必要 |

NASAの電源資料は発電・蓄電・分配を別の設計要素として整理し、分配・保護・機器監視をPMADの役割としている。この整理を境界設計に使うが、小型衛星用の電圧、機器、容量を居住施設へ転用しない。[S2: NASA Power](https://www.nasa.gov/smallsat-institute/sst-soa/power-subsystems/)

NASA ISAACは、無人期間の設備監視と保守、設備テレメトリーとロボット点検、在庫・貨物作業の統合を研究・実証している。これを、コロニーの核に「会話画面」だけでなく設備状態、点検証拠、在庫と作業管理を持たせる根拠にする。[S3: NASA ISAAC](https://www.nasa.gov/integrated-system-for-autonomous-and-adaptive-caretaking-isaac/)

## 3. 設備との接続契約

各アダプターは、自由記述の命令文を機器へ転送しない。機器ごとに版管理された型付き操作と読み取り項目を登録する。既存機器の通信方式はアダプターで変換し、Core上で同一の意味を扱う。物理バス、コネクター、配線、終端、通信周期は機器選定後にICDへ追記する。

| メッセージ | 必須要素 | 受信側の処置 |
| --- | --- | --- |
| 観測 Observation | 設備・チャネルID、起動ID、連番、採取時刻、受信時刻、単位、値、品質、時刻不確かさ、校正版、プロファイル版 | 古い値や不正な値を正常値として使用しない。欠測・推定・実測を区別する |
| 運転意図 Intent | 要求ID、対象、操作スキーマ版、発行者と役割、制御権epoch、順序番号、有効期間、期待する状態版、パラメーター、承認根拠 | 同一要求の重複、期限、権限、状態版、機器側禁止条件を検査し、拒否理由を返す |
| 実行結果 Result | 元要求ID、REJECTED / ACCEPTED / EXECUTING / SUCCEEDED / FAILED / UNKNOWN、設備状態版、根拠付き時刻、理由コード | ACCEPTEDを動作完了として表示しない。UNKNOWNのまま同じ動作を繰り返さない |
| 健全性 Health | コントローラー起動ID、ファームウェア・設定版、異常、制御モード、センサー品質、保護状態 | Core接続断と設備故障を分離して扱う |
| 作業証拠 Evidence | 資産ID、作業ID、手順版、観測・写真等への参照、ハッシュ、実行者、終了結果 | 設備の運転許可に用いた証拠を追跡できるようにする |

単一の設備に対して有効な監督制御権は常に一つに限定する。Coreの二重化方式にかかわらず、機器側が古いepochと失効済みの制御権を拒否する。分断時に双方のCoreが更新要求を出せる状態を防ぎ、所有権を確認できない間は新しい監督操作を停止する。既に許可された局所制御まで止めない。epoch発行元、鍵の保管、フェンシング経路、復旧手順はソフトウェア基盤の具体化時に確定する。

初回起動と再起動の許可状態、順序違反の拒否、入出力整合性、命令実行前の条件確認は、NASA SWE-134を参考に要求へ落とす。各設備の安全な状態は個別に定義する。「安全＝すべての電源を切る」と共通化しない。[S5: NASA SWE-134](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695493/SWE-134%2B-%2BSafety-Critical%2BSoftware%2BDesign%2BRequirements)

## 4. 切断時の運用

通常、外部通信断、Core停止、設備故障を別々の状態として扱う。WANが切れても現地の機器制御・警報・資格確認済みの作業は続けられる。AIサービス停止時は会話支援が使えなくなるが、定型画面と現地操作は残す。Coreが停止したときは、設備が最後に受理した有効な局所プロファイルまたは設備ごとの故障時モードに移る。復旧時は現物の状態を先に読み、保存済みの要求を無条件に再送しない。

通信先によって転送実装を差し替える。初期地上試験は既存のLAN/WANゲートウェイ、将来の遅延・断続リンクにはBPv7＋BPSecを接続プロファイル候補とする。BPv7には蓄積転送、寿命、状態報告があるが、設備動作の完了保証にはならない。期限切れ要求を処置するロジック、アプリケーションの認可、重複抑止と実行記録はRockstarOS側で維持する。全テレメトリーへ状態報告を要求せず、用途ごとに通信量を見積もる。[S6: RFC 9171](https://www.rfc-editor.org/rfc/rfc9171.html)

BPSecの完全性保護と機密性保護を、機器操作の権限や安全条件の代用にしない。使用する暗号コンテキスト、鍵配布、失効、端点の信頼範囲を実装プロファイルに固定してから相互接続試験を行う。[S7: RFC 9172](https://www.rfc-editor.org/rfc/rfc9172.html)

NASA/CCSDS方式を選ぶ宇宙機とは、採用したSpace Packetプロファイルをゲートウェイで変換する。パケットを読めることと、設備の意味・コマンド権限・実行順序が一致することは別々に検証する。Space PacketとBPv7を同一プロトコルとして扱わない。[S8: CCSDS 133.0-B-2](https://ccsds.org/Pubs/133x0b2e2.pdf)

## 5. rocketstar・衛星・avokadoとの関係

rocketstarは貨物の輸送系統として接続する。貨物ID、質量・外形・取扱い条件、引き渡し状態、履歴をRockstarOSと共通化する。飛行・着陸の制御は機上の専用飛行システムが担当し、コロニーCoreや会話AIの接続を必要条件にしない。将来の有人輸送は現在の無人rocketstarの設計範囲に含めない。

A-LINKは通信経路の一つ。既存の低軌道衛星案から月面や深宇宙の常時通信能力は導けない。中継範囲、時刻同期、通信遅延、見通し、周波数、送受信性能、地上設備をミッションごとに閉じる。コロニーの現地運用は外部リンクの接続を待たない。

avokadoは居住者・作業者の操作窓口として、会話、設備の状態表示、作業支援を担当する。現行E3の4本のTowerとHubを生命維持系の独立保護器に転用しない。監視対象の現地制御器とは異なる故障領域に置く。アンテナの見通しがない場所では別の中継設備が必要であり、電源だけでどの場所でも衛星を直接受信できる仕様にはしない。

## 6. 受入試験として固定する項目

以下は計画した試験。合格実績はまだない。`T_detect`、`T_response`、`T_hold`、制御許容範囲、通信負荷、停電継続条件は設備の危険分析・実測・電力設計で数値化し、未入力なら該当する実機の運用承認を出さない。ソフトウェアの模擬試験は、実機の居住適合性の検証に数えない。

| ID | 与える故障・入力 | 合格の判定 |
| --- | --- | --- |
| H-V01 | WANの遮断、遅延、復旧 | 局所制御と現地警報が継続。未送信記録を保持し、復旧後は期限と重複を再判定 |
| H-V02 | Coreプロセス停止、電源断、再起動 | 機器保護と局所制御は設計した範囲を維持。起動直後に無許可の出力変化を発生させない |
| H-V03 | avokado・AIの全停止 | 設備側制御、独立警報、現地操作経路の機能を維持 |
| H-V04 | Coreの同時有効化・ネットワーク分断 | 一つの設備が同時に二つの監督権を受理しない。古いepochの要求を拒否 |
| H-V05 | 重複要求、順序逆転、期限切れ要求、古い状態版 | 設備が拒否または記録済み結果を返す。二重の物理動作を発生させない |
| H-V06 | 操作受理直後の通信断・再起動 | 結果不明をUNKNOWNとして表示。現物確認または設備の記録照合後に次の操作を決める |
| H-V07 | 不正値、欠測、校正切れ、時刻不明、センサー矛盾 | 正常表示へ埋め込まない。局所診断・既定処置と根拠の記録を行う |
| H-V08 | 非認可操作・変更された設定・無効な署名 | 出力に到達する前に拒否。拒否記録の保存失敗で操作を許可しない |
| H-V09 | ログ容量逼迫、転送キュー上限、破損ストレージ | 局所制御を止めず、規定どおり負荷制限。警報・実行証拠の喪失を隠さない |
| H-V10 | 給電系統または共通通信機器の故障 | その故障が独立保護と全ての代替操作経路を同時に失わせないことを構成・実機で確認 |
| H-V11 | 遠隔更新の中断、互換性不一致、ロールバック | 設備制御の承認済み版を保持し、未完了版で運転開始しない |
| H-V12 | 全領域を接続した無人連続運転と記録照合 | 資産、観測、要求、設備結果、保守作業が一致。計測した応答時間・消費電力・容量が設計予算内 |

## 7. 物理設計を閉じるための入力と成果物

| 入力・解析 | 必要な成果物 | 未決定のまま固定しないもの |
| --- | --- | --- |
| 場所、人数、滞在時間、補給・退避条件 | ミッション要求、資源予算、区画配置、故障時運用 | 与圧仕様、居住容量、消耗品の量 |
| 電力需要と停止許容時間、ピーク・始動電力、劣化 | 発電・蓄電・配線・配電・保護の設計、停電試験 | 電源容量、電圧、電池容量、配線太さ、継続時間 |
| 熱環境、排熱、日照・夜間、外部環境 | 熱モデル、機器定格、断熱・排熱系の設計、環境試験 | 放熱器面積、冷却能力、ヒーター量 |
| 空気・水・廃棄物の需要と品質、故障継続時間 | 設備選定、配管・流量・漏れ・水質・故障解析、試験記録 | 酸素・圧力等の運転設定、処理能力、タンク容量 |
| 重力、放射線、粉塵、隕石、振動、着陸・運搬 | 構造・遮蔽・密閉・固定・据付仕様と実証 | 材料、厚み、質量、構造寸法 |
| 物理機器の故障モード・共通原因・交換性 | FMEA/FMECA、故障木、保護独立性、保守・退避設計 | 冗長台数、切替方式、交換周期、保護の応答時間 |
| 通信経路・遮蔽・遅延・スループット | RF設計、経路予算、端末配置、接触計画、相互接続試験 | 常時通信可能範囲、衛星数、通信容量 |

一次の電力整合は、使用可能な蓄電エネルギーが「想定断電期間に必要な負荷の時間積分＋始動等の過渡分＋予備分」を満たすこと、同時最大負荷が給電・保護の定格内であることを確認する。これは計算法の入口であり、劣化、温度、変換損失、故障、熱管理を織り込んだ機器設計の代用にはしない。

## 8. 設計を進める順序

まず、模擬センサーと模擬負荷でH-V01〜H-V09のソフトウェア契約を検証する。次に、危険を伴わない実設備と専用制御器をつないだ地上無人試験でH-V02、H-V07、H-V10〜H-V12を実測する。その後、場所とミッションが定まった段階で機器選定・資源量・環境適合を閉じる。有人居住に移る判断には、設備・人間系・避難・保守までを含む別の適合性評価が必要になる。

この順序ならRockstarOSの共通基盤を今から作り始め、将来の場所ごとの設備設計を差し替えられる。場所を決める前に居住設備の仕様を確定したことにはしない。
