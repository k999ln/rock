# A-LINK v0.4：受信機能の実装と検証

2026-09-22。通信の基本設計を、実行できる受信プログラムと異常系試験へ進めた版です。ソフトウェア71件の試験は合格。実衛星の受信とロケット帰還は未実証です。

## 今回、実装して確認したこと

通知を暗号化して受信し、保存してから受領確認を返すプログラムを作りました。接続できないWi-Fiへの張り付き、切替の繰返し、切断・再起動後の取りこぼし、同じ通知の二重表示を試験しました。データ受信だけを扱い、受信した文章から機器操作や決済を実行しません。

実ソケットで動くPC内の配信サービスと3つの模擬経路を使った結果は次の通りです。経路名のWi-Fi・携帯・衛星は論理的な試験条件であり、実電波の測定ではありません。

| 試験段階 | 結果 | 保存された通知 |
| --- | --- | --- |
| 正常時 | Wi-Fi模擬経路で受信 | 1件 |
| Wi-Fi模擬経路を切断 | 携帯模擬経路へ切替 | 2件 |
| 地上2経路を切断 | 衛星模擬経路へ切替 | 3件 |
| 全経路を切断 | 接続待ちを表示し、既存データを保持 | 3件 |
| 携帯模擬経路を復旧 | 待っていた通知を取得 | 4件 |
| 受信器を再起動し同じ通知を再送 | 重複として受理し、表示件数を増やさない | 4件 |

実行環境はPython 3.12のmacOSホストです。衛星SDKは模擬オブジェクトを使用し、実SDKの無線起動は行っていません。タイマー境界は試験用時計で確認しました。切替所要時間・起動時間・実際のSSD電源断耐性・無線感度を計測した結果ではありません。

## 設計上の食い違いも修正

関連資料の最新版はTower20 E3で、4本の20cmタワーと別Hubです。通信機能はHubへ追加する構成に変更しました。旧v0.3が参照していた20cm一体箱、3眼、内部DC80Wは、新構成へ転用しません。E3の仮DC116Wも通信追加分を含むとは扱いません。

初期の実衛星試験用構成は、外付けRockBLOCK 9704、Iridium IMT、Cloudloop、HubへのUSB接続に具体化しました。公式SDK向け受信コードを同梱し、version 1.0.1のLinux x86_64配布物について必要API9個とSHA-256一致を確認しました。配布物を読んだ確認であり、機器接続の合格ではありません。

9704の設置条件に合わせ、衛星部を他の送信機と別筐体にし、空が見える場所で受信します。屋内のHubには有線でデータを戻す方針です。実験開始は短いUSB配線で行い、建物への引込みは長さ・電源・配線方式を別途確定します。[メーカー設置条件](https://docs.groundcontrol.com/iot/rockblock-9704/installation)

## まだ解決していないこと

実際のHub・SIM・アンテナ・衛星機器・契約を使う受信は未試験です。地上のLinuxインターフェース固定と衛星の受信プロセスを完成したRockstarOSへ組み込み、機器の同時動作まで通す必要があります。配信側の運用サービス、衛星への自動再配信、初期登録・鍵更新も本番実装前です。

完全に遮蔽され、外へつながる有線経路もない場所では、新しい情報は受信できません。そこには屋外受信部からの通信経路を追加する必要があります。「電源だけで無条件にどこでも受信」は達成した扱いにしません。

自前衛星2機による常時サービスとロケットの両段帰還も未解決です。旧ロケットの質量条件を再計算すると、仮の上昇余裕は約244m/sで、上段乾燥質量が2t増えるだけで余裕が負になります。質量・帰還推進剤・再突入・着陸を結合した解析と実証が必要で、通信試験の成功をロケットの成立へ転用しません。
