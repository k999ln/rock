# avocadoOS 1.0 — 8原則を適用した製品・事業・開発設計

2026-09-16現行優先: [製品目的](product-north-star-20260915.md)とRQ48を優先し、[AIネイティブOS共通設計](ai-native-os-architecture.md)を実装設計の正本とする。中核は交換可能な端末内LLM＋offline agentを持つOS。Sky/Zema、便利な自動化、Game/IP/動画/VR、Wallet/Fundは同じ基盤を使う応用系統とする。収益経路は重要だが、全応用の直列依存にはしない。

状態: 設計。利用者が提示した8原則と「現段階を1.0のベースにし、継続改善する」を適用する。[確定要望RQ01〜RQ48](product-baseline.md)、[system構成](rockstaros-1.0-architecture.md)、[実装承認範囲](execution-approval-20260909.md)を維持する。新しい市場・価格・所有権・実資金取引を確定した文書ではない。

## 1. 製品の核と決定の区分

**目指す体験: 自動化の仕事を、実行から結果・費用・復旧まで見失わない。**

OSが端末内LLM・記憶・仕事・権限・停止・復旧を担い、Skyが「何をどこで動かすか」、Zemaが「依頼・進捗・承認・成果」、Walletが「費用と確認済み資金」を扱う。tob側の商品と関心のあるGame/IP等を同じ契約で接続する。ジョブの成功、納品、売上、入金は別イベントとし、仕事完了だけで収益を記帳しない。

| 区分 | この設計での扱い |
| --- | --- |
| 利用者の確定指示 | avocadoOS 1.0、交換可能なローカルLLMとoffline agentを中核に継続改善。Sky/Zema、便利な自動化、Game/IP/動画/VRを接続。最初の実機はPixel 10 GL066。ゲーム交換・作者SDK・既存料金は維持 |
| 具体化した設計案 | 最初の実用検証を一つの業務に集中し、同じ商品の実行・成果・状態確認・復旧を通す。配布と販売の入口を開発と同時に設計する |
| 検証する仮説 | 初期利用者は文章・記事・提案を納品する個人事業主/クリエイター。候補商品は既存の引用整理。結果と状態を探す負担の削減が選ばれる理由になる |
| 未実証 | 需要、継続率、支払意思、競争優位、市場規模、独占、世界初、利益、実機対応、本番金融。設計への記載を実証に換算しない |

引用整理は最初の検証候補であり、OSを文章専用へ転換する決定ではない。PC・cloud・self-hostを一律に後回しにせず、選定商品に必要な実行先を接続する。

## 2. 8原則から設計への変換

| 原則 | Rockでの設計判断 | 仮説を確かめる証拠 |
| --- | --- | --- |
| 0→1 | 既存OSの全機能を作り直さず、仕事・成果・費用・復旧を一つの利用体験にまとめる。Linuxや既存台帳・recipeを再利用する | 既存手順と同じ成果品質を保ち、利用者の手間が減るか。「組み合わせた」だけで発明や新規性を断定しない |
| 競争より独占 | 最初は一つの反復業務に強い製品にする。大市場の汎用アプリ数競争を先行させない | 同じ困り事を持つ小集団が繰り返し選ぶか。排他契約、移行妨害、tob一社独占を要件にしない |
| 逆張りの問い | 仮説: 自動化を増やすことより、既存自動化の実行結果と費用を見失わないことに価値がある | 実際の直近業務を観察し、既存ツールだけで十分なら仮説を修正する |
| 秘密を探す | 結果を探す、失敗後にやり直す、費用が確定しない場面を調べる | 本人の同意のある業務観察。誘導した好意的感想ではなく、繰り返す未解決作業を記録する |
| べき乗則 | 最初の完了体験、保存/復旧、導入可能性へ開発を集中する | 作業ごとに対象RQ・不便・検証指標を一つ記す。見た目の機能数や生成コード量で優先しない |
| 明確な楽観主義 | 配布・実用・実機・金融を別ゲートにし、担当・入口・合格証拠を指定する | 同じ配布候補の試験と再現手順。根拠のない完成日を宣言しない |
| 販売も重要 | CM→対象者向け説明→試用→最初の成果→継続の導線を作る | 広告再生数だけでなく導入・初回完了・自主的再利用を測る。配布未合格時の案内はデモ/試用募集まで |
| 創業チーム | 製品判断、OS、安全な資金接続、商品供給、利用者支援の責任を分ける | 役割の実名担当・決裁者・障害時の連絡先を決める。株式比率や雇用条件をAIが決定しない |

## 3. 最初の商品と一周の利用体験

最初の対象仮説は「文章を納品する個人事業主のうち、引用整理を反復し、複数の実行結果を手作業で探している人」。文書を扱う全員を対象市場としない。この問題が見つからなければ、既存商品の中から別の反復業務を選び直す。

Linux/QEMUの候補は `org.rockstar.citation-organizer` の既存native recipeで、引用整理に限定する。Androidの最初の候補は別契約の `article-preparation@1`（citations→free-article）。同名処理を同一商品にせず、各成果schemaと検収条件を比較する。調査・事実確認・顧客獲得・自動納品・売上発生を実装済みと表示しない。

1. Skyで商品を選びZemaへ引き継ぐ。用途、作者、版、出力例、対応実行先、必要な許可、料金/実費の状態を確認する。Linuxの旧Hub入口とは実装環境を分ける。
2. 本人が入力と保存先を選ぶ。外部へ送る内容と費用上限を開始前に示す。未接続/未対応なら開始せず理由を出す。
3. 実行中は実行先・状態・最後の確認時刻を表示する。接続断で結果が不明なら「照合待ち」とし、新しい仕事として勝手に再送しない。
4. 完了後、成果を表示・保存・再表示する。成果の出所と商品版を追えるようにする。job ID、receipt、成果参照を関連付けるが同じIDに統合しない。
5. Walletで関連費用を確認する。見積、予約、確定費用、確定入金を分け、未接続は「未接続」、不明は「未確定」と表示する。0円や利益と読み替えない。
6. OSを正常終了し、再度開いて結果と状態が残る。失敗時は原因、保存済み範囲、安全な再開/照合方法を案内する。

初回previewのWalletは**開発用テスト残高・模擬記帳**である。実業務データの投入や実売上の管理を許すには、公開試験鍵からの移行、データ保護、保存/削除方針、利用者の同意を別途整える。初回検証は公開または合成文書を用いる。

native recipeとPC版Mr.の同名処理を同一商品と決めつけない。既存比較では出力形式に差があり、PC adapterの追加自体は処理速度改善を示していない。[比較記録](hub-wallet-pc-comparison-20260909.md)と[接続制約](pc-citations-adapter.md)を基準に、必要な場合だけ同じ成果契約で比較する。

## 4. systemごとの責任と既存資産

新しい万能基盤を作り直さない。下表は到達設計であり、すべてが現在のOS imageに接続済みという意味ではない。

| system / 対象RQ | 再利用する基盤 | 1.0で詰める接続と境界 | 合格を判断するもの |
| --- | --- | --- | --- |
| OS・配布 / RQ12,16,17 | Buildroot/Linux/QEMU、専用UID、読取専用OS、保存disk、A/B、backup、既存launcher | 個人の既存VM/固定パスに依存しない導入。公開試験環境と本番鍵/データを分離 | 同一候補のD0〜D6とfresh環境の導入/終了/再開/復旧/削除 |
| Hub・商品 / RQ01〜04,11 | 署名manifest、catalog、有限recipe、導入/更新/停止/削除、既存引用整理 | 商品の用途と実行能力を正確に表示。代表商品の入力から成果再表示までつなぐ | 同じ成果品質、操作数、初回完了率、再利用 |
| 接続・実行管理 / RQ04,07,08 | Platform API、実行receipt、runner、PC adapter、remote fixture | 商品ごとの許可・実行先・接続断の意味を表示。nativeから実PC/cloudへの接続は対応試験まで未完扱い | 切断/再送/再起動、結果不明時の照合。検証範囲を越えたexactly-once保証をしない |
| Wallet / RQ01,05,06,07,15 | 既存予約・台帳・照合・月額重複防止、ATM simulator | job成果と資金確定を別管理。費用・入金の出所と最終照合時刻を表示 | 模擬台帳の一致、二重記帳拒否、未確定表示。実収支はprovider接続後の別受入 |
| Game・作者SDK / RQ13,14 | 現行hostのGX00、既存Wallet、GX01契約案、SDK計画 | owner/game分離→合成交換契約→SDK・サンプル・診断。ゲームclientに資金台帳の書込み鍵を渡さない | 2作者/2game/2ownerで正当な取引と相互拒否、異常系、初見導入計測 |
| 運用・更新 / RQ08〜10,12 | health判定、rollback、backup、診断、既存試験/進捗記録 | 保存形式とOS版の互換性、復旧入口、問い合わせ時に必要な最小診断をそろえる | データ保持、旧版復帰条件、秘密を含まない診断、障害時の担当 |

最初の標準利用経路はSkyで選びZemaで仕事を管理する。Gameは関心に基づく優先的な応用系統で、連携/SDKの要求を落とさず、制作・試遊・保存を金融完成と独立に検証する。OSの達成演出・ログイン報酬を追加する決定ではない。ゲーム停止で仕事・Wallet・OS復旧を止めない。

## 5. 現在地と開発順

現行順序は共通設計第9節のCore/応用別trackに従う。所有GL066での試験署名APKはLocal AI、Sky/Zema、固定Tool、実再起動、非破壊backupを確認済み。full build/flash、production署名、鍵喪失復旧は未受入。直近はmodel互換/記憶/副作用分類/Sky能力交渉の契約を具体化し、原稿Toolと非金融Game/IP候補を同じ基盤で検証する。後続の収益ProviderとFundは独立gateとする。

以下のSHA、D6、RLS01の表は**2026-09-09の設計時点の履歴**。現在の未完了taskや優先順位ではない。現在の進捗は[全体構成](system-composition.md)と進捗JSONを参照する。

配布候補はsource・image・host tools・設定・成果物hashの対応表を持つ。凍結版を採るなら対象版のCIと受入証拠を照合する。新しいsourceでbuildするなら旧imageのD0〜D6を流用せず、同じ新候補を再受入する。新台帳の搭載では移行・backup・A/B復旧も再試験する。

1.0の呼称は維持し、更新ごとに追加対応と移行条件を明記する。発売日や1.1/2.0への機能割当は現時点で保証しない。実装量ではなく上記の合格証拠で配布段階を上げる。

## 6. 最初の検証計画と「続ける/見直す」の基準

以下の数値は**提案するpilot目標**であり、実績・利用者の追加確定要望・安全試験の代替ではない。外部協力者の募集や連絡は本設計だけで実施しない。

| 観点 | 測定方法 | 最初の目標と失敗時の対応 |
| --- | --- | --- |
| 困り事 | 候補者10人に直近の実作業を聞き、現行手順を確認する。人数/選定方法を記録 | 共通する反復作業がなければ対象業務を変更。10人の意見を市場全体へ一般化しない |
| 初回体験 | 初見10人が対応環境で公開/合成入力を使う。導入、download、商品処理時間を分けて測定 | 8人以上が個別介助なしで最初の成果再表示まで到達。準備済み環境で15分以内を目標とし、総所要時間も隠さない |
| 手間の削減 | 同じ入力・成果品質で既存手順と比較。操作時間と機械待ち時間を別計測 | 人が操作/確認する時間の中央値30%以上削減を仮目標。未達なら導線/商品選定を修正し、高速化を宣伝しない |
| 保存/復旧 | 再起動・切断・二重要求・restoreの指定ケースを回す | 対象試験で成果消失/二重記帳0件。件数と条件を公表可能な要約へ記録し、無事故の一般保証にしない |
| 継続 | 7日間、同意した最小限の利用記録または本人報告を用いる。催促や報酬による利用は別計上 | 10人中6人以上が自主的に再利用を仮目標。未達なら習慣化演出ではなく業務上の必要性を見直す |
| 支払意思 | 料金体系を正しく説明し、何に対価を払うかを聞く。口頭回答と実契約を区別 | 固定の合格率は未設定。少なくとも必要コストと具体的便益を比較できるまで採算や販売成立を宣言しない |

安全・データ保持のゲートは、pilotの好評やCM日程を理由に緩めない。失敗は「追加機能を増やす」前に原因と最小修正を記録する。

## 7. CM・流通・継続運用

2026-09-10追記: 利用者からCM制作完成済みとの申告を受領。制作は残件から外し、既存CMの表現照合と告知／導入ページへの接続を進める。以下は導線と表現の方針であり、CMを新規制作する指示ではない。現在の内部受入、公開停止条件、条件付きの追加1〜2日概算は[最新の進捗追記](release-followup-20260910.md)を参照。

伝える順序は「誰のどの作業が楽になるか→実際の一周デモ→対応環境/制限→試し方」。コンセプト表現の案は「自動化の仕事と成果を、見失わない。」とする。実現済みの範囲を併記し、収益保証・世界初・BlackBerryへ今すぐ導入可能とは表示しない。

配布ゲート前の入口はデモまたは試用希望の受付、合格後は対象環境を限定した **avocadoOS 1.0 Developer Preview** の導入案内。物理端末対応と本番金融は別表示。既存Webは説明/補助画面として活用可能だが、Web公開をnative OSの配布完了にしない。

初期チャネル案は対象業務の小さなコミュニティへの説明と紹介。実際の連絡・公開・広告購入は行わない。試用支援のつまずきをHub導線と診断へ還元する。集客数、対応環境に合う人数、導入数、初回完了数、継続数を別々に把握する。

現行RQ20のSky利用料は、検証済み収益から直接実費を先に扱い、残額からUTC月最大888 USD centsまで回収する。収益0なら0、先払い・不足分の債務化・翌月繰越・カード定期請求はしない。ToB利用料0と同一契約の複数端末重複防止を維持する。nativeの月888固定試作は旧契約の履歴で、現行課金条件へ流用しない。商品代/API実費は別軸、CSV等の限定policyは各正本に従う。ATMのRock手数料0、ゲーム料金未定を維持し、previewから実課金を開始しない。

採算は契約収入から決済・実行基盤・更新配布・利用者支援等の実コストを引いて検証する。未知の費用を0にしない。無制限の推論無料化、ATM外部費用の無制限補填、架空の販売実績は設計に入れない。

## 8. 蓄積すべき強みとチーム

強みの候補は、商品を接続する契約/適合試験、異常時でも成果と資金状態を説明できる運用、既存商品から学んだ実用導線、作者と利用者への支援である。いずれも蓄積して検証する対象であり、現時点の独占力やネットワーク効果の実績ではない。利用者の成果や履歴を持ち出せないことを強みにしない。exportには権限・秘匿・形式互換の設計を伴わせる。

| 責任 | 決めること | 未割当の扱い |
| --- | --- | --- |
| 製品決裁 | 利用者が要望・対象・販売条件の最終判断。担当が証拠と提案を用意 | AIが実証なしに要望を置換しない |
| OS/配布 | 候補版、更新/復旧、対応host/機種、出荷停止判断 | 技術責任者の実名を外部試用前に決める |
| 商品供給（tob） | 商品ロジック、価格/ライセンス、品質と保守 | 接続契約と責任分界を商品ごとに確認する |
| Wallet/接続 | 認証、台帳、照合、provider境界 | 実資金開始前に運用責任者と確認体制を決める |
| 販売/支援 | 説明内容、問い合わせ、障害連絡、更新案内 | 外部募集前に窓口と対応範囲を決める |

一人が兼任できるが、責任を曖昧にしない。共同創業者、株式・知財・経営権・報酬・離脱時の扱いは当事者の合意事項で、現時点では未確認。割合や契約を本書で創作しない。

## 9. 省トークンで継続する運用

次作業は[進捗JSON](../data/project-status.json)の既存task/phaseGateを使い、重複した新バックログを増やさない。一回の開発は「対象ゲート→必要箇所→最小修正→対象試験→要約証拠」の単位にする。全履歴/全ログの再読、根拠のない全面再設計、無関係な並列作業を避ける。

必要なsource・設定・設計判断・小さいfixture・再現/復旧手順・試験要約をGitへ保存する。image/cache/大量ログ/重複成果物/秘密値は追加しない。通常の小変更は関連試験から始め、完了時のリポジトリ規約上のverifyと配布候補の広い受入を区別する。

この設計更新はruntime変更、配布、外部連絡、実機書込み、実資金取引ではない。保存branchとmain統合を区別し、残る機種・provider・担当の未確定事項で安全に進められる設計/合成検証まで止めない。
