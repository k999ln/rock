# EveのAgent開発ファンドとNoahの定期便

- 本人の構想（要約）: 今公開中のAgentはそのまま残し、これからの新しいAgentはEveを通す。開発者も稼いでEveに使え、個人や会社は複数Agentへ分散して資金を出せるようにする。AIが実際にどれだけ作るかを予測し、農家へ十分な現金を払い、投資額や技量に関係なく基礎の食べ物を継続して配る。
- 文書の状態: 2026-11-26時点の設計レビュー。今回の成果は設計。実資金の取扱い・本番運用は後段の審査対象。検証基点は最新 `origin/main` を取り込んだ `2a115abc1c725ee42346db404425b0eefca47075`（この記録は公開・本番反映を意味しない）。
- Goal（Eveが作る）: 目的＝検証可能な複数Agentの提供能力へ分散する候補を作り、実現した納品・入金・費用だけで成績を示す / 入力＝Agent版、成果単位、需要、価格、受入率、同時処理・人手・Provider上限、費用、Receipt、作者条件、法務上の提供範囲 / 期待成果＝版固定のバスケット、P10/P50/P90、実績との差、利用可能残高と用途別台帳 / 予算上限＝法務・本人が別途承認した法定通貨の上限 / 要る権限＝本人確認、作者、Wallet、Broker、独立Jev、運営の分離承認。
- Eveがつなぐもの: 現行Eve Agent作成・出典固定（`lib/eve-agent-creation.ts`, `lib/eve-agent-origin.ts`）、ビルド/審査（`docs/services/eve-agent-build.md`）、掲載版、Work/Receipt、Wallet、需要と単位経済。新しい外部の部品は、GitHub/MCP/配布物をEveが権利・出典・版・秘密・固定試験・接続先まで確認した後だけ候補にする。
- 出力先: phone/PC共通のNoahで、候補・無料予測・実績・資金台帳・作者残高・受取方法を別画面/別台帳として表示。ファイルは版固定の設計スナップショット、予測、Receipt、月次照合。eSIMは任意の専用通信経路であり本人性や金融権限ではない。
- Wallet: 初期は法定通貨だけを候補とし、円だけには限定しない。実通貨ごとに元帳を分け、表示時換算を清算額に使わない。作者の確定収益は現金受取またはEve利用料へ充当できるが、既定は現金、充当は本人の都度選択・上限内・取消可能とする。Noah収益の自動再投資は未決定なのでOFF。現金/農産物/トークンの受取選択も未決定で、トークンはPhase 4より前に作らない。
- hardware profile依存: 設計・予測・確認はphone/PC。実行は各Agentの審査済みprofile。eSIM停止中も所有記録と回復経路を失わず、出金・受取先変更はWebAuthnによる別承認を要する。
- 失敗時: 法的分類不明は無料予測と紙上計算へ戻す。Receipt不一致は該当Agentと分配を保留、結果不明は同じ操作IDで照合し自動再実行しない。資金不足なら新規約束を止め、農家の既発注分を値切らず支払い、利用者へ不足と次回条件を表示する。

## 2026-11-27 git_audit後の境界補正（設計のみ）

今回の監査で見つかった既存実装との差は、実装済み・収益化済みとは扱わない。ここでは、既存Agentを移行台帳で残すことと、移行後の新規AgentをEveだけから作ることを維持したまま、予測・証拠・公開表示の境界を明確にする。

### Eveの需要推定とファンド候補を混ぜない

`lib/eve-demand.ts` の需要台帳は、受注募集・ASP・公開価格の出典、`volumePerWeek`、競合、単価から「売れる見込み」を作る。実績が5回未満なら控えめな事前値、5回以上でも `EveSaleRecord` の出した数と売れた数から算定する需要推定であり、入金のReceiptではない。一方、現行の `lib/automation-fund-catalog.ts` は一般catalogを `ready` 候補へ写すだけで、売上・費用・Receiptを0としている。`automation-fund-store` の `observedReturnBps` も、接続された検証済み台帳の過去指標であって将来予測ではない。

したがって、需要台帳の値は次の期間の無料予測にだけ入力し、`verifiedGrossMinor`、`completedReceipts`、`paid`、利用可能残高へ昇格させない。Noahでは「需要からの予測」「検証済み入金」「未観測」を別行にし、入金証拠が無いAgentを0円の実績や成功として表示しない。需要ID・需要台帳の版・確認時刻を予測revisionに固定し、需要の更新で過去の予測や成績を上書きしない。

### 現在の容量と150分を別物にする

Eveの組み合わせ探索は、需要に対してAgentの合格率・工程の費用・本人の分数を掛けるが、ファンド候補には現在、需要量と処理容量を結ぶ共通フィールドがない。150分の無料体験上限も、1回の予約・実行時間の制限であり、Agentが作れる件数、検収できる件数、Providerが受けられる件数、販売・配送能力や売上を表さない。

将来の予測は、同じ成果単位と期間で、次の値をそれぞれ出典付きで持つ。

`納品可能数 = min(需要上限, Agent処理上限, 人の検収上限, Provider上限, 配送上限)`

どれかが未観測なら単一の金額を出さず、下限・上限または「算定不能」と表示する。150分の値を既定容量・売上実績・ファンド配分へ転用しない。

### 出典pinの効力を限定する

`EveSourcePin` の `key`・`revision`・`metadataSha256` は保存したリソースのスナップショットであり、上流の真正性、モデルの品質、実行許可、権利許諾、収益性を証明しない。`EveAgentOrigin` も本人が選んだ会話・回答の由来を固定するもので、モデル attestation ではない。よって、出典pinだけでファンド候補・収益・作者報酬へ昇格させない。

候補の証拠には、少なくとも本人のEve由来、Agent/releaseのIDと版、出典のkey・revision・metadata hash、確認時刻、許諾・接続先の判定、候補に使ったcatalog snapshotを別々に記録する。不足・失効・上流の版違いは候補から外し、既存Agentの保存や閲覧まで遡って無効化しない。

### Fund Receiptをcanonicalにする条件

runの完了数、クライアントから送られたscore、Eveのfunnel記録、WalletのSANDBOX提案は、いずれもcanonicalなFund Receiptではない。現行 `automation-fund-store` が返す `verifiedGrossMinor`・`operatingCostMinor`・`completedReceipts` を0へ戻す挙動は「未接続」を示すもので、売上0円の確定記録ではない。

canonicalなFund Receiptは、サーバーが所有する追記専用記録として、fund/AgentまたはcombinationのIDと版、Work/実行Receipt、Providerまたは銀行の外部参照、通貨・金額、発生時刻、証拠hash、状態、取消・返金なら元Receiptへのリンク、重複防止キーを持つ。外部照合・owner scope・独立Jev/Walletの必要な承認が揃うまで `candidate` または `unresolved` に留め、`paid`・`verifiedNet`・分配可能額へ進めない。実行Receiptだけで入金を作らず、未知や欠損を0へ置換しない。

### CatalogのEve/source/version gate

`catalog.status === 'ready'` は、一般catalog上で使えるという意味に限る。移行日以前の公開Agentはmanifestに固定された先行者枠として残せるが、移行後の新規Agentと重大revisionをfund candidateへ入れるには、Eve由来の証明、Eveが固定したsource/release、版hash、Jevの独立判定、確認時刻が必要である。catalogのentryだけにそれらが無い場合は、Noahで閲覧できてもファンド候補にはしない。

候補生成時は、サーバー側で保存したcatalogのsource URI・snapshot/version・checkedAtとAgentのEve source/versionを突き合わせる。sourceまたはversionの変化、古いcheckedAt、Eve証明の欠落、既存manifestとの不一致は fail-closed とし、既存の掲載枠を消さずに新しい候補だけを停止する。

### PAPER・no-depositsの公開UIゲート

法務・運営の承認前は、公開UIのモードを `PAPER` / `NO_DEPOSITS` に固定する。表示してよいのは出典付きの無料予測、仮のシナリオ、検証待ち・未観測の状態であり、入金・預り金・出金・約定・持分・利回り保証・投資家向けの確定分配を意味する文言、口座入力、deposit/join操作を出さない。PAPERの候補額は `paperCandidate` と明示し、残高・債権・権利ではないこと、実資金・本番D1未接続であることを同じ画面で伝える。

実通貨pilotへ進む切替はclient値ではなくサーバーの法務/運営ゲートで行い、Phase 0の分類・契約・登録/届出確認、分別管理、限度額、取消/返金、独立照合、監査をすべて満たすまで無効とする。切替前に実資金・実銀行・実送金を受け付けない。

### 農家の支払Receiptと受取人の配達Receiptを分離する

農家・仕入先の請求/支払Receiptは、品目・数量・ロット・単価・通貨・支払先・支払状態を確認する調達台帳の証拠である。受取人の配達/受領Receiptは、shipment・recipient・受取日時・欠配/返品を確認する配送台帳の証拠である。前者は後者の配達を証明せず、後者は農家への支払や売上入金を証明しない。農家への法定通貨の支払を、受取人の申告や配送完了だけで確定しない。

両台帳は、必要最小限のshipment/lot IDだけで関連付け、農家の支払・在庫、受取人の配達・受領、Agentの外部入金、基礎食料の分配を別Receiptとして保持する。住所・口座・顧客本文は各役割に必要な担当者だけが扱い、配達Receiptを投資家分配やAgentの収益Receiptへ再利用しない。

### 分配候補額の表現

Noahが表示する金額は、次の状態を一つにまとめない。

| 表示名 | 意味 | 許される根拠 |
| --- | --- | --- |
| 予測入金 | 需要・容量・受入率・回収率からの次期間シナリオ | 予測revisionと出典。未校正なら幅のみ |
| 候補配分額 | 予測を上限として置いた紙上のシナリオ額 | `paperCandidate`、期間・通貨・仮定・対象人数を併記。権利ではない |
| 予約額 | 承認済みmilestoneまたは調達枠として別予算から確保した額 | サーバー承認・予約Receipt。未払金と混同しない |
| 支払可能額 | canonical Receiptを照合し、返金・費用・税/紛争予備を引いた額 | 預り現金・確定債務・通貨ごとの元帳 |
| 支払済み/配達済み | 実際の決済または配達を完了した額・物 | canonicalの支払Receiptまたは受取人Receipt。互いの代用不可 |

画面の「分配候補額」は、金額・通貨・対象期間・分母人数・原資・控除・不確実性・最終確認時刻を併記し、`約束ではない／算定不能` を隠さない。農家の仕入予算、基礎食料の全員同額枠、作者の対価、資金提供者向けの契約上の分配を一つの候補額へ合算しない。実績のない候補を0円の確定分配と表示せず、canonical Receiptが無ければ `未観測` または `保留` とする。

## 組成・予測・配分の設計

1. **既存掲載枠:** 移行日の公開release ID/hash/掲載状態を署名manifestへ固定する。同じreleaseはEve再登録不要。作者変更、権限/通信先/課金/主要出力の変更は新revisionとしてEveへ戻す。現在の直接upload/intakeは原本保存には使えても、Eve証明なしに新規公開・資金対象へ昇格させない。
2. **能力と単位経済:** Agentごとに成果単位、締切、単価、取消/返金、1日処理上限、検収人分、Provider枠、変動費、共有固定費を記す。見積利益は `予想入金−変動費−割当固定費−返金予備`。配送能力と収益率を掛け合わせて水増しせず、制約の最小値を使う。現行Notionの別招待試験にある累計150計算分は候補上限の例に留め、mainの既定容量や売上実績へ昇格させない。初回の実取引・着金の受入は未確認。売上金額は未観測と表示する。
3. **バスケット:** 最初はbalancedだけ。異なる成果・顧客・Provider・検収者を優先するが、「種類が違う」だけで分散済みとは呼ばない。単一障害点、売上集中率、最大損失、現金化までの日数を表示する。重み変更は次期間からで、過去の持分や成績を書き換えない。
4. **資金→Eve開発:** 入金元本を売上とせず、EveがAgent別の目的・成果・容量・段階・予算を提案し、AMCが承認済みmilestone分だけ予約する。独立Jevの検収後に開発費を支払い、契約で定めたholdbackは運用Receiptまで保留。中止時は検収済み実費だけを精算し、未予約/未使用元本は契約と法務に従い残高維持または償還する。開発者が作者・資金提供者・評価者を兼ねる場合は権限と承認者を分離する。開発費と利用後の作者shareを両方払う時は別の対価として先に開示し、二重請求しない。
5. **能力提供者と資金提供者:** 計算資源、データ、人手、販売経路を出す人/会社には検収単位の費用を払い、元本持分や予測投票と混ぜない。資金だけを出す人/会社は運用指図・検収・作者選定権を自動取得しない。どちらも基礎食料の額を増減させない。
6. **無料予測市場:** 問いを「Agent Aは締切までに検収済み成果を何単位作るか」のように、単位・締切・判定Receiptを先に固定する。参加者は無料でP10/P50/P90または確率分布を提出する。数量分位はpinball lossとP10–P90の実測coverage、二値事象はBrier scoreで評価し、過去期間のoffline backtestで校正を見る。賭金、景品、換金、持分、注文、予測によるAgent配分権は0。自己取引、締切後編集、同一人多重投票を無効化する。
7. **予測の使い方:** 予測は人が承認する次期間の発注/容量/予約額に上限を付ける補助で、重み・報酬・分配を自動変更しない。未校正、Receipt遅延、予測後の定義変更、極端値集中時は使わない。実績との差は予測revisionを保持して公開し、当たった予測を実績に混ぜない。
8. **任意の後段:** 対価や経済的利益を伴う予測、持分の譲渡、持分の売買注文は別の法務・商品設計。許可されるまで板の見本はPAPER、約定0、入出金0、譲渡0。将来もNAV/実現残高と指値・気配値を別表示し、買い手不在・価格差・部分約定を明示する。Receipt陳腐化、基準価額差、障害、操作疑いで新規注文と約定を停止する。Noah収益の再投資、現物/現金選択、tokenはそれぞれ独立した本人決定と法務判定を要する。
9. **食:** Phase 2を待たず、別予算が確保できればPhase 3を独立して始められる。農家とは法定通貨の仕入契約で、地域相場・持続可能な原価を下回らず、品質・小口・選別・梱包の仕事にも十分な対価を払う。検収、支払期日、送料を先に固定し、利用者の投資成績やtoken価格を支払条件にしない。基礎枠は対象者全員へ同額予算。品目差は栄養・アレルギー・地域在庫・送料の説明可能な制約だけにし、農家への支払額を削って等分を作らない。

### Noahで参加者が見るもの

Agentごとの名前・作者・版・短い映像を現在の共通詳細画面に載せる。その下に「どんな仕事を、誰が検収して、いつ入金するか」を置く。直近30日の実績（対象数、入金なしの月、費用控除後の額）、次の30日の予測幅、予測の最終更新日、入金確認日を別行で示す。証拠が欠ける欄は「未確認」。組み合わせの画面から各Agentと計算根拠まで戻れるようにする。

たとえば2体がそれぞれ月80件を処理できても、同じ顧客の需要が100件で、共通の検収担当が月60件までなら、組み合わせの上限は60件。単価1万円、検収合格率80%、当月の回収率90%なら見込み入金は43万2,000円。ここから実行・人件・共通費を引く。見込手取りの分位は、共有先停止や翌月への入金ずれを同時に効かせたシナリオごとに合算してから求める。各Agentの中央値を足して組み合わせの中央値とする計算は採用しない。

最初の予測のお題は「この組み合わせは来月末までに、照合済み入金で地域の箱を何箱賄えるか」。注文前に確保できる箱数と実際に届いた箱数は別のお題にする。締切、対象地域・期間、箱の原価と送料、取消・遅延時の扱い、判定担当と異議期限を公開する。証跡の到着が遅れたら判定を保留し、停止を売上ゼロとして価格や分配を自動更新しない。

## 月次の資金配分例

以下は300人到達後の会社運営Agentについて、ある月の実入金を仮定した比較。300人到達前の試行期間は本人への分配が0のため、同じ表を適用できない。

| 1か月の例 | 円 | 根拠/扱い |
| --- | ---: | --- |
| 顧客から実際に入った現金 | 600,000 | 4 Agentの検収済み成果合計。見積売上は含めない |
| 決済・実行・計算費 | -120,000 | この例の返金は0円。外部明細と照合した費用 |
| 開発者の現金対価 | -160,000 | 返金後売上60万円の20%で作者分12万円＋別途検収した開発費4万円。この月の開発費は表の営業現金から一度だけ支払う |
| 共通運営・税/紛争見込 | -130,000 | 未確定税額は分配せず保留 |
| 期間末余剰 | 190,000 | 600,000−120,000−160,000−130,000 |
| 現行の利用者側75% | -142,500 | 現行決定をそのまま当てた比較。ファンド持分ではない |
| 現行の会社側25% | -47,500 | 運営・次期予備。元本返還ではない |
| 差額 | 0 | 190,000−142,500−47,500 |

利用者側142,500円を300人で等分すると1人475円。たとえば品物350円＋配送125円で全額を使う例で、実際の仕入価格や送料は見積もりを取って決める。

この例に仮の資金提供者分配25,000円（拠出残高2,000,000円なら期間1.25%）を足すと差額はマイナス25,000円になる。会社側47,500円のうち25,000円を充てる案なら会社に残るのは22,500円。会社にその資金を使う権限と余力があるか、準備金が足りるか、契約・税務上認められるかを個別に確認する。別案は、ファンド専用案件の売上と費用を当初から分離し、独自の分配契約を結ぶこと。売上が増えても同じお金を二度配ることはできない。年率換算・保証もしない。下振れ（実入金300,000円、必要費350,000円）は分配0・新規稼働縮小・不足50,000円を記録し、期間前に確保済みの食料予算だけを履行する。上振れ（実入金900,000円）でもReceipt、税/返金予備、集中上限を再計算するまで増額しない。価格、受入率、容量、停止時間、相関、回収日、税務は全て不確実で、実績が少ないAgentには仮定付きの試算を示す。需要・単価・費用の根拠が欠けるときは金額を「算定不能」とする。

表示は「名目分配額」「実際に支払可能な現金」「未払/保留」「元本残高」を分ける。元本は預金ではなく損失で減る可能性があり、希望時に額面で償還できると約束しない。償還可能額は未使用現金から確定債務・解約費・返金予備を引いた額を上限とし、契約上の窓口・順序・停止条件をPhase 2前に定める。

### 現物分配の権利と履行

出資者に農産物で分配する場合は、対象期間・持分の基準日・評価単価の出典・送料負担・選択期限・欠品時の代替や繰越を契約に記す。確定分配額から本人が選んだ品物に相当する額を一度だけ引き当て、引渡し結果と現金残額を記録する。農家への仕入代金と投資家向け評価額は別項目。地域の定期便は別予算で、出資しない人も対象にできる。自治体と組む場合は対象者の確認、集荷・受取場所、欠配時の連絡担当を合意し、住所は発送に必要な担当者だけが扱う。

## Jev・セキュリティの合格条件

- Jevの合格条件: client指定の売上/費用/価格採用0、同一Receipt二重計上0、未検収成果の入金化0、Eve証明のない移行後Agentの候補化0、作者と評価者の自己承認0、予測による経済利益0、基礎食料の投資額/技量連動0、通貨間の無断換算0、未決定の再投資/token/二次注文0、各月の資金保存式差0円。
- 障害: mutationはidempotency key→commit→読戻し。銀行/Provider/Receiptの一つでも停止したら新規受入・再配分・出金をfail-closedにし、閲覧は最終確認時刻付き。RTO/RPOをpilot前に決め、復旧で再計算しても過去revisionを上書きしない。
- 操作: 関係者間の循環売上、架空検収、自己売買、複数アカウントでの予測操作、締切直前の成果定義変更、需要/容量水増し、単一顧客/Provider集中を検出し、関係Agentを隔離する。予測精度は作者報酬や基礎食料の条件にしない。
- 認証: WebAuthnのRP ID/origin/user verificationを固定し、高額操作・出金先/配送先変更は別challengeと二者承認。回復は既存credentialだけに依存させない。eSIM/電話番号/SMSは通信・回復の一要素に留め、SIM swapや回線移行だけで所有権・出金権・passkeyを移さない。

## 日本で実資金を扱う前の確認

他者から金銭等を集め、共同事業・投資を行い、その収益または財産を分配する権利は、呼称・法人/任意組合・法定通貨/農産物を問わず集団投資スキーム持分等の検討対象になり得る。事業型でも自己募集・運用・媒介、持分の電子化や二次注文は別の登録/届出・業規制を生み得るため、「ファンド」「少人数」「円以外」「物で返す」を適用除外の根拠にしない。Phase 2前に[金融庁のファンド関係申請](https://www.fsa.go.jp/common/shinsei/fund.html)、[集団投資スキーム持分に関する案内](https://www.fsa.go.jp/news/27/sonota/20151214-2.html)、[金融商品取引法](https://laws.e-gov.go.jp/law/323AC0000000025)を当事者・契約・勧誘方法に即して専門家確認する。資金移動/前払式・token等は[資金決済法](https://laws.e-gov.go.jp/law/421AC0000000059)、無料予測への景品等は[消費者庁 景品規制FAQ](https://www.caa.go.jp/policies/policy/representation/fair_labeling/faq/premium/introduction)も別途確認する。対価・勝敗・経済的利益を伴う予測は、[刑法](https://laws.e-gov.go.jp/law/140AC0000000045)の賭博関連規定も含め別途確認する。

認証の設計根拠は[W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)と[NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)。これらは金融商品の適法性を保証しない。法務レビューは技術受入、税務確認、農産物の表示/衛生/配送確認を代替しない。
