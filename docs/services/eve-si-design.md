## 要点

エージェントエンジニアリングを、「あるエージェントの出力を別のエージェントの入力につなぎ、最後に外から入金が起きる流れを作る技術」と定義します。eve.si は Eve そのものの名前で（2026-11-24 にノエルが決定）、お金になる組み合わせを見つけ、作り、試し、入金の記録で採点し、悪い工程だけを作り直します。この設計書では、その流れを、リポジトリで既に使っている言葉に合わせて「組み合わせ」と呼びます。

一番大事なのは「上手に組み合わせる」所です。eve.si は、先に「誰が何にいくら払っているか」（需要）を集め、そこから逆算して組み合わせを探します。既にある稼ぎ方の型 470 通りへの当てはめと、型の無い新しい組み合わせの発見の両方を、同じ物差し（見込みの利益）で比べます（6章）。

- 組み合わせは、Eve が自動でも作り、人も Eve を道具にして作ります。どちらで作っても同じファイルになり、同じ検査・試運転・採点を通ります（6章）。
- お金は 2 つの道から入ります。組み合わせを回して外から入る収入と、組み合わせを Noah で使ってもらって作者に入る収入です（8章）。
- つなぐ役は、Noa から Eve にまとめます（2026-11-24 にノエルが決定）。ただし、作った組み合わせの合格は Eve ではなく Jev が出します。自分で作った物を自分で合格にしないためです（4章・9章）。
- 手元で数えた結果、470 通りの設計図すべてが、「需要と競合を調べる」と「成果・売上を読む」の 2 つの能力で止まっています。前者は、6章の「需要の台帳」を作る能力そのものです。
- 「エージェントエンジニアリング」という言葉は、他社が別の意味で既に使っています。それでも名前はこのまま使い、1章の定義を公式にします（2026-11-24 にノエルが決定）。

## 1. 言葉の定義と、他社の同じ言葉との違い

ノエルの意味のエージェントエンジニアリングは、エージェント同士の「つなぎ目」と「お金の出口」を設計する技術です。他社の同じ言葉は、1 つのエージェントを良くする話か、コードを書く作り方の話で、お金の出口は扱っていません。ノエルの決定（2026-11-24）で、名前はこのまま使い、この章の定義を公式にします。

| 言葉 | 誰が・いつ | 意味 | ノエルの意味との違い |
| --- | --- | --- | --- |
| Agent engineering | [LangChain](https://www.langchain.com/blog/agent-engineering-a-new-discipline)、2025-12-09 | 予測しきれない LLM の仕組みを、作る・試す・出す・観察する・直す、を繰り返して本番で信頼できる物にする | 1 つのエージェントの質を上げる話。つなぎ方とお金は扱わない |
| Agentic engineering | Andrej Karpathy、2026 年の初め（[IBM の説明](https://www.ibm.com/jp-ja/think/topics/agentic-engineering)） | ソフトウェア開発で、技術の知識を使って AI エージェントの作業を監督する | コードを書く作り方の話 |
| エージェントエンジニアリング（この設計書） | ノエル、2026-11-24 | エージェントの出力を次のエージェントの入力につなぎ、最後に外部の入金の記録が出る流れを作る | — |

この設計書では、次の 3 つを全部満たす物だけを「組み合わせ」と呼びます。

1. 2 つ以上のエージェント（または道具）を、出力と入力でつないでいる。
2. 最後の工程が、外部の記録を読む。外部の記録とは、ASP の承認、売り場の売上、入金です。クリック数や本人の申告は、入金に数えません（[noah-revenue-combinations.md](https://github.com/iceiceice999/rock/blob/main/docs/services/noah-revenue-combinations.md) の「クリックや利用者の自己申告を承認報酬へ昇格する件数0件」と同じ決まりです）。
3. 組み合わせ全体を、入金と費用で採点できる。

## 2. 理念から考える：エージェントエンジニアリングが当たり前の世界

eve.si が担うのは、下の表の 1〜6 です。7〜9 は Noah・Wallet・別の事業の仕事なので、eve.si はそこへ記録を渡すだけにします。ノエルの以前の指示「機能を細かく考える前に、理念から達成したい世界線にどんなサービスがあるかを描き、理念と機能を比べる」に合わせて、先に世界を描きました。

元にした理念は 3 つです。

- 「みんなが Agent を使って、生活がより豊かになる。」（[00-overview.md](https://github.com/iceiceice999/rock/blob/main/docs/structure/00-overview.md) の 0 章）
- かいやさんというペルソナの言葉「めんどくさい、好きなこと以外やりたくない」
- 仕事がある人は、自分の価値を出せる部分だけをやる。仕事がない人も、とりあえず使えば稼げる。

| --- | --- | --- | --- |

| 9. 計算する場所を選べる | 安い場所・秘密を守れる場所で動く | 黒殿の GPU、`lib/sky-device-tiers.ts` | 担わない。実行先は Noa が選ぶ |

## 4. eve.si の全体像

> 図: eve.si の流れ · 需要の台帳、作る人 2 通り、門 5 つ、作り直しと見込みの直し（図は [原本の設計書](https://claude.ai/artifact/AXJsY82uAvjM9TKra8Evvg) にだけあります）

作る人は 2 通り（Eve の自動と、Eve を道具に使う人）で、どちらも需要の台帳から始め、同じ組み合わせファイルを作ります。そのファイルが、検査 → 試運転 → 本番 → 外部の記録 → 採点の順に通り、採点で悪かった工程だけを作り直して新しい版にします。採点の結果は、需要の台帳の「売れる見込み」にも戻します。つなぐ役は Noa から Eve にまとめ、工程は AMC、合格の判定は Jev、お金と公開の門は Broker と Wallet が持ちます。eve.si は Eve そのものの名前なので、外から見える名前は Eve（eve.si）の 1 つです。

## 5. 組み合わせファイルの形（eve-combination/1）

組み合わせは、JSON の 1 ファイルです。工程の形は今の `NoahStep`（`lib/noah-steps.ts`）をそのまま使い、そこへ「どのエージェントのどの道具を使うか」「工程の合格の確かめ方」「お金の出口」を足します。下は、勉強ノートを note で売る組み合わせの例です（エージェントの id は書き方の例です）。

```json
{
  "schema": "eve-combination/1",
  "id": "cmb-note-study",
  "version": 3,
  "title": "勉強ノートを note で売る",
  "blueprint": "稼ぎ方の設計図の id（無い時は null）",
  "origin": "template",
  "demand": { "id": "需要の台帳の id", "expectedPriceYen": 500 },
  "author": { "kind": "person", "id": "noellesugar99" },
  "keepForSelf": ["topic"],
  "budget": { "perRunYen": 300, "trialYen": 3000 },
  "steps": [
    { "id": "s1", "label": "需要と競合を調べる", "kind": "auto", "capability": "research.market", "after": [],
      "flow": { "inputs": ["topic"], "outputs": ["demand-report"] },
      "agent": { "ref": "noah:agent-id@版のhash", "tool": "search", "args": { "query": "{topic}" } },
      "fallback": ["noah:別のagent-id@版のhash"],
      "accept": { "type": "json", "required": ["keywords", "competitors"], "minItems": 5 } },
    { "id": "s2", "label": "つなぎ目の変換", "kind": "auto", "capability": "glue.convert", "after": ["s1"],
      "flow": { "inputs": ["demand-report"], "outputs": ["article-brief"], "dataFrom": [{ "from": "s1", "material": "demand-report" }] },
      "code": "glue/s2.ts", "tests": "glue/s2.test.ts" },
    { "id": "s3", "label": "記事を書く", "kind": "auto", "capability": "content.article", "after": ["s2"] },
    { "id": "s4", "label": "note で公開する", "kind": "tap", "reason": "公開は本人が確かめて押す", "account": "note", "after": ["s3"] },
    { "id": "s5", "label": "売上を読む", "kind": "auto", "capability": "tracking.results", "after": ["s4"] },
    { "id": "s6", "label": "入金を確かめる", "kind": "human", "reason": "口座は本人しか見られない", "after": ["s5"] }
  ],
  "exit": { "material": "payout-confirmed", "source": "note の売上管理と銀行の入金", "counts": "approved-or-paid" }
}
```

| 項目 | 意味 | 元にした既存の物 |
| --- | --- | --- |
| `id`・`version` | 組み合わせの名前と版。直す時は新しい版を作り、元の版は書き換えない | Eve のビルド「原本は変えない」 |
| `blueprint` | どの稼ぎ方の型か。新しく発見した組み合わせは null | `NoahBlueprint.id` |
| `origin` | `template`（型への当てはめ）か `discovered`（新しい発見）か | 6章 |
| `demand` | 狙う需要（需要の台帳の id）と、見込みの単価 | 6章 |
| `author` | `eve`（Eve が自動で作った）か `person`（人が作った）か。人の場合は作者の id も持つ | 6章 |
| `keepForSelf` | 本人が自分でやりたい工程。自動にしない | `RecipeGoal.keepForSelf` |
| `budget` | 1 回の上限と、試す期間の上限 | `noahBusinessCanSpend` |
| `steps[]` | 工程。種類（auto・tap・human・review）、能力、待つ工程、受け渡す素材 | `NoahStep` |
| `steps[].agent` | Noah のエージェントの id と版の hash、道具の名前、入力の作り方 | Noah の接続（L5・L6） |
| `steps[].fallback` | 差し替えの候補 | 新しく足す |
| `steps[].accept` | 工程の合格条件。Jev が機械で判定できる形（種類・項目・数・長さ） | 04 章の「合格条件が書けないサービスは作らない」 |
| `code`・`tests` | つなぎ目の変換のコードと、その固定テスト | Eve のビルド R5 |
| `exit` | お金の出口。必須。外部の記録だけを数える | 1章の 3 つの条件 |

### つなぎ目の変換が、エージェントエンジニアリングの中心

エージェント同士の出力と入力は、ほとんどそのままでは合いません。たとえば調査のエージェントは表を返し、記事のエージェントは指示文を受け取ります。この間を埋める小さな変換が「つなぎ目の変換」です。変換は、決まった操作（取り出す・定数・文の型・先頭から取る・項目の付け替え・つなぐ・数にする・数える）を並べる宣言型（eve-glue/1）にし、必ず固定テストを持たせます。コードを動かさないので外へ通信できず、Workers と Node で同じ結果になります。変換は手でも書けますし、Eve が LLM で書いてもかまいません。どちらも固定テストに通った物だけを使います。

### 検査の規則（すべて決まった式。LLM は使わない）

1. 工程の順番と受け渡しが合っている（`noahBlueprintWaitProblem` が問題なしを返す）。
2. どの素材も、手元にある物か、前の工程が出した物である。同じ素材を 2 回出さない。成果に使われない工程が無い（棚の `chain` の規則と同じ）。
3. 最後の工程が `exit` の素材を出し、`exit` の元が外部の記録である。
4. auto の工程は、能力を「確かめた」エージェントか、固定テスト付きのつなぎ目の変換だけを使う。確かめていない物がある組み合わせは、試運転だけができる。
5. tap・human・review の工程は、理由を持つ。登録の工程の前に「規約と登録の要件を確かめる」がある（spec-122 と同じ）。
6. 金融の分野は、ノエルが確かめる review の工程を持つ。
7. 費用の合計が `budget` の内側にある。
8. どの `agent` にも版の hash がある。相手の版が変わったら、黙って新しい相手へ送らず、止めて知らせる（L5 と同じ）。
9. 鍵・パスワード・口座の番号をファイルに書かない。要る鍵は、接続要件の `services` で名前だけを指す（Eve のビルド R3）。

## 6. 上手に組み合わせる：お金になる組み合わせの見つけ方

eve.si は、先に「誰が何にいくら払っているか」を集め、そこから逆算して組み合わせを探します。費用が安いだけの組み合わせは選びません。買う人がいて、費用を引いても利益が残る組み合わせを、上から並べます。

### 需要の台帳

需要とは、「ある成果に、誰かがお金を払っている」という事実です。1 件ごとに、次の項目を出典付きで持ちます。確かめていない物は入れません（spec-122 の「確かめた物だけを出典付きで持つ」と同じ決まりです）。

| 項目 | 意味 | 例 |
| --- | --- | --- |
| 成果の型 | 買われる物の型。素材の型と同じ名前の決まりで書く | `lp-site`、`vertical-video-15s`、`translation-ja-en` |
| 払う人と場所 | どこで、誰が払うか | ココナラの依頼者、A8.net の広告主、BOOTH の買い手 |
| 単価 | 1 件あたりの円 | 募集の予算、ASP の成果報酬、売り場の価格 |
| 量 | 1 週間あたりの件数 | 募集の数、ランキングの動き |
| 競合 | 同じ物を出している数 | 出品の数、応募の数 |
| 出典と日付 | どこで確かめたか | URL と確かめた日 |

集める元は、リポジトリで既に読んでいる物から始めます。受注の募集（`lib/sky-gig-desk.ts`・`lib/sky-gig-offers.ts`）、ASP の案件と条件（`toolkits/noah-affiliate-agents`）、売り場の公開価格の 3 つです。X などで見つけた紹介（`data/noah-scout/leads.json`）は、使えるエージェントの候補（供給）で、需要ではありません。誰もお金を払っていないので、台帳には入れません（2026-11-24 に実装で分けました）。売り場のランキングと検索の需要は、規約が許す公式の口で後から足します。3章で 470 通りすべてを止めていた「需要と競合を調べる」能力は、この台帳を作る能力のことです。

### 組み合わせの地図

素材の型を点に、エージェントを「素材 A から素材 B を作る矢印」に、需要を「この素材をこの値段で買う人がいる」という終点にして、1 枚の地図にします。組み合わせは、手元にある素材から需要の終点までの道です。

- **型への当てはめ：** 稼ぎ方の設計図 470 通りは、既に確かめた道の型です。各工程に、地図の中で一番良い矢印（エージェント）を当てはめます。
- **新しい組み合わせの発見：** 型の無い道を探します。探し方は 2 つです。
  1. 需要から逆算する。終点の成果を作れる矢印を探し、その入力を作れる矢印を探し、と手元の素材に届くまでさかのぼります。
  2. エージェントから順に広げる。あるエージェントの出力を入力にできる別のエージェントを探し、その先に需要の終点があるかを見ます。「A と B はつながる」という発見は、ここから出ます。
- 発見した道が型と同じなら、型の組み合わせとして扱います。型に無い道だけを「新しい組み合わせ」と呼び、設計図の候補として本人か作る人に見せます。

### 見込みの利益で並べる

型への当てはめも、新しい組み合わせも、同じ式で並べます。

```latex
\text{見込みの利益（1 回）} = \text{売れる見込み} \times \text{単価} - \text{実費} - \text{本人の手間の値段}
```

- 売れる見込みは、実績が無い間は、需要の台帳の量と競合から控えめに置きます。実績が 5 回以上たまったら、実際の割合 `(売れた数 + 1) ÷ (出した数 + 2)` に置き換えます（棚の並びと同じ控えめな見積りです）。
- 本人の手間の値段は、今の選択器の `ownerMinuteValueMinor` をそのまま使います。本人が自分でやりたい工程（`keepForSelf`）は、手間に数えません。
- 試す予算の中でだけ、5 回に 1 回は実績の少ない組み合わせを試します（`RECIPE_TRIAL_INTERVAL`）。新しい組み合わせが、ずっと試されないままになるのを防ぐためです。
- 学習したモデルは使いません。並びは、数えた実績と決まった式だけで作ります（2026-11-21 の決定「アルゴリズムに機械学習は要らない」と同じです）。

### 作る人と作り方

エージェントエンジニアリングは、Eve が自動でもやり、人も Eve を道具にしてやります（2026-11-24 にノエルが決定）。どちらで作っても同じ組み合わせファイルになり、同じ検査・試運転・採点を通ります。

| 作る人 | 何をするか | 向く時 |
| --- | --- | --- |
| Eve（自動） | 需要の台帳から、見込みの利益が高い道を探して組み合わせを作る。足りない部品とつなぎ目の変換は LLM で作り、試験に通った物だけを使う | いつも。会社で回す組み合わせの大半 |
| 人（Eve を道具に使う） | 地図と見込みの利益を見ながら、自分の知っている需要や好みで組み合わせを作る。手で書く（JSON か TypeScript の `defineCombination()`）か、Eve に一文で頼む | 台帳に無い需要を知っている時。金融のように規約が細かい時 |

「自分でコードを入れるか、エージェントか」は、組み合わせを作る時の話だと、ノエルの回答（2026-11-24）で決まりました。上の表のとおり、両方使えます。勧める順番は、手で書いた数本で検査と試運転の門を固め、次に Eve の自動の探索、最後に Eve が LLM で部品を作る、です。手で書いた数本が、正しい見本と試験の材料になるからです。Eve の LLM は手元の Qwen を使い、外部の有料モデルへは、本人の許可までは切り替えません（Eve のビルドの決まり）。

## 7. 試す・採点する・作り直す

組み合わせは、試運転 → 小さく本番 → 採点 → 一番悪い工程だけを作り直す、の輪で育てます。どの段でも元の版を残し、外の記録だけを数えます。

> 図: 作り直しの輪 · 7 つの歩み、1 つの判断（図は [原本の設計書](https://claude.ai/artifact/AXJsY82uAvjM9TKra8Evvg) にだけあります）

### 試運転（外へ出さない）

見本の入力で、全部の工程を動かします。公開・送信・申込・課金の工程は実行せず、「送る予定の中身」を見せて止めます。各工程の `accept` を Jev が判定し、落ちた工程と理由を出します。費用は、実際に使ったモデルと道具の実費だけを数え、上限は `budget.perRunYen` です。

### 小さく本番

spec-122 の 7 章の数をそのまま使います。試す期間は 14 日、出した物は 10 件です。承認された収益が費用の 2 倍以上なら増やします。承認が 1 件以上か、クリックが 50 以上なら続けます。期間と件数を過ぎ、クリックが 20 未満で承認が 0 なら止めます。それ以外は待ちます。

### 採点

段ごとの数を数えます。作った → 出した → 見られた → 押された → 申し込まれた → 承認された → 入金された、の 7 段です。そのうえで、組み合わせ全体を次の 2 つで採点します。

```latex
\text{1 日あたりの利益} = \frac{\text{承認・確定した額} - \text{使った額}}{\text{動かした日数}}
```

```latex
\text{費用 1 円あたりの承認額} = \frac{\text{承認・確定した額}}{\text{使った額}}
```

回した後の実績は、6章の「売れる見込み」に戻します。需要の台帳の見込みは、実績が 5 回以上たまった組み合わせから、実際の割合に置き換わります。こうして、型への当てはめも新しい発見も、同じ入金の記録で育ちます。

### どこが悪いかを見つける

- Jev の判定で落ちた工程があれば、その工程が悪い所です。
- 判定は通るのに数が落ちる段があれば、その段の前の工程が悪い所です。たとえば「見られた → 押された」で落ちるなら、記事・台本・画像の工程を疑います。
- 比べる相手は、同じ設計図の他の組み合わせの率です。実績が 5 本以上ある時だけ使います（棚の並びの「5 人未満の実績は使わない」と同じ）。無い間は、前の版の自分の率と比べます。

### 作り直す

1. 一番数が落ちている段の工程だけを選びます。
2. 候補を、`fallback` → 同じ能力の確かめたエージェント → Eve が作る部品、の順に探します。
3. 新しい版を作り、試運転で前の版と比べます。元の版は残します。
4. 見込みが 20% 以上良い時だけ、作り直しを提案します（`RECIPE_SWITCH_MARGIN`）。
5. 5 回続けて合格した工程は固定し、毎回の作り直しから外します（`RECIPE_FREEZE_STREAK`）。試す予算の中でだけ、5 回に 1 回は実績の少ない候補を試します（`RECIPE_TRIAL_INTERVAL`）。
6. 相手のサーバーが止まった時や版が変わった時は、接続の巡回（L7）で見つけ、同じ手順で差し替えます。

## 8. お金の流れ

eve.si は、送金も課金もしません。お金を動かすのは、今までどおり Wallet・Broker・本人です。eve.si は、組み合わせごとに「使った額」と「外部で確定した額」を記録し、採点と分け方の計算に渡すだけです。

### 1 つ目の道：組み合わせを回して稼ぐ

2026-11-22 のノエルの回答どおり、会社（avocado）が回し、収益の名義は当面ノエル個人です。使ってよい額は、今の式 `noahBusinessAllowance` をそのまま使います。

```latex
\text{使ってよい額} = \text{最初の 10,000 円} + \text{承認・確定した収益} - \text{使った額} - \text{押さえた額}
```

組み合わせごとに試す期間の上限（`budget.trialYen`。既定案 3,000 円）を置き、全部の組み合わせの合計が、この額を超えないようにします。発生しただけ・承認前の収益は数えません。

### 2 つ目の道：組み合わせを使ってもらって稼ぐ

組み合わせを Noah に載せ、他の人が使って稼ぐと、作者にもお金が入ります（2026-11-24 にノエルが決定：お金の元は両方）。分け方は、2026-11-22 の決定「Agent の利益のうち本人の分は定期便で渡し、残りは Agent を作った人の収益と運営の分」に合わせます。

| 受け取る人 | 何に対して | 既定案 |
| --- | --- | --- |
| 使った人 | 組み合わせが自分の名義で稼いだ収益 | 外から本人へ直接入る。eve.si は触らない |
| 組み合わせの作者（人でも Eve でも） | 使った人の、外部の記録で確定した収益 | 確定した収益の一部（割合は未決。13章）。Eve が作った組み合わせの分は運営に入る |
| 部品の作者 | 組み合わせの中で、自分のエージェントが使われた時 | 有料の部品は、使った回数で受け取る（今の従量の決まり）。組み合わせの作者の分からは分けない |
| 運営 | 実費と運営 | 実費への上乗せ（今の料率）。利用者から月額は取らない（2026-11-22） |
| 定期便の受取人 | 月の余剰 | 分配率は未決。既定は 0 |

数えるのは、外部の記録で確定した収益だけです。本人の申告やクリックでは、作者への支払いは起きません。

## 9. 守る決まり

どの作り方で作った組み合わせも、次の決まりを破る工程を持てません。検査（5章）か、運転の門（Broker・Wallet）で止めます。

1. **画面をジャックしない。** ノエルの言葉「agent を動かす時に、画面がジャックされるのは絶対にダメ」（2026-11-20）。組み合わせは自社のクラウドか専用の端末で動かし、他人が作ったエージェントは画面と入力装置の無い端末でだけ動かします。
2. **人にしかできない工程は本人がやる。** パスワード・確認コード・本人確認・口座・電話番号・規約への同意は、human か tap の工程にします。eve.si はこれらを入力しません。
3. **SNS は規約が許す公式の口だけを使う。** 大量の自動投稿と、複数アカウントの使い分けはしません（spec-122 の 6 章）。TikTok の公開は tap です。
4. **売り場の規約を工程に入れる。** たとえばココナラは、アカウントの利用が個人に限られ、複数アカウントが禁止され、自動応答ソフトに制限があります（規約 13-2-22。2026-11-19 に確かめた内容）。登録の工程の前に、毎回「規約と登録の要件を確かめる」を置きます。
5. **金融の表現はノエルが確かめる。** FX などの紹介には、金融商品取引法の広告の決まりと、景品表示法のステマ規制がかかります。金融の分野の組み合わせは、公開の前に review の工程を必ず持ちます。
6. **送金・課金・契約の申込をしない。** eve.si は Broker と Wallet を飛ばしません（AGENTS.md 7 章）。
7. **他人のエージェントは、ライセンスが許す時だけ包む・直す。** 元の版は書き換えません。
8. **自動でつなぐのは、条件を全部満たす物だけ。** 条件は task 80 と同じです。無料であること、権限が入力の読み取りと成果の保存だけであること、接続試験に通っていること、動く所が専用の端末であること。
9. **相手のサーバーへ入力を送る物は、最初の 1 回だけ本人に聞く。** 送り先を見せてから聞きます。
10. **「必ず稼げる」と言わない。** spec-122 の「マネタイズ絶対は約束できない」と同じです。画面にも広告文にも、約束する金額を書きません。
11. **証拠の無い「完了」「収益」「公開」を書かない。** 外部の記録が無い入金は、成績表に出しません（AGENTS.md 5 章）。

つなぐ役を Eve にまとめ、需要の台帳を足したので、次の 2 つの決まりも足します（2026-11-24）。

- **作った組み合わせを、作った者が合格にしない。** 組み合わせを作るのは Eve か人ですが、合格は必ず Jev が出します。Eve が作った組み合わせを Eve が合格にした数は 0 にします。
- **需要の台帳は、規約が許す公式の口と、公開された情報だけで作る。** 出典と確かめた日の無い需要は使いません。売り場や SNS の規約が自動の読み取りを禁じている所は、読みません。

## 10. 画面（スマホが先）

画面は、幅 390 px のスマホで全部できるように作ります。2026-11-20 のノエルの指示「PC の前に座ることを前提にしない」に合わせます。作る前に、リポジトリの `design/references/README.md` と関係する参照画像を見ます（AGENTS.md 9 章）。

1. **入口「何で稼ぐ？」** 入り方は 2 つです。稼ぎ方の一覧から選ぶ（並びは spec-122 の点数）か、一文で Eve に頼む欄に書くかです。
2. **組み合わせの図。** 工程を縦に 1 列で並べます。横に長い図は、スマホでは読めないからです。工程のカードには、エージェントの名前、工程の種類（auto・tap・human・review）を表す色、「確かめ済み」かどうかを出します。部品が無い工程には「Eve が作る」の印を出します。2026-11-22 のノエルの意見「工程の図は、ピンの画像には分かりにくすぎる。ピンを押した先の説明画面に置く」に合わせ、この図は詳細の画面にだけ置きます。
3. **試運転の結果。** 工程ごとに、成果の見本、合格か不合格か、かかった秒数と円を出します。
4. **本人の番。** tap・human・review の工程の待ち一覧です。何を、なぜ、どこで押すかを 1 行ずつ出します（spec-122 の 6 章と同じ）。押すと、その工程を待っていた工程が動き出します。
5. **成績表。** 段ごとの数（作った → 出した → 見られた → 押された → 申し込まれた → 承認された → 入金された）、費用、承認額、一番数が落ちている段を出します。
6. **作り直しの提案。** 差し替える前と後の違い、見込み、試運転の結果を出し、「採用」と「やめる」のボタンを置きます。採用しても、元の版は残ります。

需要から探す形にしたので、次の 3 つの画面を足します（2026-11-24）。

- **需要の地図。** 成果の型ごとに、単価・量・競合・出典を出します。作る人は、ここから「何を作れば売れるか」を見ます。
- **発見の候補。** 型に無い新しい組み合わせと、その見込みの利益を出します。本人か作る人が「試す」を押すと、試運転に進みます。
- **作る人の成績。** 作った組み合わせが使われた数と、外部の記録で確定した収益のうち作者に入った額を出します。
