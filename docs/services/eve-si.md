## お金になる組み合わせの見つけ方

1. **需要の台帳。** 「ある成果に、誰かがお金を払っている」事実を、出典付きで集める。確かめていない物は入れない。spec-122 で 470 通りすべてを止めていた能力「需要と競合を調べる」は、この台帳を作る能力のこと。
2. **組み合わせの地図。** 素材の型を点、エージェントを「素材 A から素材 B を作る矢印」、需要を「この素材をこの値段で買う人がいる」終点にする。組み合わせは、手元の素材から需要の終点までの道。
3. **型への当てはめ。** 設計図 470 通りの各工程に、地図の中で一番良い矢印を当てはめる。
4. **新しい組み合わせの発見。** 需要から逆算する（終点を作れる矢印 → その入力を作れる矢印 → 手元の素材まで）か、エージェントから順に広げる（A の出力を入力にできる B → その先に需要の終点があるか）。型に無い道だけを「新しい組み合わせ」と呼び、本人か作る人に見せる。
5. **見込みの利益で並べる。** 見込みの利益（1 回）＝ 売れる見込み × 単価 − 実費 − 本人の手間の値段。売れる見込みは、実績が無い間は台帳の量と競合から控えめに置き、実績が 5 回以上たまったら `(売れた数 + 1) ÷ (出した数 + 2)` に置き換える。試す予算の中でだけ、5 回に 1 回は実績の少ない組み合わせを試す（`RECIPE_TRIAL_INTERVAL`）。学習したモデルは使わない（2026-11-21 の決定）。

## 組み合わせファイル（eve-combination/1）

工程は `NoahStep` をそのまま使い、次を足す。`origin`（`template` か `discovered`）、`demand`（需要の台帳の id と見込みの単価）、`author`（`eve` か `person`。人なら作者の id）、`agent`（Noah のエージェントの id と版の hash、道具の名前、入力の作り方）、`fallback`（差し替えの候補）、`accept`（Jev が機械で判定できる工程の合格条件）、`code`・`tests`（つなぎ目の変換）、`exit`（お金の出口。必須。外部の記録だけを数える）、`budget`、`keepForSelf`。直す時は新しい版を作る。

### 検査の規則（決まった式。LLM は使わない）

1. `noahBlueprintWaitProblem` が問題なしを返す。
2. どの素材も、手元にある物か前の工程の出力。同じ素材を 2 回出さない。成果に使われない工程が無い（棚の `chain` の規則と同じ）。
3. 最後の工程が `exit` の素材を出し、`exit` の元が外部の記録。`demand` が出典付きの需要を指す。
4. auto の工程は、能力を確かめたエージェントか、固定テスト付きのつなぎ目の変換だけ。確かめていない物がある組み合わせは、試運転だけができる。
5. tap・human・review の工程は理由を持つ。登録の工程の前に「規約と登録の要件を確かめる」がある。
6. 金融の分野は、ノエルが確かめる review の工程を持つ。
7. 費用の合計が `budget` の内側。
8. どの `agent` にも版の hash がある。
9. 鍵・パスワード・口座の番号を書かない。要る鍵は接続要件の `services` で名前だけを指す。

## 作る人と作り方

Eve（自動）は、需要の台帳から見込みの利益が高い道を探して組み合わせを作り、足りない部品とつなぎ目の変換は LLM で作って試験に通った物だけを使う。人は、需要の地図と見込みの利益を見ながら、手で書く（JSON か TypeScript の `defineCombination()`）か Eve に一文で頼む。どちらも同じファイルになり、同じ検査・試運転・採点を通る。順番は、手で書いた数本で門を固める → Eve の自動の探索 → Eve が LLM で部品を作る。LLM は、本人の許可までは手元の Qwen（外部の有料モデルへ自動で切り替えない）。

## マイAgentで開く仕事の収益明細

収益運用者は「マイAgent → 保存した成果」から仕事を選び、成果承認・入金・費用を別々に確認する。資料作成の依頼者や広告の紹介先には、運営者の報酬を表示しない。

記録のない金額は未確認として扱う。署名を確認した提供元の記録を仕事・運用者・組み合わせの版に結び付け、入金とその仕事の最終費用がそろった時に、正の差額の20%を作者分として円未満切り捨てで計算する。作者と利用者が同一なら分配対象外とし、本人関係を確認できなければ保留する。画面の再表示は読取のみ。

### 提供元との接続

1. 運営者が対象の系列・HTTPSの実行先・道具名・組み合わせIDを確認し、サーバー専用の `NOAH_REVENUE_PROVIDER_TARGET` に `{familyKey, endpoint, tool, combinationId}` を設定する。証憑を照合する提供元の識別子と専用の共有鍵（32文字以上）を `NOAH_REVENUE_PROVIDER_ID` と `NOAH_REVENUE_PROVIDER_SECRET` に設定する。
2. 作者のIDと認証済みアカウントの対応は `NOAH_REVENUE_AUTHOR_OWNERS` に保存する。各仕事の受取人の照合には `NOAH_REVENUE_OPERATOR_ACCOUNTS` の「認証済み利用者ID → 提供元の運用者ID」が必要。1つの運用者IDを複数の利用者には割り当てない。いずれもサーバー側のJSONオブジェクトで管理する。
3. 通常のMCP実行では、対象の道具に限り `tools/call` の `params._meta["avoado.si/revenue-work"]` で `workId, combinationId, version, dispatchProof` が渡る。Gradioでは同じ値を `X-Noah-Revenue-Work`、`-Combination`、`-Version`、`-Proof` ヘッダーで渡す。提供元は受けた仕事と実行記録の対応を保ち、提供元自身が照合できた明細だけを送る。
4. 提供元は `POST /api/noah/revenue/receipts` にJSONを送る。共通項目は `schema: "noah-revenue-receipt/1"`、`providerId, workId, combinationId, version, stage, source, currency: "JPY", amountYen, observedAt, reference, evidenceSha256`。日時はUnixミリ秒、金額は円整数、参照とSHA-256はその仕事に帰属する明細に対応する。全件で提供元が確認した受取人の `operatorRef` を添え、通常実行ではさらに `dispatchProof` を添える。実行当時に組み合わせと版を保存していない仕事には、自動では帰属させない。
5. `avocado-provider-signature` は `t=<Unix秒>,v1=<16進HMAC-SHA256>`。署名対象は `<Unix秒>.<生のJSON本文>`、許容時間差は5分。再送時は同じ明細参照、観測日時、金額、ハッシュを保持する。201は新規、200は記録済みを示す。409は元の仕事の完了状態・版・明細の重複を照合する。

| 段階 | 証憑の種類 | 金額の意味 |
| --- | --- | --- |
| `approved` | `asp-approval` | その仕事に帰属すると承認された報酬。承認だけでは作者分は未確定 |
| `paid` | `bank-deposit` | その仕事への実入金を確認した明細。複数の入金は合計 |
| `cost` | `final-work-cost` | その仕事の全費用がそろったときの合計。実費0円は明示的に受理 |

提供元の連携前でも本人は仕事の収益記録を開ける。確定には実際の入金と最終費用の明細が必要で、証憑の書き込みによる送金は発生しない。
