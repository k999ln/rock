# RockstarOS — 製品目的から逆算した開発軸

状態: 利用者が2026-09-15から2026-09-16に明示した製品目的の正本補助資料。**製品の中核は、高性能で交換可能なローカルLLMとoffline agent runtimeを備えたAIネイティブOS**である。Sky、Zema、便利さを増やすシステム、Wallet、ファンド、IP／動画、ゲーム、VRは、その中核を実用化・検証・拡張する接続システムとして扱う。

## 1. 最上位目的

RockstarOSの目的は、**一人ひとりが自分専用のAI自動化チームを所有し、そのチームの効率を継続的に改善することで、仕事と生活を便利にし、検証可能な収益機会を増やし、利用者全体がより豊かになれる基盤を作ること**である。

この社会的目的に対する**製品上の中心**はRockstarOSであり、一般的なスマートフォン機能の集合ではない。OSが、端末内LLM、agentの記憶・仕事・権限・停止・再開、Tool実行、receipt、更新、復旧を共通基盤として保証する。その上でSky、Zema、生活や仕事を便利にする自動化、興味のあるゲームやIP／動画／VRを接続し、実際の利用から共通Coreを改善する。

長期像は、利用者がSkyで自動化Tool群またはファンドを選ぶだけで、Zemaと端末内LLMが役割分担、実行、再試行、確認、成果保存を進め、外部接続が必要な時だけ仕事取得、納品、収益確認、Wallet照合を行う状態である。改善の到達指標として月50万円規模の検証済み収益を目指すが、全利用者の収入、将来利回り、達成時期を保証する表示には使わない。

## 2. 製品中核と接続システム

- RockstarOSは製品の中核である。ただし、OSを作る行為自体を社会的目的と取り違えない。価値は、高性能な端末内LLMとagentが通信断でも安全に働き、利用者が選んだシステムへ成果をつなげられることで生まれる。
- LLMはOSへ固定して交換不能にしない。共通の権限、記憶、仕事、Tool、receipt、更新契約の内側で、端末性能や用途に応じてmodelとruntimeを更新できるようにする。
- SkyはTool・ファンド・接続先を選ぶ第一者システム、ZemaはAIチームへの依頼、役割、進捗、確認、停止、成果を扱う第一者システムとする。この2つを最初の実用経路としてCoreを検証する。
- 仕事や生活を便利にする自動化を継続的に追加する。個別機能をOS imageへ直書きせず、署名・権限・版・停止・receiptを持つ更新可能なTool／Providerとして接続する。
- ゲーム、IP／動画生成、VRは利用者の関心に基づく優先的な応用開発系統とする。ただし特定ゲームや生成サービスをOS起動の必須依存にはせず、公式API、権利、利用条件、経済境界を確認したadapterとして接続する。
- Pixelは最初のreference hardwareであり、スマートフォン市場やiPhoneとカメラ、電話、一般アプリ数で競争するための製品ではない。カメラ品質は1.0の完成条件に含めない。
- 将来の専用端末は、購入後に初期設定済みのAI自動化チームをすぐ使える配布形態である。Pixelで価値と安全性を実証する前に独自端末開発を始めない。
- Walletは収益、費用、留保、払出し、税務資料の根拠を追える照合層であり、目的ではない。
- Googleサービス、カメラ、一般向けブラウザ、ATMはCore成立の前提にしない。必要になった時だけ独立systemとして追加する。

## 3. 目的からの逆算

```text
世界中の利用者が便利になり、より豊かになる
  ├─ Sky／Zemaと社会に役立つ自動化が仕事・生活を改善する
  ├─ Game／IP／動画／VRが新しい体験と経済圏へ広げる
  └─ 検証可能で持続可能な収益機会が増える
      └─ 各systemの成果・費用・失敗・収益が正確に測れる
          └─ 交換可能な端末内LLMとagentが通信断でも判断・処理・再開する
              └─ AIネイティブOS Coreが権限、記憶、仕事、receipt、更新、復旧を保証する
```

優先順位はこの下段から積み上げる。外観、カメラ、アプリ数、端末独自開発を先に増やして、上段の収益loopを未接続のままにしない。

## 4. 二層の実行方式

### 端末内で通信なしに継続する層

- LLM推論、仕事分解、Tool選択、ローカルデータ処理、成果物生成
- 許可済みschedule、再試行、停止、確認待ち、履歴、暗号化保存
- ファンド構成の評価と次の行動提案
- 未送信の仕事、成果、receipt要求を重複しないqueueとして保持

### 接続時だけ同期する層

- 新しい外部案件、価格、市場情報、Provider状態の取得
- 外部サービス操作、納品、請求、入金・払出し確認
- 署名済みEarning Receiptの取得とWallet照合
- 利用者が同意した改善データ、更新、失効情報の送受信

永久に通信しない端末は外部案件の取得、納品、入金確認ができない。そのため「offline-first」は、通信がなくても安全に仕事を進め、接続復帰後に同じ仕事を二重実行せず同期できることと定義する。

## 5. 1.0で証明する最小loop

技術上の層別責任・契約と合格条件は[AIネイティブOS共通設計](ai-native-os-architecture.md)を参照する。下記1〜4と8がCoreの最小loop、5〜7は外部作用・実収益を扱う応用の受入である。Core合格を収益利用可能や製品全応用完成と呼ばず、実収益公開前には外部Provider gateを満たす。Game/IPの非金融体験はこの収益経路と並行して進める。

1. 所有PixelでRockstarOSが起動し、端末内LLMが機内モードで動く。
2. Skyで一つの実用Toolまたは最小Tool構成を選ぶ。
3. Zemaが依頼を分解し、入力確認、実行、進捗、本人確認、結果を一つの仕事として管理する。
4. 通信断でも対応可能な工程を完了し、再起動後も安全に再開できる。
5. 接続復帰後、外部作用を本人の許可範囲で送信し、冪等keyとProvider照会で結果を確認する。不明時は照合待ちで停止し、一般的なexactly-onceは保証しない。
6. Tool成果と実際の収益を別イベントとして扱い、Providerが確認した収益だけを署名済みEarning Receiptにする。
7. Earning ReceiptをWalletへ一度だけ転記し、費用を差し引いた検証済み運用収支を表示する。
8. 失敗、取消、重複、更新、rollback、純正OS復旧を再現できる。

6〜7の **Tool完了→署名済みEarning Receipt→Wallet自動照合** は、2026-09-15にROCK_READYのfixture縦断まで実装し、2026-09-16に同一の合成実行IDと証拠hashでPixelのTool／端末Wallet区間と署名精算区間を相関した。Provider署名、完了済み・非サンプルjob、利用者、Tool、時刻を照合し、同じ実行をWalletへ二重計上しない。実販売・決済Providerのsandbox接続、返金、chargeback、払出しは未接続であり、相関済みfixture合格を実収益実績や1.0完成とは扱わない。

## 6. ファンドの自律改善

ファンドは金融利回りの保証商品ではなく、目的に合う複数Toolの役割構成と実行順を管理する自動化単位から始める。改善判断には次の実測だけを使う。

- 完了率、再試行率、人の確認時間、処理時間、端末資源・温度
- Provider確認済み売上、返金、Tool／通信／外部Provider／運用費
- Tool版、入力種別、実行先、失敗原因、成果の受入結果
- 同じ構成を再実行した時の再現性と、利用者ごとの差

`検証済み運用収支 = Provider確認済み収益 - 実行費用 - Provider費用 - platform費用 - 返金等`を基本指標とする。税額は個人・法人、地域、時期で異なるため、この値へ推測で混ぜない。月50万円は、改ざん不能なreceiptと費用を持つ継続実績として到達を判定し、合成値、PAPER結果、単発売上、将来予測を達成扱いしない。

## 7. Walletと税務支援

Walletは収益最大化だけでなく、合法的な税務準備を効率化する。収益・費用・receiptの収集、分類候補、控除候補の根拠、期間別集計、申告用export、専門家への確認資料を作る。

RockstarOS自身が脱税、架空経費、居住地偽装を提案しない。法域ごとの税務判断、申告、納税、法人化等の最終判断は、対応資格と責任を持つProviderまたは専門家と本人確認を通す。将来自動提出を扱う場合も、対象国、資格、委任、exactな本人承認、receipt、取消・訂正経路を別gateにする。

## 8. 改善用データの収集境界

改善のためのデータ収集は行う。ただし、利用者が何を送るかを理解して選べることを製品条件にする。

標準候補は、Tool／モデル／OS版、成功・失敗種別、処理時間、再試行、端末資源・温度、通信状態、費用、Provider確認済み収益、ファンド構成変更と受入結果である。仕事本文、成果物本文、私的会話、写真、連絡先、秘密鍵、seed phrase、認証情報、正確な位置は既定で収集しない。

収集categoryごとに目的、送信先、保存期間、第三者提供、匿名化、export、削除、同意撤回を示す。収益や安全性の集計から個人を再識別する必要がない場合は端末内集計または匿名化した値を送る。データ提供を収益保証や不明瞭な包括同意と交換しない。

## 9. 段階gate

A〜FはCoreから収益利用を育てる系統。GはAの共通契約を使う並行系統であり、F完了後という順序ではない。Core 1.0と各応用の独立受入は共通設計第9節に固定する。

| 段階 | 合格条件 |
| --- | --- |
| A 実行 | 端末内LLMと一つのToolがofflineで完了し、再起動・失敗復旧できる |
| B 収益loop | 外部案件またはProvider fixtureから、成果、署名済み収益、Wallet照合を一度だけ完走する |
| C 反復 | 同じ仕事を複数回実行し、費用込みの検証済み運用収支と失敗率を再現できる |
| D ファンド | 複数Tool構成を一押しで開始し、Zemaが役割、順序、確認、停止、結果を管理する |
| E 改善 | 同意済み実測データから構成変更を提案し、旧構成との比較で改善を証明する |
| F 拡大 | 複数利用者・地域・Providerで本人分離、法務、税務、払出しを受け入れる |
| G Game/IP並行 | 同じ仕事・権限・成果・receipt基盤で自作の制作/試遊/save復旧を検証。動画/VRは追加adapter、実資産交換時だけWalletを必要とする。専用端末は価値実証後の別段階 |

OS full buildと最初の実機起動はCoreの実証として行う。Sky、Zema、便利機能、ゲーム連携は、共通Coreを利用しながら独立更新できるsystemとして並行・段階的に進める。専用端末は価値実証後に行う。作業量や機能数ではなく、各段階の実測証拠で次へ進む。
