# RockstarOS device account linking

The Android client must use one Rockstar account across Sky, Zema, entitlement lookup, and cloud work APIs. A device does not invent a cloud owner ID from its Android serial number, and account credentials are never copied between services.

## Authorization flow

1. The device calls `POST /api/rockstar/device-authorizations` with `{ "action": "begin", "deviceName": "..." }` over HTTPS. The service returns a one-time `deviceCode`, an eight-character `userCode`, a ten-minute expiry, a five-second poll interval, and the browser verification URL.
2. The user opens `/connect/device`, signs into the Rockstar account, checks the displayed device name, then approves or denies the code. Approval binds the pending request to the authenticated account.
3. The device polls the same API with `{ "action": "poll", "deviceCode": "..." }`. Approval consumes the request exactly once and returns a random `rock_session_...` bearer token with a 90-day expiry. Repeated polling cannot recover that token.
4. APIs that accept the device session resolve its owner from the hashed server-side token record. Supported routes include Rockstar service-entitlement lookup/claim, Sky A2A agent and delegation access, delegation artifacts and settlement lookup, and remote LLM pricing/execution guards. Existing service entitlements and paid-execution controls still apply.
5. The account holder can list and revoke sessions at `/connect/device`. Revocation and expiry immediately reject the bearer token. The database stores only SHA-256 token hashes; the clear token is returned once and must be held by the native app in protected storage.

`rockstar_device_authorizations` stores hashes of both authorization codes and the binding state. `rockstar_device_sessions` stores a hash of the device token, account owner, display name, expiry, last-use time, and revocation time. The server routes return codes/tokens only in no-store responses and do not write cleartext values to D1; deployment access-log redaction still needs acceptance.

## Trust boundaries and remaining device work

This flow proves that the user approved a particular app session for an account. It does not prove the Android package, device integrity, eSIM activation, or possession of the hardware Broker key. Cloud settlement still requires its separately registered Broker signature and an owner-scoped delegation. The device flow does not bypass service scopes, provider pricing, budget authorization, or provider receipt checks.

The server and browser pieces are implemented and locally exercised with synthetic users and a local D1 database. Android UI for entering/polling the device code and protected token persistence is implemented in source; the authenticated read-only service-home bridge is described below. These Android changes remain uncompiled on this host because the Android SDK is absent. Broker-key enrollment and exact-device acceptance remain open. No production OAuth provider, carrier, SIM/eSIM activation, or production billing has been accepted.

An Android-independent Core client protocol now implements the `begin`/`poll` contract, validates the server origin and response fields, enforces the polling interval, handles pending/slow-down/denied/expired responses, and hands an approved token once to an injected `SessionStore`. The `HttpTransport` must enforce HTTPS, reject redirects, bound JSON responses, and omit browser cookies; the `SessionStore` must provide platform-protected persistence. The protocol tests pass on the local JVM, but those interfaces do not constitute an Android HTTP transport, an Android Keystore-backed session vault, a user-facing code/poll flow, or device acceptance. See [local evidence](evidence/rockstar-device-link-local-20261001.json).

The Android Broker/Shell source now supplies those adapters: Broker-only Internet permission; exact-origin HTTPS transport with redirects and process cookie handlers rejected, bounded identity-encoded JSON and timeouts; no-backup AES-GCM session storage under an AndroidKeyStore key; and Shell AIDL/UI entry points for code display, browser approval and rate-limited polling. The service origin has no production default and must be supplied at build time as `-ProckstarServiceOrigin=https://service.example` (origin only, no path or trailing slash). The shell app itself has no Internet permission and never receives the bearer token over AIDL. The transport and storage Java files passed a syntax/type compile using temporary Android API stubs, but the actual Android build, AIDL generation, instrumentation tests and device runtime are unavailable because this host has no Android SDK. That partial compile does not accept this device path.

The Android Broker uses the encrypted session internally for allowlisted GET home/detail/result calls and POST quote/create/approve/execute calls at the exact configured HTTPS origin. It rejects redirects/cookies, bounds and validates JSON, and exposes only approved operations through Shell API v10; the bearer token never crosses AIDL. The service home returns scopes/entitlements, recent cloud LLM/Agent state and an explicitly saved LLM result snippet. Users can open LLM usage/results, Agent state/live meter/receipt, or retrieve Agent artifacts through user-selected calls. The native quote form sends a request to RockstarOS for a signed-rate estimate, shows exact currency, selected cap, rate version/unit prices/source, and save-result choice. A separate consent checkbox and button are source-wired to reserve that exact budget then call the approved text route; the button is hidden unless quote endpoint reports execution available, and the server independently checks the pricing/provider/key gate before dispatch. The current pricing gate is false, so this path does not execute in the current configuration. An uncertain post-send result is not automatically retried; the Broker only attempts cancellation through an API that permits cancellation before send. Transport paths are built from closed operation kinds and validated task IDs. The home omits prompts and remains owner-scoped; invoice/funded-Wallet fields remain false. Focused product-source and public-rate-card tests, TypeScript, production build, OS contract check and targeted OxLint pass. API/D1 integration cannot run here because localhost `listen` returns `EPERM`; Android SDK/APK/Binder/device acceptance is unavailable. No production billing, carrier activation, live provider execution, or successful OS installation is proven.
