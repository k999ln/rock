# RockstarOS device account linking

The Android client must use one Rockstar account across Sky, Zema, entitlement lookup, and cloud work APIs. A device does not invent a cloud owner ID from its Android serial number, and account credentials are never copied between services.

## Authorization flow

1. The device calls `POST /api/rockstar/device-authorizations` with `{ "action": "begin", "deviceName": "..." }` over HTTPS. The service returns a one-time `deviceCode`, an eight-character `userCode`, a ten-minute expiry, a five-second poll interval, and the browser verification URL.
2. The user opens `/connect/device`, signs into the Rockstar account, checks the displayed device name, then approves or denies the code. Approval binds the pending request to the authenticated account.
3. The device polls the same API with `{ "action": "poll", "deviceCode": "..." }`. Approval consumes the request exactly once and returns a random `rock_session_...` bearer token with a 90-day expiry. Repeated polling cannot recover that token.
4. APIs that accept the device session resolve its owner from the hashed server-side token record. Supported routes include Rockstar service-entitlement lookup/claim, Sky A2A agent and delegation access, delegation artifacts and settlement lookup, and remote LLM pricing/execution guards. Existing service entitlements and paid-execution controls still apply.
5. The account holder can list and revoke sessions at `/connect/device`. Revocation and expiry immediately reject the bearer token. The database stores only SHA-256 token hashes; the clear token is returned once and must be held by the native app in protected storage.

`rockstar_device_authorizations` stores hashes of both authorization codes and the binding state. `rockstar_device_sessions` stores a hash of the device token, account owner, display name, expiry, last-use time, and revocation time. The server routes return codes/tokens only in no-store responses and do not write cleartext values to D1; deployment access-log redaction still needs acceptance.

## Browser confirmation and recovery (2026-10-11)

The confirmation binds the inspected eight-character code to the displayed device name. Editing the code clears the old confirmation; the input is disabled during requests, and approval/denial submits only the exact inspected code. Approval is not reported as a completed native connection: the device must still poll and receive its session.

The browser uses the shared 10-second header/body deadline and does not follow authentication redirects. A 401 removes the previous device list and confirmation, offers sign-in in a separate tab, and requires a fresh inspection before approval. Unknown approval/revocation outcomes are never automatically repeated. The user checks the native device and refreshes the owner-scoped session list; a delayed older list cannot undo a newer authentication failure. The browser retains the typed code only while the page stays open.

Nine actual-component regressions cover changed codes, pending inspection, 401/redirects, header/body timeout, stale lists, malformed approval responses, and revocation readback. Local synthetic browser checks at 390px and 1280px confirm A-to-B code replacement, exact B approval, timeout recovery without automatic resubmission, and authentication loss. These checks do not grant a real device session.

## Trust boundaries and remaining device work

This flow proves that the user approved a particular app session for an account. It does not prove the Android package, device integrity, eSIM activation, or possession of the hardware Broker key. Cloud settlement still requires its separately registered Broker signature and an owner-scoped delegation. The device flow does not bypass service scopes, provider pricing, budget authorization, or provider receipt checks.

The server and browser pieces are implemented and locally exercised with synthetic users and a local D1 database. Android UI for entering/polling the device code and protected token persistence is implemented in source; the authenticated read-only service-home bridge is described below. The integrated source `19ef1020d2065fd6c31bfeb6d7cbaa703be0a1f0` built and passed Android 35 emulator CI: Core 116 unit tests, automation 16 unit tests plus 43 instrumentation tests (2 physical-reboot cases skipped), Shell 6 and operator-agent 6 instrumentation tests. The 20 response-deadline cases ran on the actual Android monotonic clock. Exact-device acceptance remains separate. No production OAuth provider, carrier, SIM/eSIM activation, or production billing has been accepted.

An Android-independent Core client protocol now implements the `begin`/`poll` contract, validates the server origin and response fields, enforces the polling interval, handles pending/slow-down/denied/expired responses, and hands an approved token once to an injected `SessionStore`. The `HttpTransport` must enforce HTTPS, reject redirects, bound JSON responses, and omit browser cookies; the `SessionStore` must provide platform-protected persistence. The Core protocol and Android adapters are tested separately; neither is full-OS or production acceptance. The earlier [2026-10-01 local evidence](evidence/rockstar-device-link-local-20261001.json) records the environment limitations at that time.

The Android Broker/Shell source now supplies those adapters: Broker-only Internet permission; exact-origin HTTPS transport with redirects and process cookie handlers rejected, bounded identity-encoded JSON and timeouts; no-backup AES-GCM session storage under an AndroidKeyStore key; and Shell AIDL/UI entry points for code display, browser approval and rate-limited polling. The service origin has no production default and must be supplied at build time as `-ProckstarServiceOrigin=https://service.example` (origin only, no path or trailing slash). The shell app itself has no Internet permission and never receives the bearer token over AIDL. The same-SHA Android build/AIDL/instrumentation results are tracked in the [integrated evidence](evidence/integrated-development-20261011.json) and [Android workstream](workstreams/07-android-device-local-ai.md). The debug APK/emulator result does not establish a production device origin, issuer contract, exact physical SKU, or full OS image acceptance.

The Android Broker uses the encrypted session internally for allowlisted GET home/detail/result calls and POST quote/create/approve/execute calls at the exact configured HTTPS origin. It rejects redirects/cookies, bounds and validates JSON, and exposes only approved operations through Shell API v10; the bearer token never crosses AIDL. The service home returns scopes/entitlements, recent cloud LLM/Agent state and an explicitly saved LLM result snippet. Users can open LLM usage/results, Agent state/live meter/receipt, or retrieve Agent artifacts through user-selected calls. The native quote form sends a request to RockstarOS for a signed-rate estimate, shows exact currency, selected cap, rate version/unit prices/source, and save-result choice. A separate consent checkbox and button are source-wired to reserve that exact budget then call the approved text route; the button is hidden unless quote endpoint reports execution available, and the server independently checks the pricing/provider/key gate before dispatch. The current pricing gate is false, so this path does not execute in the current configuration. An uncertain post-send result is not automatically retried; the Broker only attempts cancellation through an API that permits cancellation before send. Transport paths are built from closed operation kinds and validated task IDs. The home omits prompts and remains owner-scoped; invoice/funded-Wallet fields remain false. Focused product-source and public-rate-card tests, TypeScript, production build, OS contract check and targeted OxLint pass. The integrated local API/D1 tests and CI APK/Binder tests now run; their exact source SHA and environment are recorded separately from physical-device acceptance.
