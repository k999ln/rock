# avocadoMini / RockstarOS
# ゲームから、暮らしの「できない・面倒・分からない」を減らす製品へ

調査日：2026年9月24日。公開研究・公的調査・公式仕様に基づく製品展開案。

## 結論

**avocadoMiniの目標は「空中に映るゲーム機」で終わらず、遊びや制作で覚えた操作が、そのまま日常の行動を助けること。RockstarOSは、その操作・データ・接続先・権限・費用を本人の管理下でつなぐ。**

文献から最初に検証したい生活価値は、①自分に合う方法で操作できる、②手を止めずに次の作業へ進める、③機器やAIを切り替えても設定・費用・作品を見失わない、の3つである。「何でも自動化」や「常時見守り」を最初の約束にしない。

提案する展開順は、**ゲーム → 創作・学び → 限定した日常作業の支援 → 対応機器・サービスとの連携**。これは研究からの製品仮説であり、利用者が必ずこの順に欲しがるという市場予測ではない。

ユーザーが求める、**使用時20cm以内・1本で動作・増設で広範囲かつ鮮明・眼鏡なしで周囲の実空間全体に舞う粒子**という目標は維持する。ただし、全条件を満たす表示ハードウェアは今回も確認できていない。生活機能の必要性の証拠と、表示装置を製造できる証拠は別である。

## 1. まず、利用者には何ができる製品にするか

以下は目標機能。現時点の実装済み一覧ではない。

| 機能 | 利用者ができること | 解決したい「不」 | 優先判断 |
|---|---|---|---|
| 空間ゲーム | 手・身体・声で粒子を動かし、衝突・結合のルールで遊ぶ。協力、対戦、一時停止、再開 | コントローラー操作の壁、受け身の娯楽 | 製品の入口。表示の研究開発と入力・ゲームの開発を分離して検証 |
| つくる・学ぶ | 遊んだルールを変える。自作の粒子・3D作品・短い体験を保存し、比較し、共有する | 作り方が分からない、専門ツールが難しい | ゲームに近い第1拡張。学習効果は楽しさと別に評価 |
| 手順を支える | 許可した作業について「次は」「戻って」「ここで中断」を使う。手順・タイマー・メモをまとめる | 両手がふさがる、説明の見直し、再開時の混乱 | 最初の生活実証。火や刃物を扱わない作業から |
| 対応する暮らしの操作 | 登録した照明、音量、タイマー等を操作し、実際にどうなったか確認する | アプリやリモコンの行き来、操作の覚え直し | 低リスク・対応確認済みの機能だけから |
| 許可した物・作業の記憶 | 指定した物の「最後に見えた場所と時刻」、保存した途中工程を確認する | 探し直す、思い出せない | 探索機能。視野外を含む現在位置の保証はしない |
| 一緒に遊ぶ・つくる | 本人が選んだ相手を招待し、同じゲームや作品を共同で扱う | 離れていて一緒に行動しにくい | ゲームの拡張。孤独解消や健康改善の保証にはしない |

全機能共通で、**着座・片手・小さい動作・声・物理入力等を選べること、止められること**を土台にする。取り消せる操作には取消を設け、取り消せない作用は実行前に明示・確認する。身体ゲームだからといって、大きな身体動作を生活機能まで強制しない。[W3C XAUR](https://www.w3.org/TR/xaur/)

## 2. 生活の課題について、何が根拠としてあるか

### 2.1 忙しさはある。ただし端末が家事を代行するわけではない

2021年の社会生活基本調査では、6歳未満の子供を持つ「夫婦と子供の世帯」の家事関連時間は、週全体平均・1人1日で夫1時間54分、妻7時間28分だった。家事関連は家事・介護看護・育児・買い物の合計で、すべての世帯の平均ではない。この時間をminiによる削減可能時間に換算してはいけない。[総務省、表2-2・本文p5](https://www.stat.go.jp/data/shakai/2021/pdf/gaiyoua.pdf)

**製品への推論：** 掃除や調理を物理的に代行する機構がない以上、まず「手順を探す・確認する・他の作業に戻る」という情報処理の負担を狙う。家事を担当する人へ新たな機器管理を押し付けない。

### 2.2 操作の壁は、機能数を増やすだけでは消えない

消費者庁の2022年度調査では、65–74歳のネット非利用者の55.2%、75歳以上のネット非利用者の57.6%が、使い方が分からないことを非利用理由に挙げた。これは高齢者全体の半数を意味しない。生活に必要ないという回答もある。[消費者白書2023、図表I-2-1-7](https://www.caa.go.jp/policies/policy/consumer_research/white_paper/2023/white_paper_122.html)

一方、音声アシスタントを利用する障害者に関する質的研究では、自分で日常操作ができる価値と同時に、設定、認識失敗、機能の発見の難しさが報告されている。[Pradhan et al., 2018](https://doi.org/10.1145/3173574.3174033)

**製品への推論：** 「話せば何でもできる」より、「何ができるか分かり、失敗したとき直せる」導入と操作が必要。若者用・高齢者用と単純に分けず、本人の能力と場面に合わせる。

### 2.3 学ぶ時間の不足には、短い再開可能な体験で挑む

OECDの2025年報告は、2023年調査に基づく仕事関連の成人学習の議論で、希望した学習に参加できなかった25–65歳の日本の回答者では、60%以上が仕事・家庭の時間制約を最大の障壁としたと報告する。全成人や子供の60%以上を意味しない。[OECD、Figure 3.8](https://www.oecd.org/en/publications/trends-in-adult-learning_ec0624a6-en/full-report/why-is-participation-not-more-common_73893b53.html)

**製品への推論：** 長い講座を空中に置き換えるより、小さな問いを試し、途中保存して戻れることを優先する。短時間化が理解を高めるかは別に試験する。

### 2.4 経済圏は、使う側が抜け出せる設計にする

消費者庁の2023年度調査では、ネット利用者4,439人の68.8%が「登録は簡単でも解約が複雑・難しいと感じることがある」に、とても／ある程度当てはまると回答した。実際に解約不能だった割合ではない。[消費者庁、問9・図2-9](https://www.caa.go.jp/policies/policy/consumer_research/research_report/survey_002/assets/consumer_research_cms201_240614_15.pdf)

**製品への推論：** RockstarOSがアプリ、外部AI、作品販売をつなぐなら、利用開始だけでなく料金確認、停止、解除、データ持ち出しも同じ場所で分かるようにする。外部サービスをOSが何でも解約できるとは約束しない。

## 3. 操作研究から、採用したいこと・採用しないこと

| 文献で確認したこと | 製品の設計判断 | 飛躍させない点 |
|---|---|---|
| 空中操作の腕の保持は疲労を生む。曲げた肘・肩と腰の間など、負担の低い条件がある | 生活操作は短い動作にし、腕を下ろして完了できる。物理入力も残す | 短時間実験を全利用者・長時間プレイへ一般化しない |
| 調理対話では作業文脈が重要。しかし2024年、2026年の例には人間が認識を代行した研究がある | レシピ・工程・確認済み状態を持つ限定支援を作る | 人間代行の会話がうまくいったことを自動視覚AIの精度と呼ばない |
| 小規模な高齢者音声利用研究では、タイマーやリマインダーの信頼性に懸念が出た | 登録内容、訂正、通知の到達、再起動後の未完了状態を明確にする | 停電でも鳴る、必ず本人に届くと保証しない |
| VR研究では、臨場感が高くても知識得点がPC条件より低い例がある | 楽しさ、理解度、別課題への応用を別々に測る | VR一般や裸眼空間表示に効果がないと決めつけない |
| 家庭へ運動ゲームを渡すだけでは、日常全体の身体活動が増えなかったRCTがある | 身体を使って遊ぶ楽しさとして提供し、継続を実測する | 痩せる・治療できる・健康になると売らない |

根拠：[腕の疲労研究](https://doi.org/10.1145/2556288.2557130)、[調理支援研究2024](https://discovery.ucl.ac.uk/id/eprint/10189212/)、[調理支援研究2026](https://aclanthology.org/2026.iwsds-1.15/)、[高齢者音声利用研究](https://doi.org/10.1145/3373759)、[VR学習比較](https://doi.org/10.1016/j.learninstruc.2017.12.007)、[家庭内活動ゲームRCT](https://pubmed.ncbi.nlm.nih.gov/22371457/)。人数・比較条件・解析上の限界は研究台帳に記載した。

## 4. 体験を具体化する：4つの利用場面

以下は**提案シナリオ**。動作を確認済みの製品説明ではない。

### A. ゲームを遊び、そのまま自分の作品にする

1. miniを置き、本人がゲームを開始。登録済みの利用者だけでなく、ゲストとして記録せず遊ぶ選択も用意する。
2. 先に入力方法を選び、必要な範囲だけ校正。声・スイッチ等で補助または不要な身体校正を省略できる。遊べる範囲と、観測できない場所を示す。
3. 粒子を選び、動かす。両手が使いにくければ声やコントローラーで同じ操作をする。
4. 衝突・結合・分離をゲーム内ルールとして計算。取消、スロー再生、条件変更を行う。
5. 「このルールで別のステージを作る」。作品とルールの版を保存する。
6. 共有するときだけ、送り先・公開範囲・権利・費用を確認する。

ゲーム粒子、科学学習用のモデル、実際の化学反応は区別する。学習用途では、予測→条件変更→観察→説明の流れと、どこを単純化したかを示す。[PhET研究概説](https://phet.colorado.edu/phet-dist/publications/PhET_Simulations_That_Enhance_Learning.pdf)

**表示の条件：** 望まれる完成体験は裸眼の実空間表示。開発用モニターでゲームロジックが動いたことを、その完成とは扱わない。

### B. 工作中に、手を離さず次の工程へ進む

1. 作業面にminiを置き、「この組立を手伝って」と明示的に開始する。
2. 本人が選んだ説明書・版・現在工程だけを読み込む。
3. 「次は？」「もう一度」「一つ戻って」を短い音声やボタンで操作する。
4. 見えない部品や向きは断定しない。「部品の印を見せて」または本人の確認へ戻る。
5. 中断時に工程を保存。復帰時は、保存時点と実物の現在状態が一致するか確認する。
6. 終了すると撮影・保存を止める。記録を消す選択も同じ流れで示す。

最初の比較対象は紙の説明書、スマホ動画、既存の音声タイマー。miniを置く・設定する・片付ける時間も含めて、総負担が減ることを検証する。

### C. 「この明かり」を操作する

1. 本人が対象の照明を登録する。位置と機器IDを結び付ける。
2. 「この明かりを暗くして」の声と指差しから候補を出す。
3. 候補が複数なら確認する。視線や指差しだけで誰の意図かを決めない。
4. 許可された低リスク操作を機器へ送り、機器からの応答を確認する。
5. 応答がなければ成功と表示しない。元のスイッチも利用できる。

「この明かり」の位置解決に空間認識の独自価値がある。一方、固定名で一つの照明を切り替えるだけなら、スマートスピーカーや物理スイッチの方が適する可能性もある。Matterは接続基盤の候補だが全機器・全機能対応ではない。[CSA Matter FAQ](https://csa-iot.org/all-solutions/matter/matter-faq/)

### D. 「鍵はどこ？」に、見た事実だけ答える

1. 本人が対象物と観測する場所・期間を選ぶ。来客や同居者への説明・停止手段を用意する。
2. 問い合わせに対し「許可された作業面で、最後に見たのは17時20分」のように、時刻を伴って返す。
3. その後に移動している可能性、視野外、遮蔽は明示する。未観測なら不明と答える。
4. 写真を常時保存する以外の、イベント・位置情報のみで成立するかを試す。位置情報も私的情報として保護する。

これはEgo4Dの過去映像検索に近い課題設定であり、部屋全体の「現在地レーダー」ではない。[Ego4D Episodic Memory](https://ego4d-data.org/docs/benchmarks/episodic-memory/)

## 5. 機能から逆算したRockstarOSの役割

この表は提案アーキテクチャであり、実装済みと判定したものではない。

| 共通機能 | ゲームで使うこと | 生活へ広げること | 必要な境界 |
|---|---|---|---|
| 入力・校正 | 手・身体・音声の操作 | 作業対象、指差し、短い命令 | 入力方法を選ぶ。追跡喪失は検出する |
| 空間・状態管理 | 同じ座標上で粒子を扱う | 許可した作業面・物・工程の状態 | 観測事実、推定、未観測を分ける |
| 意図と操作の管理 | 選択・移動・結合・取消 | 次工程・照明・タイマー | 見聞きしただけの情報を操作許可に変えない |
| 実行と停止 | ローカルゲーム、保存、停止 | 許可された機器・サービス操作 | 送信済み、成功、失敗、不明を区別 |
| Capability Adapter | 対応ゲームや制作ツール | 家電、外部AI、連携先 | 対応版、機能、費用、権利、地域、認証を申告 |
| Asset Registry | ゲーム内作品と版 | 教材、3D、動画、手順テンプレート | 来歴と利用許諾を別管理。持ち出し可能にする |
| 本人と同居者の制御 | ゲスト、公開承認 | 撮影・記録・連携の権限 | 物理停止、目的別許可、削除、利用履歴 |
| 更新・復旧 | 再起動後の状態回復 | 通信断・更新失敗・端末交換 | 支援終了方針、署名、鍵保護、復旧手段 |

操作の流れは、**入力 → 意図候補 → 対象と権限の確認 → 実行 → 結果確認 → 必要な履歴**。例えば説明書に「ドアを開ける」と書いてあっても、それは観測した文章であり、現実のドアを開けるユーザー指示ではない。

鍵、加熱、支払い、外部公開など重大な作用は、ゲーム内操作と同じ自動実行経路へ入れない。初期生活実証からは除外し、後の対応時も別の本人確認・安全設計・利用条件審査を行う。

### 日本語音声を「対応済み」とする前に

低消費電力の定型コマンド経路と、自由質問・生成用の重い経路を分けるのが候補。Home Assistantにはこの分離の実装例がある。ただし、閲覧したSpeech-to-Phraseの対応言語一覧には日本語がなく、そのまま採用して日本語性能を約束できない。[ローカル定型認識の公式説明](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)、[対応言語一覧](https://github.com/OHF-voice/speech-to-phrase)

日本語のウェイクワード、音声認識、意図理解、読み上げを個別に試す。生活音・テレビ・ゲーム音・複数人・方言・発話差・距離・本体ファン音を含め、認識率だけでなく誤起動と訂正負担も測る。緊急停止は物理手段を持ち、音声成功に依存させない。

## 6. 20cm・mini単体・増設を、生活でも意味のある条件にする

### 別のEdge Hubを必須にしない

各miniへ基本処理・保存・入力・停止を持たせる同型構成を基本仮説とする。「Hubを別筐体にしない」のであって、制御処理や通信機能が不要になるわけではない。例えばThread機器への連携を採用するなら、境界ルーターの役割と対応無線が別途必要になる。[Home Assistant Matter資料](https://www.home-assistant.io/integrations/matter)

### 20cmは本体の高さ。必要な視界は利用場面で違う

- 床置きゲーム：低い位置から全身や手が見えるか、家具・人の遮蔽、足元の配線を検証。
- 作業台：本体を作業面に置いた時、手で隠れる部品や近距離を読めるか検証。調理なら衛生・清掃・水はね・熱源との距離も設計対象。
- 居室：ファン音、通知の音、撮影表示、夜の光が、新しい不快や負担にならないか検証。

銀色の細い円筒、黒いカメラ帯、円形台座という外観を保持しつつ、視野・マイク配置・熱・安定性が収まるかを確認する。既存の生活家具へ置くことと、本体を伸ばして20cmを超えることは区別する。

### 台数を増やす価値を分けて測る

1. **認識**：別の方向から見えるため遮蔽を補えるか。台数だけで精度向上を保証しない。
2. **表示**：有効表示領域や点密度を増やせるか。認識範囲の改善とは別試験。
3. **生活サービス**：部屋をまたぐ作業の再開や通知が可能になるか。複数台が同じ発話を重複実行しないことも必要。

単体の有効範囲を測定 → 2台の同期・連続領域・干渉を測定 → 4台を評価する。本数から「何畳」と計算するのは、単体の実測値と配置条件が得られてから。

## 7. 裸眼の空間表示は、専用の研究開発課題として残す

2026年の二光路体積表示研究は、Xe充填領域内のセンチメートル級の像を協調描画している。これは有用な研究参考だが、20cmの独立タワーから通常の室内空気全体へ表示できる実証ではない。[Kumagai et al., 2026、訂正版](https://doi.org/10.1145/3816042)

光で実粒子を保持・移動して体積像を描く研究もあるが、本製品の安全・寸法・部屋規模を証明していない。[Smalley et al., 2018](https://www.nature.com/articles/nature25176)

従って研究を二つに分ける。

- **体験とOSの研究**：身体入力、粒子ルール、音声、途中再開、権限・費用管理。仮の表示装置を使う場合は「体験検証」と明示する。
- **表示と筐体の研究**：表示体積、観察方向、照度、点間隔、位置誤差、更新、光安全、人体の侵入、気流、電力、熱、寸法を測る。

最終製品としての完成判断には両方が必要。壁投影、眼鏡、卓上の小さい像へ要求を無断で変更しない。表示が未成立のまま確定BOM・加工図・回路を「製造可能な完全版」としない。

## 8. 経済圏の中心は、データと創作物を本人が制御できること

提案する仕組みは、ハード、標準ゲーム・制作機能、追加の体験/教材、任意の外部AI・連携を分ける。価格、利益率、市場規模は今回の調査では算定していない。

### 販売・生成・公開の流れ

1. 誰が、何を、どの素材と条件で作ったかを記録する。
2. 外部AIを使う場合、送るデータ、提供者、見積費用・上限、利用条件を事前に確認する。
3. 出力はモデル/サービス版と編集履歴を保存する。失敗・再試行費用も分かるようにする。
4. 公開と販売は別の承認にする。生成しただけで自動公開しない。
5. 使う側は、対応環境、許可、価格、更新・サポート条件を確認して導入する。
6. 自社サービスを停止し、作品を出力し、連携を解除する道を用意する。

C2PAのような来歴情報は改変検知や出所の説明に使えるが、内容の真実性や著作権所有の自動証明ではない。[C2PA Explainer、2.2版](https://spec.c2pa.org/specifications/specifications/2.2/explainer/Explainer.html)

3Dの持ち出し形式にはglTF等を検討できるが、ファイル形式だけでゲーム挙動や外部ゲームへの導入まで互換になるわけではない。[Khronos glTF 2.0仕様](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

**GTAのような没入感を目指すことと、GTA VIの公式対応は別。** 外部タイトル、生成AI、SNSは公式に許される接続・必要性能・権利・地域条件と実機試験を確認した機能だけを対応表へ載せる。今回、個別サービスの契約審査やGTA実行試験はしていない。

## 9. 常時カメラを増やす前に、信頼を仕様にする

機器の所有者以外にも、同居人、訪問者、家で働く人がいる。ナニーと雇用する親への面接研究は、撮影を選ばなかった人と所有者の力の差を示している。[Bernd et al., 2020](https://www.usenix.org/conference/foci20/presentation/bernd)

提案する必須条件：

- 撮影・マイク・記録・外部送信は別の状態として分かるようにする。
- 物理的なセンサー遮断/ミュートと、実際の稼働状態に結びついた表示を設計する。
- 原則は、本人が開始した目的と範囲で処理。不要な映像・音声の保存を避ける。
- ローカル保存でも、閲覧権限、保存期限、削除、端末譲渡時の消去を設計する。
- 子供の身体・声・室内情報を第三者の広告用プロファイルへ流すことを前提にしない。
- 部屋の映像、ゲームの台詞、読み込んだ説明書は未信頼の入力。そこに含まれる命令を本人承認として扱わない。
- 費用上限、連携権限の撤回、外部公開の確認をOS共通機能にする。
- 署名付き更新、鍵保護、復旧、脆弱性窓口、サポート終了後の扱いを発売前に決める。[NIST IR 8259 Rev.1](https://csrc.nist.gov/pubs/ir/8259/r1/final)

法的な適合性や医療用途は、販売地域・対象・実装が決まった段階で専門家による別審査が必要。今回の提案だけで認証済みとはしない。

## 10. 展開の判定ゲート：日付より、越えるべき証拠を決める

| 段階 | 最小の検証対象 | 次へ進むための証拠 | 見送り・修正する条件 |
|---|---|---|---|
| G0：要求と価値 | ゲーム1体験＋工作支援1体験。外観と20cm条件を維持 | 使いたい場面と既存方法の不便が本人の観察で確認できる | 珍しさだけで、繰り返す課題がない |
| G1：入力と基本ゲーム | 1台の手・声・代替入力、粒子ルール、保存・停止 | 追跡喪失や誤認から自力で戻れる。目標負荷で演算・熱・音を測れる | 訂正・準備が遊びや作業より負担になる |
| G2：生活の最初の用途 | 危険を伴わない手順支援、タイマー、照明の模擬操作 | 従来方法より総負担が減り、利用者自身で完了できる | カメラが不要なら撮影なしへ変更し専用ハードの追加価値を再評価。同居者が受け入れない場合も見直す |

| G4：増設 | 1→2→4台、共通座標・時刻・操作の重複排除 | 範囲/品質のどちらがどれだけ改善したか分離して実測 | 二重像、隙間、干渉、断線時の誤実行 |

G3はG1/G2と並行研究できるが、**完成版avocadoMiniの販売可否を左右する必須ゲート**。体験検証の成功だけでG3を通過した扱いにしない。すべて未実施であり、日付・価格・性能保証を置いたロードマップではない。

## 11. 試作機がなくても次にできる検証

### 課題観察

ゲーム/制作をする人、作業で手がふさがる人、今の入力方法に不便がある人を、年齢だけで一括りにせず募集する。本人が普段使う方法を観察し、準備・設定・訂正・後片付けを含む負担を記録する。募集・撮影はまだ行っていない。

### 同じ内容で比較する体験試験

18–24人程度の形成的テストを候補とし、紙/スマホ、声のみ、声＋作業状態、自由に選べる入力を順序を入れ替えて比較する。人数は検出力計算済みの値ではなく、探索計画。本人に可能な条件だけを試す。

認識を人間で代行する場合は参加者への適切な説明・同意の下で行い、「この体験が役立つか」の試験として記録する。自動AI性能の試験とは混ぜない。実物の加熱、鍵、支払い、緊急通報は操作しない。

### 評価指標

- 目的を自力で完了できたか。誰の補助が何回必要だったか。
- 手順誤り、中断、訂正、取り消し、誤起動。平均値だけでなく失敗する条件を見る。
- 総負担時間：設置＋操作＋失敗復旧＋片付け。初回設定・保守時間は独立して報告し、セッション当たりへ配分する場合は実利用回数を分母として併記する。単位は分/セッション等を明記する。
- 楽しさ、疲労、理解度、別課題への応用、継続したい理由を分ける。
- 外部送信・費用・保存範囲を、利用者が正しく説明できるか。
- 試作品完成後は10–15世帯、従来方法の1週＋4–6週程度の探索的利用を候補にする。新鮮さが薄れた後の自発利用、置かれなくなった理由も見る。

数値的な合否値は、先に測る従来方法の分布と、当事者が意味があると感じる最小改善量から設定する。今回、削減分数・精度・成功率を実測した値はない。少数の成功例だけで量産や医療的効果を判断しない。

## 12. 今回の判断と、まだ答えがないこと

**進める価値がある方向：** ゲームと創作を軸に、同じ操作で日常の小さい負担を減らす。生活の初手は、本人が開始する限定した手順支援と低リスク操作。アクセシビリティ・停止・費用・持ち出しは最初から共通化する。

**需要をまだ確認していない点：** 新しいハードに支払う理由、ゲーム利用者と生活利用者の重なり、同居者の受容、長期利用、導入・保守を誰が担当するか。公的統計から売上や購入人数を推計しない。

**技術をまだ確認していない点：** 全室裸眼表示、20cmでの熱・電力・収納、家庭内での日本語音声と視覚認識、1→4台の改善、外部ゲームの実行/操作互換性。実機試験は今回0件。

**最初から約束しないこと：** 万能家事代行、現在地を何でも知るカメラ、健康・孤独の改善保証、無審査の家電操作、全AI/ゲームへの対応、確定済み製造図面。

目指すのは「生活のすべてを機械に任せるOS」ではなく、**本人ができることを増やし、やらなくてよい操作を減らし、機械が何をしているかを本人が把握できるOS**である。

## 調査の方法と限界

総務省・消費者庁・内閣府・OECD・WHO・W3C、HCI/教育研究の原著、接続規格と開発元の公式資料を分担調査した。肯定結果だけでなく、負担・誤起動・学習効果の不一致・人間代行条件も確認した。

大きな効果量は比較条件を点検し、本文を直接取得できないものは出版社索引・著者公開版等の確認範囲を研究台帳に残した。公的調査の主要3図表はPDFのページ画像でも数値・分母・見出しを照合した。
