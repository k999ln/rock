# Rock OS — Hub・Wallet・Game 設計書

版: 1.0 / 2026-09-09 / 状態: **利用者の確認・承認待ち**

これは実装を始める前に確認する設計書。既存の確定要望は製品ベースv1.5/RQ01〜RQ15で保持し、今回の画面・体験案は下記「提案」と区別する。本書を保存しただけでは承認・実装・安全試験完了にならない。

## 1. どんな端末・基盤にするか

Rockは「自動化の準備、稼働状況、成果、お金を一か所で管理できるOS」。今回の提案は、そこへ任意のGame入口を加えること。自作ゲームの作者が共通Walletへ簡単につなげられる基盤を目指す。

利用者にとっては、サービスを巡回せず仕事の状態を確認し、確定した収入とゲーム資産を混同せず管理できる。ゲーム作者にとっては、Walletの認証・取引履歴・二重処理防止を自作せず、安全な接続契約から始められる。

「ゲームを入れればPCにはない価値が自動的に生まれる」「市場で一番便利」は現時点で未実証。外出中の操作時間や、作者の導入時間・復旧時間を測って価値を判断する。

## 3. OSの入口と利用体験

### Hub — 自動化を使う

商品を選ぶ→必要なPC/cloud/端末と契約を確認→許可・費用を確認→実行→結果・失敗・停止/再開を確認する。商品内部の業務処理はtobの商品が担当し、OSは接続と安全な管理を担当する。

日中に開く理由は「完了した」「止まった」「確認が必要」「費用や入金に変化があった」。意味のない通知を増やさない。

### Wallet — お金と交換を確認する

利用可能、保留、未照合、費用、入金、ATM、ゲーム交換を取引種別で分ける。仕事の成功件数をお金へ換算しない。実際のお金は認証済み売上/入金と照合し、今の開発段階では合成データと明示する。

### Game — 任意の遊びの入口（提案）

接続済みゲーム、ゲームごとの資産、交換の見積/履歴、対応する起動先をまとめる。ゲームを入れなくてもOSは成立する。ゲームを消してもWalletや成立済みの交換記録を消さない。

最初は「接続・資産・交換」の軽い入口とする。ゲーム本編をOSへ固定搭載したり、現OSで未検証の3Dゲームを動くと表示したりしない。端末/PC/cloud等の実行先はゲームごとに確認する。

追加の達成演出を採用する場合、例として「成果が1件保存された」を小さなアニメーションで見せる。これは演出用の集計値であり、売上や換金できる通貨ではない。仕事本文や個人情報・残高はゲームへ勝手に渡さない。

ゲーム要素の狙いは、成果を理解しやすくし、望む人が遊びへ移れること。ログイン報酬で何度も開かせたり、金融操作をゲームの達成条件にしたりすることではない。

## 4. 仕組みの役割分担

| 部分 | 担当すること | 担当しないこと |
| --- | --- | --- |
| Rock OS | 本人操作、Hub/Wallet/Gameの表示、許可と重要通知、保存・更新・復旧 | 未確認の残高を真実として扱うこと |
| 共通Walletサービス | 所有者/端末の認証、残高・予約・取引記録、照合、同時支出の制御 | ゲームのスコアを根拠に現金を発行すること |
| ゲーム交換サービス | 見積、承認、両側の処理状況、再送の重複防止、照合 | ATMコードの流用、結果不明の自動返金 |
| 各ゲームのサーバー | そのゲームのアカウント、資産、付与/消費の確定結果 | Rock Walletの利用可能額を直接増やすこと |
| 作者向けAPI/SDK | 接続、sandbox、見積/承認の導線、状態/履歴照会、診断 | 秘密鍵をプレイヤーのクライアントへ埋め込むこと |
| ATM経路 | 独立した本人承認・払出し・結果照合、自社手数料0 | ゲーム交換の必須中継になること |

Walletを複数ゲームの共通窓口にすることと、全ゲームの通貨を同じ通貨へ統一することは別。Game AのコインとGame Bのコインは発行元・単位・交換条件を分ける。

## 5. 交換でお金を壊さないルール

Wallet→ゲームは、条件提示→本人承認→利用可能額を予約→ゲーム側の付与→確定結果を照合→完了、という流れ。

途中で通信が切れたら「確認中」として保留を残す。ゲーム付与済みか不明なのに返金すると、通貨とお金を両方受け取れてしまうため、相手の記録を照会する。同じ操作を連打・再起動しても取引は1回だけ。

ゲーム→Walletは別の許可が必要な機能。方向を未確定のまま本番で有効にしない。ゲーム側の対象通貨の確定消費と、Wallet/承認済み清算先で確認できる交換原資が必要。作者が自由に増やせるポイント・bonus・スコアは、それだけでは換金できない。

ATM、月額、ゲーム交換が同時に同じ残高を使っても、全体で二重使用させない。Game Aの作者にGame Bや他プレイヤーの資金・履歴への権限を与えない。ATM障害はゲーム固有処理の前提にせず、ゲーム障害でATMを止めない。ただし共通Walletそのものが停止中なら、新しい資金確定はどちらも止める。

バックアップ復元では、同じ台帳を元と復元先の2か所で同時に支出可能にしない。外部で成立した取引は復元で巻き戻さず、再照合する。

## 6. ゲーム作者にとって使いやすい状態

作者が「ゲーム登録→テスト環境の設定→動くサンプル→プレイヤー接続/同意→合成交換→履歴/エラーの確認」まで進められることを最初の目標にする。

納品するのはAPI契約、reference SDK 1つ、合成通貨sandbox、最小サンプル、導入手順、診断/照会方法。最初から全ゲームエンジンの専用SDKを作らない。対象未指定なら汎用接続の小さな実装から始め、対応範囲を明記する。

2つの合成ゲームで同じSDKを使い、権限/通貨/履歴が混ざらないことを試験する。新しい作業環境で手順を試し、設定数・初回交換までの時間・エラー原因特定時間を測る。外部の初見作者の評価は別pilotとし、内部テストで市場優位性を証明したことにしない。

## 7. OSとしてどこまで動けば最初の合格か

現状は旧基準版のQEMU起動実績と、native source回帰の成功がある段階。最新統合コードから作り直したOSの一連の合格証拠はまだない。

最初の合格は次のすべてを満たす「QEMU開発用OS雛形」。

1. 最新sourceと依存版を固定し、新しい領域からOS imageをbuildできる。
2. 実際にOSが起動し、native画面・Hub・模擬Walletを操作できる。
3. 既存商品を実処理し、許可外操作・通信・二重実行を拒否できる。
4. 正常終了・再起動で結果/同意/履歴が残る。
5. 更新失敗、起動無応答、容量不足、通信断を安全に処理し、復旧できる。
6. OSと補助サービスの保存範囲を明示し、新しい復元先で整合を確認できる。
7. 試験した版・環境・結果・ログ・未検証部分・再開手順が揃っている。

ゲーム機能を追加した候補は、ゲームが停止・過負荷になってもHub/Walletの基本操作を維持できることを追加確認する。LinuxにはCPU/メモリ等の[資源制御機構](https://docs.kernel.org/admin-guide/cgroup-v2.html)があるが、Rockで実際に設定・試験するまで達成済みにはしない。

公開試験鍵・合成データの開発検証なので、「本番で安全」「BlackBerryで動く」「実際のお金を交換できる」とはまだ言わない。型番/BSP/driver/電源・本番鍵/データ保護・実provider/運営条件は次の別ゲート。

## 8. 進める順番と今回やらないこと

承認後の順番は、ベースとnativeの統合→OS起動/安全基礎→既存商品とWalletの縦断操作→保存/復旧の受入。ゲーム交換fixtureと作者SDKは独立して進め、承認されたGame入口/演出を追加後に関連試験をやり直す。

ゲーム本編の新規開発、巨大ストア、全engine対応、新規課金モデル、実送金、ATM現金操作、端末購入/書込み、公開運営は今回の一括実行範囲外。実機・ゲーム/providerが未指定でも進められる合成テストは分ける。

## 9. 確認してほしい内容

- **中心と順番**：Hub＋Walletを中心に、まずQEMUで稼働/復旧できるOSを固める。
- **ゲーム要素**：任意のGame入口を追加する。達成演出は採用するか、入口/交換だけにするか選べる。
- **作者向け**：共通API/SDK・sandbox・サンプルから、組み込みやすさを測って改善する。
- **お金の境界**：ATMは独立・自社手数料0。ゲーム料金/交換方向/実資金は未確定のまま有効化しない。

「この設計で進めて。演出は不要」「この部分を直してから」などの確認を受けてから実行する。未決の実ゲーム/方向は、合成契約開発を承認しても実交換の許可にはならない。
