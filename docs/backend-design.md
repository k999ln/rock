# LOOP バックエンド設計

設計日: 2026-09-05。対象は現在の4ツールとインストール可能なLOOPアプリ。

## 実装する流れ

1. Sitesで識別した利用者が実行を依頼する。
2. サーバーがツールの許可・同時実行・回数制限を確認し、実行IDを発行する。
3. 実行開始は一度だけ取得できる。ブラウザまたは接続済みの同じPCが処理する。
4. 結果本文は端末に残し、成否・経路・時間・処理データ量をサーバーへ報告する。
5. 完了と履歴を同一トランザクションで確定する。通信再送でも件数を増やさない。
6. 開始または完了が届かない記録は期限後に中断扱いとする。再実行は本人が入力を確認して新しい実行IDで行う。

アプリを閉じた後にクラウドがPCを遠隔操作する構成にはしない。4ツールは入力したデータを扱う単発処理。常駐・予約実行は、専用の端末エージェントと機械認証を導入する次段階とする。

## データと境界

| 保存先       | 保存するもの                                                                       | 保存しないもの                    |
| ------------ | ---------------------------------------------------------------------------------- | --------------------------------- |
| D1           | ファンド設定、実行状態、イベント、端末の最終確認、停止設定、売上・経費の手入力記録 | 原稿、成果物、MCPトークン、秘密鍵 |
| 端末         | 実行入力と結果、タブ内のPC接続トークン                                             | 他の利用者の情報                  |
| 外部サービス | 将来の実売上・決済の正本                                                           | 未接続時の架空残高                |

すべての読込・更新に利用者IDを必須とする。利用者IDは公開ホストの認証ヘッダーからのみ取得し、リクエスト本文から受け付けない。変更APIは同一Originのみ。想定外の項目・サイズ超過・不正な数値を拒否し、サーバー内部のエラーを返さない。

## 状態と異常処理

| 状態                                         | 許可する次の状態                  |
| -------------------------------------------- | --------------------------------- |
| queued                                       | running / cancelled / interrupted |
| running                                      | completed / failed / interrupted  |
| completed / failed / cancelled / interrupted | 変更不可                          |

利用者につき同時に1件、直近1時間120件を上限とする。開始・完了の期限は120秒。期限は読込・新規実行時にも評価するため、放置された実行が枠を占有し続けない。実行済みのものをサーバーが自動再実行しない。4ツールは許可リストに固定し、任意シェル・任意URL・任意ホストパスは受け付けない。

PC接続はMCPのtools/listまで応答を確認して記録する。PC接続トークンが存在するだけではオンラインとしない。直近の確認から90秒を超えた端末は状態不明として表示する。履歴の自己申告は決済の証拠には使用しない。

## 売上・費用・還元

まず売上・経費を手入力で記録できる照合前台帳を実装する。金額はJPYの整数、入出力は利用者単位、重複依頼は一度だけ記録。原記録は消去・上書きせず、取消記録を一度だけ追加する。売上から経費を差し引いた記録上の差額を表示し、現金残高や払出可能額とは表示しない。

処理バイト数は入力・出力のUTF-8サイズであり、通信量の実測ではない。電力量・API代は未計測を維持する。$8.88控除・ブースト・分配は既存の試算を使い、手入力台帳や支援額から実際の送金を発生させない。

将来の実会計は専用サービスで、外部イベントIDの重複排除 → 入金照合 → 複式台帳 → 月次締め → 分配債務 → 払出の順に行う。入金・売上・ブースト原資を別勘定に置く。承認済み取引の訂正は反対仕訳、払出は二重承認・冪等キー・照合を必須とする。Sites上では実決済を有効化しない。

## 外部接続の前提

- ウォレット: 今回は接続アドレスのみ。ウォレット署名ログインは、公開認証を提供できるホストでnonce・ドメイン・期限・一度だけの検証を実装する。アドレス接続は実名本人確認の代わりにはならない。
- ココナラ売上: 今回の公式情報調査ではLOOPから利用できる公開売上APIの仕様を確認できていない。利用可能な仕様・認証方法が確定するまで手入力記録を使う。
- 決済・分配: 事業内容に対応する決済サービスと利用許可が必要。Stripeを選べばファンドの資金受付が可能になるという前回答の断定は採用しない。[Stripeの制限対象](https://stripe.com/legal/restricted-businesses)を確認したうえで提供先を決める。

## 検証条件

- 他人の実行・端末・台帳を読み書きできない。
- 同じ依頼の再送、同時の開始、遅れた完了、期限切れで二重確定しない。
- 停止中のツールは新規実行できない。
- 完了した件数と履歴の件数が一致する。
- 費用未計測・売上未接続を0円の実績に置き換えない。
- 手入力記録の重複・二重取消を拒否する。取消後の合計が整合する。
- 既存のファンド設定と4ツールの処理結果を維持する。
