# avocado Mini：本人認証と個人データ管理の追補仕様

更新日：2026-09-27  
対象：Mini / Pro 共通の RockstarOS  
状態：ユーザー要求を反映した実装用の設計案。ソフト実装、部品採用、実機性能、認証試験の完了を意味しない。

## 1. 今回追加する製品要件

1. Miniは独立端末として動作する。基本操作・個人データ保存にPro、外部PC、インターネット接続を必須にしない。
2. 登録者をカメラで見分け、その人のプロフィールを選択する。保護されたセーブ・設定・履歴は、本人認証に成功してから読み出す。
3. 認証に成功したユーザーへ、そのユーザーに許可されたデータだけを開く。別人のデータをプロフィール選択や名前の指定だけで開けない。
4. 利用者交代時は前の利用者のアクセスを閉じ、次の利用者を認証する。離席時も個人情報の出力を止め、ロックする。
5. 生体認証・データ保護の基本方針はMiniとProで共通。Proの追加は処理能力・容量の拡張であり、本人認証の代替にはしない。
6. 製品の映像出力は実空間への表示を目標とする。テレビ接続は前提にしない。スマホは任意のリモコン・追加認証手段とする。

ここでの「本人」は、登録プロフィールに結び付いた認証資格情報を使う人を指す。公的な氏名等の確認は別のKYC手続きで扱う。

## 2. 認識からアクセスまでの実装案

### 処理順序

カメラで個人候補を識別 → 利用意思を確認 → 本人認証 → 対象ユーザー専用のセッションを発行 → セーブ・設定を読み出す → 利用終了でロック

| 処理 | 扱うもの | 制限 |
|---|---|---|
| 個人識別 | 顔特徴とプロフィール候補 | この結果だけで秘密情報を復号したり認証済みにしない |
| 本人認証 | 生体照合、なりすまし対策、保護された資格情報 | 検証済みの認証経路だけが成功を通知できる |
| セッション管理 | 利用者、端末、期限、許可範囲 | 顔候補・KYC済みフラグ・課金ランクから直接発行しない |
| 個人データ管理 | ユーザー別の暗号化データと鍵 | 読取・保存・削除の都度、認証セッションの利用者と一致することを確認 |
| 空間・音声への出力 | 利用者が公開を選んだ情報 | 私信・決済情報などは自動で表示・読み上げない |

### 登録と復旧

- 顔登録は本人の同意を得て行う。既存アカウントへの顔追加・再登録は、既存の認証資格情報または正式な復旧手続きで承認する。
- 背面ボタンは操作意思を確認する入力として利用できるが、押しただけで本人認証済みにはしない。
- 生の顔画像は登録・照合に必要な一時処理に限定する。顔特徴も機密な個人データとして暗号化・アクセス制限・削除対象にする。画像や特徴をログ・クラッシュダンプへ残さない。
- 生体認証が使えない場合の非生体の代替認証・復旧手段を用意する。Mini単体でも使える入力手段と復旧方法は実機設計で決める。音声で秘密の暗証番号を読み上げる方式は採用しない。
- 他端末への顔特徴の同期は初期仕様に含めず、各端末で登録する案を採る。セーブ同期とは分離する。

### 利用者切替と離席

- 別の顔を検出しただけで、進行中のゲームを別人のセーブに書き込まない。
- 切替開始で前の利用者の入力・外部実行受付と機密出力を停止する。許可済みの範囲でチェックポイントを保存し、旧セッションを終了して次の利用者を認証する。
- 離席・認識喪失時の保持時間は、誤検知と情報露出を測定して決める。機密表示の停止はセッション終了待ちにしない。離席検知を完全な本人在席証明と扱わない。
- 複数人・不確実な識別では、個人情報を出さず利用者の選択と認証を求める。
- 非同期ジョブやスマホからの古い操作は、切替後に新しい利用者へ引き継がない。実行中の取消不能な外部処理は、元の利用者と取引IDに結び付けて結果を記録する。
- ロック時はデータを読む権限を失効させ、平文キャッシュと一時鍵を破棄する。主OSが侵害された場合にも何を守れるかは、鍵・認証・実行環境を合わせて検証する。

## 3. 本体単独の生体認証に必要な追加設計

Mini内部に、次の役割を持つ認証系を設ける。正確な部品型番はまだ採用しない。

- 顔照合と写真・動画等へのなりすまし対策を、対象環境で評価できるセンサー／認証処理。
- センサーから認証判定までの改ざん・偽入力への対策。
- 端末の資格情報とユーザーごとのデータ鍵を保護する実行環境。
- 認証結果をユーザー・端末・今回の要求・有効期限へ結び付け、使い回しを拒否する仕組み。
- 認証結果、鍵の使用許可、セッションを結び付ける仕組み。一般アプリが「成功」と送るだけで鍵を使えない設計。顔特徴から直接暗号鍵を生成しない。
- 署名検証を伴う起動・更新、試行回数制限、資格情報の失効・復旧。

R5候補のRGBカメラと8×8距離センサーについて、強い顔認証性能は確認されていない。赤外線・深度を使う方式を含めて比較するが、追加しただけで安全性が成立するとは扱わない。候補ATECC608Cも、単独で顔認証やデータ保護全体を完成させるものではない。

試作段階では、任意のスマホによるパスキー認証を追加経路にできる。これは本体だけの生体認証が完成した証拠にはしない。生体認証が未検証の試作品では、保護データをカメラ識別だけで自動解錠しない。

## 4. 現段階で何が可能か

この作業フォルダで確認できたものは、設計資料・検討画像・資料処理ファイルであり、Mini向けの動作する製品ソフト、接続済み実機、認証試験結果は確認できていない。

| 機能 | 現在の判断 | 次に必要な確認 |
|---|---|---|
| 顔の登録・個人候補の識別 | 既存技術で試作可能。Miniでは未実証 | モデル、距離、照明、誤識別、処理負荷 |
| 人別セーブ・設定・再開 | ソフトの実装を開始できる | 切替時のデータ分離、停電・再起動復旧 |
| 認証後だけ個人データへアクセス | 標準的な認証・アクセス制御で試作可能 | 鍵管理、認証結果の信頼性、越権アクセス |
| 本体だけで強い顔認証 | 要求に追加。構成・性能は未確定 | 認証系部品、なりすまし評価、信頼できる処理経路 |
| 手の操作・短い音声命令 | 既存技術で試作可能。候補部品での同時性能は未実証 | 誤操作、声の認識、遅延、発熱 |
| 音声・状態灯による反応 | 部品・配置を決めて試作可能 | スピーカーと発光部の型番、配置、出力 |
| スマホのリモコン | アプリとローカル通信を試作可能 | 明示的なペアリング、端末別権限、切替時の失効 |
| 暗号化同期・Pro連携 | ソフトとサービスの設計・試作対象 | 同期競合、端末承認、鍵配布、復旧、Proの構成 |
| KYC・決済 | 外部事業者との連携構想 | 対応サービスと手続き、本人・取引・認証セッションの結合 |
| 画像に描いた裸眼空間表示 | 現時点で実現可能と確約できない | 表示原理、視域、明るさ、安全、200mm内の収納と熱 |

部品が存在すること、設計案があること、UIの画像があることは、製品が動作する証拠にはしない。

## 5. 最初の試作の合格条件

1. Aが認証するとAのセーブを読める。AのセッションからBの識別子を指定しても、Bのデータを読取・変更・削除できない。
2. 顔の候補が一致しただけでは認証済みにならない。写真、録画、認証成功イベントの偽造、過去の認証結果の再利用で保護領域が開かないことを評価する。
3. AからBへ切り替える際、旧入力・スマホ操作・遅延ジョブがBのデータを変更しない。
4. 離席、手動ロック、再起動で機密出力が閉じ、再認証前に個人データが出ない。
5. ネット切断でも、検証済みのローカル認証と基本の保存・再開が動く。未完了のオンライン本人確認や決済は成功扱いにしない。
6. 保存領域の取得やログの閲覧から、平文のセーブ・顔特徴・秘密鍵が流出しないことを、想定する攻撃範囲を定めて確認する。
7. 生体認証の誤受入・誤拒否・なりすまし受入率、遅延の合格基準を試験前に決め、条件別に測る。数例成功したことを安全性の証明としない。
8. 空間表示には別の成立試験を設ける。認証ソフトの試験画面や生成画像を表示エンジンの実証に数えない。

これらは受入計画であり、実行・合格済みの一覧ではない。

## 6. 関連方針

- ハードウェア能力、アカウントの紐付け、KYC状態、現在の認証状態、契約・購入権限は別項目で管理する。一本の「ランク」だけで全権限を与えない。
- KYC済みでも現在の操作者の認証を省略しない。決済は金額・相手先・対象が定まった取引ごとに承認する。
- 個人データへのアクセス制限は、周囲から見えない表示を保証しない。空間表示・スピーカーは周囲に内容が伝わる出力として設計する。
- 生体認証が失敗しても、停止操作や安全機能は使えるようにする。
