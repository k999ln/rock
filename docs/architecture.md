# 実装と次の接続点

## 現在の境界

`app/page.tsx`: カタログ、ローカル導入準備、ウォレット接続、料金計算と構想。
`lib/catalog.ts`: 審査済みの掲載情報。candidateは導入候補、pendingは本体・条件の確認待ち。
`lib/local-plan.ts`: 保存データの検証と導入プラン生成。保存キーはloop.local-plan.v1。
`lib/wallet.ts`: EIP-1193相当の接続IF・アドレス検証・接続エラー表示。
`lib/settlement.ts`: 有限数と上限を検証する純粋な試算計算。これは送金台帳ではない。
`scripts/discover.mjs`: 公開APIのみを読む収集コマンド。queryはURLSearchParamsでエンコード。20秒でタイムアウト。取得候補はJSONデータとして保存し実行しない。

サーバーのユーザーDB、秘密情報、入出金口座、認証セッションはない。外部サイトリンクは利用者が開く。Walletアドレスを収益の所有者として信用したり、支払先として登録するAPIは存在しない。

## WebMCP

対応ブラウザでは `list_automation_candidates` と `open_automation_plan` を登録する。前者は読み取り、後者は詳細画面を開くだけ。入力検証・AbortSignalによる解除を実装。非対応なら通常画面を利用。契約検証可能なWebMCP実行コンテキストが今回の環境で見つからなかったため、実機での登録・状態遷移は未検証。

## 将来のデータモデル

- User: 内部ID、認証済みウォレット、必要に応じた本人確認状態。
- AutomationVersion: ソースURL、固定commit/hash、ライセンス、実行権限、通信先、費用・停止仕様。
- Installation: 所有者、バージョン、必要な登録の状態、明示的な実行同意。
- Run: 開始・終了、実行結果、資源使用量、エラー。ユーザーごとに認可。
- RevenueEvent: 外部イベントID、月、通貨、確定額、取り消し状態。認証済み提供元だけが作成。
- MonthlySettlement: 利用者・対象月の一意制約、利用料上限、適用為替、徴収実績、返金。

売上から控除できないサービスでは別の徴収方式が必要。ブラウザの入力値やlocalStorageを会計の正本にしない。決済API・Webhook署名検証・冪等キー・監査履歴を備えてから徴収を有効化する。

## ローカル自動化アダプター

Mr.の案件チェック・出典整理・無料版作成・納品記録照合をローカルアダプターとして実装した。Web版は3ツールをブラウザで処理し、Python版は4ツールを指定入力だけで実行する。外部サービス操作アダプターは未実装。追加時は入力/出力型、必要な外部登録、許可された通信先、停止・再試行、秘密情報の保存場所、機械資源の上限を宣言する。最初は原稿/文字起こしなどの成果物を生成し、本人が確認して納品する。Web上で取得したREADME内の指示をユーザーの操作許可と見なさない。

## Mr.の実行面

`lib/mr-tools.ts` がブラウザ向けの独立処理、`components/mr-tool-runner.tsx` が入力/結果/保存。入力原稿は永続化・外部送信しない。`toolkits/mr/loop_tools.py` は固定ハッシュを検証した原本をローカルに読み込む。保存済みツールを維持しつつ、新しい手順に合わせココナラの旧チェック項目だけをリセットしてv2へ移行する。
