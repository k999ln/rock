## 1. 変えてはいけない製品ベース

最初に `AGENTS.md`、`docs/product-baseline.md`、`data/product-baseline.json`、`docs/prompt-playbook.md` を読み、RQ01〜RQ11を基準にしてください。出発ブランチにない場合は最新mainの該当ファイルを読み、段階0で作業ブランチへ取り込んでください。

- tob側が個別の商品を開発・提供・保守し、RockはHub、接続adapter/SDK、資格、権限、実行・停止、結果、費用、収益照合・Walletの共通基盤を作ります。tobを特定企業や独占契約と推測せず、商品の業務ロジックやAIをOS側で一から作り直さないでください。
- 現在Gitにあるツールも独立商品です。通常の商品追加・更新にOS全体の再buildを要求しない構成を維持します。既存Hub、商品schema、Walletを調べず新設・置換しないでください。
- 標準の入口はHubとWallet。日常生活の汎用アシスタント、巨大ストア、ファンド中心のエコシステムへ広げないでください。
- 実行場所、ホスト運用者、接続方式、複数工程、料金、ライセンス、契約・利用資格、キー所有者/BYOK、実行費用は別軸です。OSSでも有料APIや運用費が必要な商品を扱います。全商品をMCPや同じOAuth方式へ強制しないでください。
- nativeの同一契約につき月888 USD cents固定・複数端末重複防止を保持し、旧Webの上限試算、商品代、外部API費と混同しないでください。新料金・手数料・分配率を創作しないでください。
- BlackBerry優先・機種/variant未定、Linux/Buildroot/ARM64 QEMUのnative開発と、旧Android/AOSP・Pixel計画を区別してください。携帯端末の価値をhost画面やQEMUの成功だけで証明したことにしないでください。

同じ製品要望を利用者に聞き直さず、実装に必要な未決条件だけを具体的な選択肢・影響とともに示してください。

## 3. 実装する順番と段階ごとの合格条件

### 段階0 — 開発ブランチへベースと優先順位を反映する（GAP01、B04）

1. `npm run prompt:context` または同等の読み取りでmain・全branch・関連open/closed PR・40桁SHA・同一SHAのCIを取得し、対象ソースをfetchして固定します。取得失敗や途中のref変更を最新確認済みとしないでください。
2. 対象SHAのREADME、project、進捗JSON、CHECKPOINT、native統合/検証文書、native README、実装・テストを読みます。利用者の未commit変更や稼働中のVMを触らず、分離した作業ブランチを用意します。nativeが未マージならその最新ソースを出発点にし、マージ済みなら最新mainを使います。
3. 最新の製品ベース・作成規約・本プロンプトと関連検査を作業ブランチへ取り込みます。AGENTS、README、project、進捗JSON、CHECKPOINT、native統合設計の正本参照と次作業を整合させます。片側の全採用でnative実装・Nタスク・検証記録を落とさず、ベースのRQも失わないでください。
4. 優先順位を「引継ぎ同期→既存商品の実利用・改善前測定→商品条件/実行adapter→Wallet接続→同条件の再試験」に統一します。既存B01は文書保存の完了にとどめ、B04は引継ぎ同期、B02は段階1〜2の基礎、B03はWallet接続、B05は段階4の比較・再試験を追跡します。旧OS02〜OS05はAndroid/AOSP別トラックと明記します。
5. N02の未適用起動patch、N03の機種適合、N04/N05の未検証事項、通常gate外の旧ATM fixtureの失敗/skipは保持します。Hub試験を妨げる起動・安全性の問題は必要最小限を先に直しますが、機種選定や実機完成を独立したHub/Wallet作業の一律の前提にしません。

合格証拠: 両入力SHA、統合方法・commit、競合箇所と保持した契約、入口文書間で一致する次作業、`baseline:check` と `project:check` の結果を残してください。「mainに文書がある」だけではGAP01解消ではありません。対象作業ブランチでの反映と、元nativeブランチ/mainへの反映状態を分け、再開先を明記してください。

### 段階1 — 既存商品をHubから使い、改善前の不便を測る（GAP04、B02）

nativeの `os/tools/README.md`、`os/tools/packages/`、`examples/registry/` にある提案下書き `org.rockstar.proposal-draft`（1.0.0/1.1.0）、引用整理 `org.rockstar.citation-organizer`、入力テキストhash `org.rockstar.utf8-sha256` を棚卸ししてください。登録済みならその商品を使い、未登録なら既存の開発用署名・配布契約で登録します。公開テスト鍵や `LicenseRef-Development-Only` を本番署名/商用配布許諾としないでください。

Rock rootの `toolkits/mr/README.md`、`toolkits/mr/rock_star_tools.py`、`toolkits/mr/mcp_server.py`、`vendor/mr` にある案件チェック・出典整理・無料版作成・納品記録照合も確認してください。nativeと同名でもsource/ref/hash・入出力・権利を照合し、別の商品実体を勝手に同一視しないでください。

- 提案下書きと引用整理を、正しい入力形式の合成案件/原稿でHub画面から実行します。検索→必要準備→導入/接続→許可/料金確認→入力→実行→結果保存/再表示→失敗/停止/復旧まで通してください。hashだけの試験で業務用途を代替しないでください。
- PC商品も最低1件、既存の業務ロジックを保持してHubから実プロセスへ接続してください。現在の有限recipeへ任意shell/rootを追加する方式を使わず、範囲を限定したadapter/companionとして接続します。利用者が選んだ入力以外のファイル・秘密情報・外部送信を許可しないでください。
- 改修前に、同じ業務を既存PC/サービスの手順で行った結果と、現状のHubで行った結果を記録します。Hubでは実行不能なら、その事実・原因・到達点を改善前値にします。成功時間を捏造せず、接続に必要な最小修正後の初回値と区別してください。
- 技術用語、手動設定、入力形式、待ち状態、結果の場所、停止・再開で詰まる箇所を記録し、Hub/adapter側の修正に結び付けます。商品内部の別機能開発へ広げません。

合格証拠: 使用商品と版・source、合成入力、Hub操作記録、実プロセス呼出/実結果、準備時間・操作数・画面切替数・手動コピー数・初回結果/復旧までの時間、未対応条件を保存してください。CLI単体・商品カード・固定の成功出力だけでは未完了です。host、Linux guest、別PC、実USB、BlackBerryを区別してください。

### 段階2 — 多様な商品条件を「動く接続」へ広げる（GAP02、B02）

既存 `src/blackberryrock/packages.py`、`schemas/recipe-manifest-v4.schema.json`、`src/blackberryrock/hub.py`、`os/service_access/`、`os/ai_routes/`、`os/runner/`、`os/mcp_broker/` と、Webの `lib/catalog.ts` を再利用します。段階1の実商品で見つけた不足から最小の拡張を選びます。

1. 商品ID/版/供給者/source/権利と、実行場所（端末・PC・サーバー/cloud）/運用者（利用者・提供者等）/接続方式/複数工程を分けます。導入はpackage installだけでなく、外部サービス接続やPC companionも表現してください。
2. 商品料金（無料・買い切り・月額・従量・無料枠等）、実行費、必要契約、価格版/有効期限、利用資格、キー所有者/BYOKを独立して扱います。ソース、モデル、依存物、再配布条件も区別します。
3. 既存v2/v3/v4と無料recipeの署名・互換性・安全制限を保持し、新しい商品契約をカタログ、導入、資格判定、見積/同意、adapter、実行、receipt/利用量、費用照合まで接続します。USD 0制限を削るだけ、またはJSON項目を増やすだけで終えないでください。
4. 接続切れ・契約切れ・キー失効・権限不足・価格変更・予算不足を実行前に判定し、利用者へ理由と必要な再開操作を返します。未知の価格や送信先を黙って承認せず、非対応は非対応と表示してください。
5. PC sleep、端末offline、クラウド継続、再接続、取消要求と停止確認を商品能力に応じて扱います。外部直契約や停止APIがないサービスの即時停止・厳密な課金上限は保証しません。許可外の送信先/実行先へ自動fallbackしないでください。

合格証拠: 無料端末、OSS PC、有料API併用、外部月額cloud、従量cloud、BYOK、self-host、複数工程の組合せを合成fixtureで判定します。非ゼロ料金・外部契約・BYOKについて、許可ありの開始→adapter処理→実行receipt/利用量→費用照合と、期限切れ/予算不足/条件変更の拒否を試験してください。金額はテスト値と明記し、既存無料ツールを勝手に値上げしないでください。fixture上の対応と、接続確認済みの実商品は別一覧にします。選ぶprotocol/providerの実仕様は公式一次資料で確認し、実providerを未接続のまま対応済みとしないでください。

### 段階3 — 実行費用・取引・既存Walletを接続する（GAP03、B03）

B03の着手条件はB02の段階1〜2（実商品操作・改善前測定・必要なHub改善・商品契約/adapter基礎）の合格です。Wallet接続後の最終比較はB05へ分け、B02の完了条件に段階4を重ねて依存を循環させないでください。

`src/blackberryrock/wallet.py` と `os/wallet_backend/` の追記journal、整数金額、複式の保存則、購入者資格/同意、月額の冪等性、不明応答の照合を再利用してください。現在のlocal/remote構成を確認し、remoteならbackend台帳を正本として第二の残高正本や暗黙のlocal切替を作らないでください。

- 商品、Work/Run、実行receipt、外部取引、費用、売上、入金先、照合状態の対応を永続化します。利用者の仕事の収益、tobの商品販売、Rock利用料の所有者と支払先を分けます。一括入金/複数Run等の多対多を根拠付きで扱い、外部直払い費用をWalletから再徴収しないでください。
- Hubの実行成功だけで売上や利用可能残高を増やさないでください。手入力は未照合、外部未接続は未接続と表示します。Webhook署名だけでなく、対象providerアカウント・取引・所有者・金額・通貨・確定/入金状態を認証済み情報と照合する境界を設けます。
- 重複イベント、順序逆転、通信断、処理結果不明、再起動、取消/返金、照合差異を試験し、無条件の再実行・二重請求・二重計上を防ぎます。出金済み/返金済みの履歴を現在残高へ足さず、別通貨を無換算で合計しません。
- 同一契約の複数端末でも月888 centsは重複させません。Rock有料サービスの資格と無料/offline商品の資格を混同せず、未払い時も自分のデータと回復経路を保持してください。

合格状態は必ず分けて記録してください。

1. 台帳連携コードと移行/互換テストの完了。
2. 合成取引によるHub→実行→費用/売上イベント→Wallet照合の縦断成功。画面と証拠はテスト専用と明記。
3. 利用可能かつ許可済みのprovider sandboxによる接続・認証・照合成功。接続条件がなければ未実施。
4. 認証済み実取引による実収益照合。今回の範囲では未実施とし、別の権限・接続準備後に検証。

1〜2だけで「実収益未接続を解消」「お金を受け取れる」と報告しないでください。3〜4が未完ならGAP03を残し、必要なprovider/接続情報・契約/同意・対象取引・安全な試験・再開条件を具体化します。providerや資金保管方式を勝手に決定したり、新規契約・課金・送金を開始したりしないでください。依存しないadapterと合成試験は先に進めます。

### 段階4 — 同じ仕事を再試験し、解決した不便を確認する（GAP04、B05）

段階3の1〜2が通れば、B03/GAP03の実サービス検証が未完でもB05へ進めます。B05はB02の基礎に依存し、B03全体の完了を待ちません。B03は未完部分を残し、台帳/fixture基礎の合格証拠をB05の着手記録に添えてください。

段階1と同じ業務・入力・環境条件で、Hub→接続/資格/費用→実行→結果/receipt→Walletの状態確認を再試験してください。準備込みの初回と日常の繰返しを分け、改善前・改善後・既存PC/サービス手順を比較します。

「何を契約/起動すればよいか分からない」「PCやサービスを巡回する」「出先で止められない」「成果が散らばる」「費用と入金がつながらない」のどれが減ったかを実測で示してください。端末を追加する準備・管理の手間も含め、良くならなかった点やPC/Webで十分な点も残します。

外出利用・通知からの対処・通信断復帰・本人の認証/停止操作を検証対象にします。実機がない場合は実施可能なhost/guestで関連動作を試験し、携帯端末固有の価値や省電力/入力性は未実証としてください。「PCには不可能」「専用端末でなければ成立しない」と根拠なく主張しません。日中何度も見たくなる理由は、意味のある成果・停止・費用/入金・必要確認に置き、無関係な通知を増やさないでください。

合格証拠: 同条件の比較結果、見つけた不便→原因→修正→再試験、残る不便と未実証事項、利用者向けの開始/入力/結果/停止/復旧手順。改善がなければ達成とせず、共通基盤内の次の最小改善へ反映します。B05の比較記録が完成しても、実機や外出利用が未検証ならGAP04の携帯端末価値は未実証として残してください。
