## 製品の役割

tob側が個別のAI自動化商品を開発・提供し、RockはHub、接続、資格、権限、実行、停止、結果、費用、収益/Walletを管理します。tobを特定企業や独占契約と推測しないでください。現在開発中のツールも独立した商品です。SDK/adapterはOS側の接続基盤として維持し、商品の業務ロジックやAIの作り直しを今回のOS開発へ追加しないでください。

入口はHubとWallet。携帯端末では実行状態、問題への対処、成果、費用、入金/照合を短時間で確認できることを重視してください。汎用生活アシスタントや巨大ストア化を追加目標にしないでください。

## 今回先に行う実装

**最初の実利用試験（RQ11）を、汎用契約の全面拡張より先に行ってください。** nativeの `os/tools/README.md`、`os/tools/packages/`、`examples/registry/` にある `org.rockstar.proposal-draft`、`org.rockstar.citation-organizer`、`org.rockstar.utf8-sha256` の3商品・提案の更新版を確認します。既にHub登録済みなら重複登録せず、その商品を使ってください。未登録なら現在の署名/配布契約でローカル開発用Hubへ登録・接続します。`LicenseRef-Development-Only`や公開テスト署名を商用配布許諾/本番署名として扱わないでください。

mainの `toolkits/mr/README.md`、`toolkits/mr/rock_star_tools.py`、`toolkits/mr/mcp_server.py`、`vendor/mr` にある案件チェック・出典整理・無料版作成・納品記録照合も棚卸しし、既存のPC実行をHubへ接続する最小adapterを評価してください。native同名ツールとの同一性は確認が必要です。非対応商品は不足する契約や実行先を特定し、利用可能と偽らず、既存業務ロジックを保持して接続する方針を記録してください。

少なくともnativeの提案下書きと引用整理を実入力形式の合成案件/原稿で使い、準備→検索→導入/接続→許可→入力→実行→成果保存/再表示→失敗/停止/再開を利用者向けHub画面から通してください。既存PC商品も最低1件、利用可能な環境でHub経由の実プロセス呼出を検証します。Macからのhost試験、Linux guest、実PC接続、BlackBerryは別々に証拠を残し、fixtureで実PC成功を代替しないでください。

利用準備の説明不足、技術用語、入力方法、待ち状態、成果を見つけにくい問題を発見したら、Hub/adapter側を修正して同じ操作を再試験します。非対応環境で証拠が得られない場合は、実施可能な試験と不足条件を残します。UI自体を未操作なら実利用検証は未完了です。

修正前後で「何を設定するか分からない」「別サービスを巡回する」「外出中に停止/確認できない」「成果が散らばる」「費用と収益が分からない」のどれを減らしたかを記録し、操作数、初回結果までの時間、画面切替、手動コピー、復旧時間で比較してください。良くならなかった点も記録し、架空の短縮時間/収益を作らないでください。測定結果を次の1〜5の設計優先度へ反映します。

1. **既存商品と契約の棚卸し（RQ02〜05）**。nativeの `src/blackberryrock/packages.py`、`schemas/recipe-manifest-v4.schema.json`、`os/tools/`、Webの `lib/catalog.ts`、Mr.固定原本を読み、ID/source/版/実行先/料金/権利/状態を対応付けてください。既存v2/3/4の署名・互換性を保持します。未知の任意コードの権限を有限recipeに追加して対応扱いにしないでください。

2. **商品条件を独立した軸で表現（RQ03〜05、08）**。実行場所（端末/PC/サーバー/クラウド）、ホスト運用者、接続adapter、複数工程、ライセンス/ソース/モデル条件、商品料金/実費、資格/認証/BYOKを別項目にします。クラウド商品は接続登録、PC商品はcompanion接続等、方式ごとの導入を表現します。既存USD 0/run recipeを壊さず、有料/外部契約を表す新契約と移行adapterを追加してください。金額不明・未対応は利用可能と偽らず、その判断に必要な条件だけを止めます。

3. **実行可能性と費用を共通判定（RQ04〜05、08）**。既存 `os/service_access/`、`os/ai_routes/`、`os/runner/`、`os/mcp_broker/` を再利用し、接続、資格、必要権限、送信範囲、価格版、予算から開始可否と再開手順を返します。Rock月888 cents、商品代、外部API費を分けます。外部直契約の予算はproviderが制限できる範囲のみ保証します。未知の価格で無制限に走らせないでください。

4. **実行とお金を接続（RQ06、08）**。既存 `src/blackberryrock/wallet.py` と `os/wallet_backend/` の追記journal、整数金額、保存則、月額の冪等性、取消/結果不明照合を保持します。local/remoteの現在の構成を確認し、remoteならbackend台帳を正本として暗黙切替をしないでください。商品/Work/Run/外部取引と収益/費用を紐付ける契約を追加し、第二の残高正本を作らないでください。利用者の収益、tob商品販売、Rock手数料を別の所有者/取引として管理します。一括精算や多対多の対応を許し、対応根拠のない収益は未照合にします。provider本番接続時は署名だけでなく認証済み実取引と照合する契約にし、今回は公開fixtureの合成取引で試験して実収益と表示しないでください。

5. **HubからWalletまでの縦断（RQ01、03、07）**。商品選択→必要契約/接続と費用確認→実行→進捗/停止→成果/receipt→認証済みの合成収益イベント→Wallet照合を一連で実装します。利用者画面は動く場所、契約の必要性、送信データ、料金、実行/照合状態と次の操作を分かるようにしてください。詳細protocol名は診断向けにします。接続断でも外部jobが動き得ること、停止要求と停止確認、表示の最終同期時刻を扱ってください。

実装順は上記の依存順を基本に、現在のコードと失敗テストから必要な最小範囲を選んでください。BlackBerryの適合や実providerの契約待ちで進められない試験は残課題として分け、独立したhost/fixture作業を進めてください。実資金、実機書込み、本番公開の開始はこのプロンプトに含めません。

## 合格条件

- 既存の業務用途商品（提案/引用）をHub画面から実行し、実際の結果を再表示できる。PC商品1件もHubから実プロセスへ接続する。商品カードや単体CLIテストだけではこの条件を満たさない。
- 利用者向けに必要環境、契約/費用、利用開始、入力例、結果の場所、停止、問題時の手順を残す。対応環境と未検証環境が分かる。
- 解決する不便と改善前後の操作/時間を記録する。専用OS/携帯端末が有利だった点、既存PC/Webで十分だった点、未実証の価値を区別する。

- 無料端末商品、OSSのPC商品、有料API併用、外部月額cloud、従量cloud、BYOK、self-host、複数工程のfixtureで、実行場所・料金・ライセンスの組合せを判定できる。fixtureと接続確認済み実商品を区別する。
- 現在の商品候補を少なくとも1件、source/版/権利を確認して既存runtimeのままHubへ対応付け、結果と履歴を取得できる。価格や収益を捏造しない。
- PC停止/契約切れ/キー失効/価格変更/予算不足では理由を示す。許可外実行先や送信先への変更を拒否する。
- 再起動、接続断、取消応答消失、二重receipt、Webhook重複/順序逆転、不明応答を試験し、勝手な再実行・二重請求・二重計上を起こさない。外部に冪等性や停止能力がない場合は照合待ちとして扱う。
- 実行成功だけでは売上や払出可能額が増えない。未照合・保留・利用可能を分ける。出金済み/返金済み等の履歴を現在残高へ足さない。別通貨を無換算で合計しない。
- 同一契約の複数端末でも月額を重複請求しない。無料/offline商品の資格とRockの有料サービス資格を混同せず、未払い時の自分のデータ/回復経路を保持する。
- 適切なnative、Wallet、商品契約の変更前後テスト、`npm run baseline:check`、`npm run project:update`、`npm run verify`を実行する。Android runtimeを変えた場合だけ対応する追加試験も行う。
- 検証はhost/fixture/仮想OS/provider sandbox/実機/本番の別を明記し、入力SHA、実行条件、結果、未実施を保存する。変更していないOSイメージの起動成功を新成果として報告しない。

## ベースの先の改善
